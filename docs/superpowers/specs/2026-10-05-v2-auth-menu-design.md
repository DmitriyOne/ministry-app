# v2: авторизация, роли, нижняя навигация — дизайн

Дата: 2026-10-05. Ветка: `release/v2` (отделена от `develop` после
мержа PR #6 с `CHANGELOG.md` 1.0.0).

Документ по-русски — по тому же правилу, что `CLAUDE.md` и ADR: рабочая
запись о проекте, а не часть продукта.

## Задача

v1 — релиз Coming soon: `LAUNCH_MODE = "coming-soon"` держит `/day`
закрытым заглушкой `/soon`, а сам `/day` — пробник, который опрашивает
Edge Function `health`. v2 открывает приложение людям, которым владелец
выдал учётные данные лично, и задаёт каркас навигации под будущие
экраны.

В объём v2 входит: вход по email и паролю, роли в JWT, гвард роли на
фронте, нижняя навигация из пяти пунктов, пять новых экранов (у всех,
кроме `/profile`, только заголовок), общий механизм тостов и
классификация отказов бэкенда.

**Не входит:** таблицы записей служения и работающий экран дня,
экран администрирования людей, самостоятельная регистрация, вход через
сторонних провайдеров, отправка письма для сброса пароля.

## Что человек видит

Три гейта складываются последовательно:

```
Safari на iPhone, браузер          →  /install        (LaunchGate, как в v1)
со значка, нет сессии              →  /login          (proxy.ts, новое)
со значка, есть сессия             →  приложение
не iPhone / не Safari              →  /access/*       (proxy.ts, как в v1)
DEV_MODE=true                      →  всё напрямую    (как в v1)
```

После успешного входа — переход на `/day` и тост «Welcome back, ИМЯ».

## Решения

Каждое решение фиксируется ADR; номера — в разделе «ADR» ниже.

### D1. Вход — email и пароль, регистрация выключена

`signInWithPassword({ email, password })`. `enable_signup = false` в
`config.toml` и в облачном дашборде: учётные записи создаёт владелец в
Studio. Вариант «username + синтетический email» отклонён — он ломает
сброс пароля навсегда и расходится с макетом `login.html`, где поле
подписано «Эл. почта».

### D2. `profiles` и `user_roles` с настоящими RLS-политиками

```sql
create type public.app_role as enum ('user', 'admin');

create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()  -- общий триггер set_updated_at
);

create table public.user_roles (
  user_id uuid primary key references auth.users on delete cascade,
  role public.app_role not null default 'user'
);
```

**Это осознанное отступление от модели доступа v1.** Правило v1 (ADR
0033/0037) — «таблица в `public` закрывается полностью, наружу только
`execute` на RPC» — выведено из задачи, где анонимный посетитель пишет
в таблицу, которую не должен читать. Здесь задача другая: строки
принадлежат конкретному человеку и читаются им же от своего имени, под
его собственным JWT. Для этого случая RLS-политика — прямой инструмент,
а RPC-обёртка была бы лишним слоем, который пришлось бы писать и
тестировать без выигрыша в безопасности.

```sql
alter table public.profiles enable row level security;
alter table public.user_roles enable row level security;

create policy "read own profile" on public.profiles
  for select to authenticated using ((select auth.uid()) = id);
create policy "update own profile" on public.profiles
  for update to authenticated using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);
```

Grant на `update` — **колоночный** (`grant update (display_name)`), не
табличный: политика ограничивает строки, а не колонки, и при табличном
grant клиент может переписать свой `created_at`. `updated_at`
поддерживает общий триггер `public.set_updated_at()` — `profiles` первая
таблица, которую клиент правит напрямую, а не через RPC, поэтому у поля
нет другого места, где его можно выставить, не доверяя клиенту.

`insert` и `delete` на `profiles` политик не получают: аккаунты создаёт
владелец, человек не может ни создать себе профиль, ни удалить его.
`user_roles` не получает **ни одной** политики для `authenticated` —
роль человек узнаёт из своего JWT, а не чтением таблицы; запись — только
`service_role`. То есть `user_roles` остаётся ровно в модели v1, а
исключение касается только `profiles`.

`(select auth.uid())` в политике, а не `auth.uid()` — так планировщик
вычисляет значение один раз на запрос, а не на строку.

### D3. Профиль и роль создаются триггером

Триггер `after insert on auth.users` создаёт строку в `profiles`
(`display_name` из `raw_user_meta_data->>'display_name'`, иначе —
локальная часть email) и строку в `user_roles` с ролью `user`. Благодаря
этому владелец создаёт человека одним действием в Studio и больше ничего
не делает руками; роль `admin` выставляется правкой `user_roles`.

Функция триггера — `security definer` с `set search_path = ''`, иначе у
неё не будет прав на запись в таблицы `public`.

### D4. Роль в JWT через `custom_access_token_hook`, без `role_permissions`

Хук по документации Supabase кладёт в claims `user_role`:

```sql
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb language plpgsql stable security definer set search_path = '';

grant usage on schema public to supabase_auth_admin;
grant execute on function public.custom_access_token_hook to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook from public, anon, authenticated;
grant select on public.user_roles to supabase_auth_admin;
```

Второй половины примера из документации — таблицы `role_permissions` и
функции `authorize(permission)` — **не делаем**. При двух ролях и
отсутствии таблиц данных это слой, у которого нет ни одного потребителя:
проверять `authorize('records.delete')` негде, пока нет `records`.
Вернём вместе с первыми таблицами служения, и тогда у решения будет
обоснование из реальных политик, а не из примера в документации.

Включение хука — **настройка проекта, миграцией не выставляется**:
`[auth.hook.custom_access_token]` в `config.toml` для локальной среды и
Authentication → Hooks в облачном дашборде для прода. Это ручной шаг
релиза, и он попадёт в ADR как обязательный.

### D5. Две роли, `admin` ничего не охраняет

`app_role` — enum, не `text`: опечатка в роли должна падать на вставке,
а не всплывать в проверке прав. Роли две — `user` и `admin`.

Гвард `hasRole` написан и покрыт юнит-тестами, но в v2 **не блокирует ни
одного маршрута**: `/admin` не создаётся. Единственное место, где роль
видна, — `/profile`, там выводится её название. Так решил владелец, и
это сознательный выбор: инфраструктура готова, поверхность для неё
появится вместе с администрированием.

### D6. `LAUNCH_MODE` удаляется, доступ решает сессия

`web/src/app/config/launch-mode.ts` удаляется целиком. В `proxy.ts`
порядок проверок:

1. `env.DEV_MODE` → пропустить всё.
2. Путь не из `APP_ROUTES` → пропустить (чтобы `/qwerty` давал настоящий
   404, как в v1).
3. Классификация `User-Agent` → не iPhone Safari → 307 на `/access/*`.
4. Сессия: нет на экране приложения → `/login`; есть на `/login` или
   `/forgot-password` → `/day`.

Сессия читается `createServerClient` из `@supabase/ssr` по кукам запроса
и `getClaims()`.

### D7. `getClaims()`, а не `getUser()`

`getClaims()` проверяет подпись и срок действия токена локально.
`getUser()` на каждый запрос дёргает Auth-сервер — единственное, что он
даёт дополнительно, это обнаружение отозванной на другом устройстве
сессии. В официальном примере middleware Supabase используется именно
`getClaims()`, и в документации прямо сказано, что для авторизации
запроса его достаточно. При одном человеке на устройство разница в
безопасности пренебрежимо мала, а разница в задержке — сетевой вызов на
каждую навигацию.

Обновлённые куки сессии **обязательно переносятся на redirect-ответ**
(`myNewResponse.cookies.setAll(supabaseResponse.cookies.getAll())` плюс
заголовки `cache-control`/`expires`/`pragma`) — без этого людей будет
случайно разлогинивать, о чём предупреждает документация.

### D8. Требование установки сохраняется, `/soon` становится публичным

`LaunchGate` остаётся как есть: без запуска со значка человек уходит на
`/install`. `/login` и `/forgot-password` добавляются и в `APP_ROUTES`
(щит устройства на них действует), и в `APP_SCREEN_PATHS` LaunchGate
(требуют установки) — владелец выбрал порядок «сначала установка, потом
логин».

`/soon` **выводится** из `APP_SCREEN_PATHS` и становится настоящим
публичным лендингом, открытым в обычной вкладке Safari. Без этого после
удаления `LAUNCH_MODE` на него не попадёт никто и никогда: `rewrite` с
`/day` был единственным входом, а форма вайтлиста осталась бы мёртвым
кодом.

### D9. Маршруты v2

| Путь | Экран | Содержимое в v2 |
|---|---|---|
| `/login` | вход | форма email + пароль, ссылка на сброс |
| `/forgot-password` | запрос сброса | поле email, нейтральный экран успеха |
| `/calendar` | календарь | только заголовок |
| `/month` | месяц | только заголовок |
| `/day` | день | только заголовок (центральная «+» в меню) |
| `/year` | год | только заголовок |
| `/profile` | профиль | имя, роль, выход, About, Privacy |

Все литералы — в `shared/config/routes.ts` (ADR 0030).

### D10. Route group `(app-shell)`, ссылки About/Privacy переезжают на `/profile`

Новая группа `app/(app-shell)/` с общим `layout.tsx`, который добавляет
`BottomNav`. В неё переезжают `/calendar`, `/month`, `/day`, `/year`,
`/profile`. Группа `(with-footer)` остаётся для `/`, `/soon`,
`/install`, `/about`, `/privacy`.

Текстовый футер со ссылками «About» и «Privacy & cookies» внутри
приложения не остаётся: две тихие текстовые ссылки под стеклянной
панелью навигации — визуальный мусор, а естественное место для них —
`/profile`. Публичные экраны футер сохраняют, поэтому ссылки не теряются
для посетителя, который до приложения не дошёл.

### D11. Четыре класса отказа, у каждого своё место

Проверено по `features/join-waitlist/api/join-waitlist-action.ts`:
серверное действие там оборачивает обращение к Supabase в `try/catch` и
возвращает `{ status: "error", formError }`. **Значит 500 при
недоступном бэкенде не возникает** — `error.tsx` ловит исключения
рендера, а не отвергнутые промисы действий, если действие их не бросает.

Но текущая форма хуже 500 по другой причине: «неверный ввод» и «база
недоступна» показываются одинаково — общим текстом под формой. Человек
думает, что ошибся, и перебирает ввод, хотя причина не в нём. Поэтому
классы разделяются явно:

| Что случилось | Где видно | Почему так |
|---|---|---|
| Нет связи с origin | `OfflineScreen` целиком | Уже работает: `NetworkGate` + `/api/v1/health` |
| Origin жив, Supabase не ответил | **тост** | Экран на месте, ввод не теряется, видно, что дело не в человеке |
| Неверные креды, кривой email | ошибка под полем | Это ввод |
| Ошибка в нашем коде | 500 (`error.tsx`) | Пусть падает громко, а не прячется в тост |

Различать второе от третьего можно надёжно, а не угадыванием: Supabase
на неверный пароль отдаёт `AuthApiError` со `status: 400` и кодом
`invalid_credentials`, на недоступность — `AuthRetryableFetchError` либо
5xx. Серверные действия получают третий вариант состояния,
`{ status: "unavailable" }`, и решение, что показать, принимает UI.

Контракт действий **расширяется, а не переписывается**: `join-waitlist`
в v2 не трогаем, его перевод на `"unavailable"` — отдельная задача,
иначе объём v2 тихо растёт.

### D12. Свой тост, не `UNSTABLE_*` из react-aria

В `react-aria-components` 1.21.1 тост есть, но только как
`UNSTABLE_ToastQueue`/`UNSTABLE_ToastRegion`/`UNSTABLE_Toast`. Владелец
выбрал свою реализацию: предсказуемость при обновлении RAC важнее
готовой очереди, тем более что образец уже есть в проекте —
`features/network-status/ui/ConnectionRestoredToast.tsx` (роль `status`,
`aria-live="polite"`, анимации входа/выхода через `data-state` и
`tw-animate-css`, `fill-mode-both` против мигания при уходе,
`motion-reduce:animate-none`). Общий тост наследует эту вёрстку и
поведение.

Устройство:

- `shared/ui/toast.tsx` — вёрстка одного тоста и регион (`fixed`,
  `pointer-events-none`, безопасная зона сверху), плюс типы и настройки:
  вёрстка владеет контрактом.
- `shared/ui/toast-provider.tsx` — контекст, `ToastProvider`,
  `useToast()`, тип `ToastTone` (`"neutral" | "positive" | "negative"`),
  очередь в состоянии, таймер автозакрытия, страховочный таймер на
  случай, когда анимация выхода не наступает.

Оба файла — в `shared/ui`, а не в `shared/lib/toast`, как задумывалось
сначала: внутри `shared` направление импортов одностороннее
(`shared/ui` → `shared/lib/cn`, и ни один файл `shared/lib` не
импортирует `shared/ui`), а провайдер, рендерящий регион, создал бы
встречный импорт без прецедента. Очередь тостов — собственное состояние
элемента, а не бизнес-сценарий, поэтому граница `shared/ui` из ADR 0013
его допускает.
- Провайдер подключается в `app/layout/providers.tsx` внутри
  `NextIntlClientProvider` (тост берёт текст из словаря).

`ConnectionRestoredToast` **заменяется** общим компонентом, а не
остаётся рядом с ним: два тоста с одинаковой вёрсткой в одном
приложении разойдутся при первой же правке стиля. Его логика — образец,
из которого общий тост берёт поведение (`role="status"`,
`aria-live="polite"`, `data-state` + `tw-animate-css`,
`fill-mode-both` против мигания при уходе,
`motion-reduce:animate-none`, страховочный таймер на случай, когда
`animationend` не наступает).

**Но переносится не только вёрстка.** У `useReconnectFeedback`
(`features/network-status/model/`) есть два поведения, которых у простой
очереди нет:

1. **задержка перед показом** (`phase: "pending"`,
   `NETWORK_CONFIG.reconnectToastDelayMs`) — связь, которая вернулась и
   через секунду снова пропала, не должна давать тост вообще;
2. **досрочное снятие** — если связь пропала, пока тост висит, он
   убирается сразу, а не продолжает сообщать о восстановлении поверх
   офлайн-экрана.

Поэтому публичный API общего тоста — не только `showToast`: он
возвращает идентификатор, и рядом есть `dismissToast(id)`.

```ts
const { showToast, dismissToast } = useToast();
const id = showToast({ message, tone });
dismissToast(id); // снять досрочно
```

Решение «что показывать» остаётся в `network-status` (там живут и
`NETWORK_CONFIG`, и машина состояний связи), а «как показывать и сколько
держать» уезжает в общий тост. Файл `ui/ConnectionRestoredToast.tsx`
удаляется.

### D13. Сброс пароля — страница и действие, пишущее в лог

Отправки письма пока нет (resend подключим позже). `/forgot-password`:
заголовок, поле email, кнопка, ссылка назад на `/login`. Слайс
`features/request-password-reset` — схема, серверное действие, лимитер.

Действие пишет адрес в серверный лог. Три свойства заложены сразу,
потому что потом их легко забыть:

- **Ответ одинаковый, есть такой аккаунт или нет.** Иначе страница
  становится проверялкой «кто зарегистрирован», и это нельзя будет
  починить позже, не меняя поведение.
- **Лимитер обязателен** (`shared/lib/rate-limit`): это
  неаутентифицированная ручка, которая пишет в лог — без ограничения её
  заливают мусором.
- **Адрес в логе — временная мера**, ровно по образцу ADR 0027, где
  email вайтлиста тоже сначала писался открытым текстом. Разница в том,
  что здесь лог и есть рабочий механизм: владелец видит запрос и меняет
  пароль в Studio. Условие снятия — подключённая отправка писем; тогда
  лог сводится к факту без адреса, как уже сделано в вайтлисте.

### D14. Приветственный тост — одноразовый флаг в `sessionStorage`

Действие входа возвращает `display_name`; клиент кладёт его одноразовым
флагом в `sessionStorage` и переходит на `/day` клиентской навигацией;
`/day` показывает тост один раз и флаг гасит.

Через query-параметр — нельзя: он остаётся в адресной строке и повторяет
тост при перезагрузке. Чтение `sessionStorage` обёрнуто в `try/catch`:
в приватном режиме доступ к нему бросает, и из-за тоста приложение
падать не должно.

### D15. Supabase не добавляется в пробу `/api/v1/health`

Соблазн есть: тогда недоступность базы была бы видна сразу. Но
`NetworkGate` при неудачной пробе закрывает приложение целиком
офлайн-экраном — любой чих Supabase выключал бы всё приложение, включая
экраны, которым база не нужна. Недоступность бэкенда — свойство
конкретной операции, а не всего приложения, и показывается тостом по
месту.

### D16. Известное последствие: авария дольше часа выбрасывает на `/login`

`getClaims()` проверяет токен локально, поэтому при недоступном Supabase
уже вошедший человек продолжает работать. Но `jwt_expiry = 3600`, и
обновить токен без Supabase нельзя: если авария длится дольше часа,
человека уводит на `/login`, где войти он тоже не сможет.

Лечится только grace-периодом на истёкший токен, то есть ослаблением
проверки подлинности. В v2 этого не делаем — фиксируем в ADR, чтобы
свойство не выяснилось в проде как новость.

## Тесты

**pgTAP** (`backend/supabase/tests/`, `pnpm db:test`):

- триггер создаёт профиль и роль `user` при вставке в `auth.users`;
- `display_name` берётся из метаданных, а при их отсутствии — из
  локальной части email;
- `authenticated` читает только свой профиль и не видит чужой;
- у `authenticated` нет ни одного права на `user_roles`;
- `custom_access_token_hook` возвращает claims с `user_role`;
- `anon` и `authenticated` не могут выполнить хук.

**vitest** (`web/src`): разбор claims (валидные, без роли, с неизвестной
ролью), `hasRole` для обеих ролей, схема входа, схема сброса пароля.

**CI**: `db-test.yml` уже проверяет, что сгенерированные типы совпадают
со схемой, — каждая миграция требует `pnpm db:types` в том же коммите.

## Ручные шаги, которые миграции не делают

1. Включить `custom_access_token` hook в облачном дашборде
   (Authentication → Hooks).
2. Выключить регистрацию в облачном проекте (`enable_signup = false`
   локально + соответствующая настройка в дашборде).
3. Создать учётные записи в Studio; роль `admin` — правкой `user_roles`.
4. Подключить отправку писем, когда будем снимать лог из D13.
