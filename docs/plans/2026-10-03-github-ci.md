# План: GitHub Actions для ministry-app

> Это **план**, а не реализация. Ни одного файла в `.github/workflows/` он не создаёт: сейчас там только `.gitkeep`. Каждый workflow ниже появляется отдельным шагом (см. «Порядок внедрения»).

## Зачем

Сейчас ни одна проверка не выполняется автоматически. Vercel собирает проект на каждый push, поэтому ошибку типов видно на деплое, но `lint`, `test` и pgTAP не прогоняются нигде, кроме машины разработчика. При этом pgTAP — единственное, что сторожит модель доступа к данным (RLS без политик, отозванные гранты, `execute` только у `service_role`), и однажды он уже поймал ошибку до попадания в базу (ADR 0037, 0039). Ещё две задачи, которые сейчас делаются руками или не делаются вовсе: бесплатный проект Supabase встаёт на паузу после 7 дней неактивности, а автоматических бэкапов на бесплатном тарифе нет. И в `CLAUDE.md` прямо названо временное состояние: `db:push` и `functions:deploy` выполняются вручную, а как только появится CI, они должны переехать туда.

## Общие принципы для всех workflow

Взяты из официальной документации GitHub Actions.

- **Сторонние actions — по полному SHA коммита, не по тегу.** Привязка к полному SHA — единственный способ использовать action как неизменяемый релиз: тег можно переместить или удалить, если злоумышленник получит доступ к репозиторию action. Компрометация одного action в workflow даёт доступ ко **всем** секретам репозитория и, через `GITHUB_TOKEN`, возможность записи в репозиторий. Пиним по SHA `supabase/setup-cli` и любые подобные (`pnpm/action-setup`, если понадобится). Для `actions/*` допустим тег, но SHA лучше. При пиновании нужно убедиться, что SHA взят из репозитория самого action, а не из его форка; рядом в комментарии пишем человекочитаемую версию (`# v2.1.0`).
- **Минимальные права.** `permissions` задаётся явно — на уровне workflow и, где нужно, на уровне job. Для всех наших проверок достаточно `contents: read`. Без явного указания токен получает права по умолчанию, которые шире необходимого.
- **Группы параллелизма.** Для проверок на PR — `concurrency` с `cancel-in-progress: true`: новый push отменяет устаревший прогон и не жжёт минуты. Для деплоя — наоборот, `cancel-in-progress: false`: прерывать деплой посередине хуже, чем дать ему закончиться.
- **Расписания.** GitHub может задерживать `schedule` на 15+ минут при нагрузке и **отключает расписание после 60 дней без активности в репозитории**. Для keep-alive и бэкапа это терпимо, но знать надо.
- **Ничего из `github.event.*` в блоках `run:`** — это вектор инъекции. У нас таких данных нет и не будет; принцип фиксируем на будущее.

## 1. `ci.yml` — проверки на каждый PR и push

**Назначение.** Дешёвые проверки, которые ловят большую часть регрессий: линт (eslint + steiger), типы, unit-тесты (vitest, 72 теста).

**Триггеры.** `pull_request` и `push` в `develop` и `master`.

**Права и параллелизм.** `permissions: contents: read`; `concurrency` по `github.ref` с `cancel-in-progress: true`.

**Шаги.**

1. `actions/checkout`.
2. `corepack enable` — pnpm берётся из `package.json#packageManager` (12.4.1), версию в workflow не дублируем.
3. `actions/setup-node` с Node 24 и `cache: pnpm`.
4. `pnpm install --frozen-lockfile`.
5. `pnpm lint`.
6. `pnpm typecheck`.
7. `pnpm test`.

**Секреты и переменные.** Не нужны.

**Время.** Около минуты.

### Почему сборки здесь нет

`pnpm build` в нынешнем виде в CI не запустится. Скрипт — `dotenv -e envs/web.local.env -- pnpm --filter web run build`, а `envs/web.local.env` лежит в `.gitignore` и в репозитории его нет. Кроме того, `web/src/shared/config/env.ts` работает по принципу fail-fast: без обязательных переменных сборка падает. Vercel собирает проект на каждый push и ловит то же самое, поэтому пропуск осознанный. Возможные решения на будущее:

1. генерировать CI-файл окружения из GitHub Secrets;
2. переписать скрипт так, чтобы отсутствие файла не было фатальным;
3. оставить сборку за Vercel.

Выбор отложен; **по умолчанию — третий вариант.**

## 2. `db-test.yml` — pgTAP

**Назначение.** Прогон 45 проверок модели доступа к данным (`pnpm db:test`, то есть `supabase test db`).

**Триггеры.** Те же, что у `ci.yml` (`pull_request` и `push` в `develop` и `master`), но с фильтром по путям `backend/**`: схема меняется редко, а запуск небыстрый.

**Права.** `permissions: contents: read`; `concurrency` по `github.ref` с `cancel-in-progress: true`.

**Шаги.**

1. `actions/checkout`.
2. `supabase/setup-cli` (пин по SHA; версию CLI согласовать с `backend/package.json`, сейчас 2.117.0).
3. `supabase db start`.
4. `supabase test db`.

На `ubuntu-latest` Docker уже есть, отдельной установки не требуется.

**Секреты и переменные.** Не нужны — стек поднимается локально, в раннере.

**Время.** Несколько минут (поднятие локального стека Supabase).

### Почему отдельным workflow, а не job внутри `ci.yml`

Он в разы медленнее остальных проверок, и его незачем гонять на правках фронтенда. Отдельный файл с фильтром `backend/**` решает это без условной логики внутри job.

### Зачем он вообще

45 проверок модели доступа ловят ошибки вроде грантов, отозванных не у тех ролей. Такую ошибку он уже поймал один раз (см. ADR 0037/0039). Кроме того, он служит гейтом для `supabase-deploy.yml` (раздел 5).

## 3. `health-ping.yml` — держать бесплатный Supabase живым

**Назначение.** Бесплатный проект Supabase встаёт на паузу после 7 дней неактивности. Раз в 3 дня workflow выполняет настоящий запрос к базе.

### Ключевое отличие от соседнего проекта

Пинговать `/api/v1/health` бессмысленно, он до базы не доходит. `web/app/api/v1/health/route.ts` отдаёт 204 и намеренно не трогает ни Supabase, ни auth — это проба достижимости собственного origin для `features/network-status`. Edge Function `backend/supabase/functions/health` возвращает `{"status":"ok"}` из `Deno.serve` и тоже в базу не ходит. Значит ping по любому из них **не сбросит** таймер неактивности. В соседнем проекте пользователя этот приём работал потому, что там эндпоинт выполнял `select count(*)`. Поэтому здесь запрос идёт **напрямую в Supabase REST**, из самого workflow.

**Триггеры.** `schedule` с `cron: "27 6 */3 * *"` и обязательно `workflow_dispatch` рядом — чтобы можно было дёрнуть руками.

**Права.** `permissions: {}` (репозиторий не читается, checkout не нужен).

**Шаги.** Один шаг с `curl`:

```bash
set -euo pipefail
: "${SUPABASE_URL:?}" "${SUPABASE_SECRET_KEY:?}"
curl -fsS --head --max-time 15 \
  -H "apikey: ${SUPABASE_SECRET_KEY}" \
  -H "Authorization: Bearer ${SUPABASE_SECRET_KEY}" \
  "${SUPABASE_URL}/rest/v1/waitlist_signups?select=id&limit=1"
```

Значения приходят через `env:` шага из `secrets`/`vars`, не подставляются в `run:` выражениями.

- `set -euo pipefail` и явная проверка, что секреты непустые.
- `curl -fsS --max-time 15`: флаг `-f` роняет job на любом ответе 400+, то есть на истёкшем или отозванном ключе job честно упадёт.
- `timeout-minutes: 2` на job.

**Секреты и переменные.** `SUPABASE_URL` (можно переменной репозитория: это не тайна), `SUPABASE_SECRET_KEY` (секрет).

**Время.** Секунды, в счёте минут — одна.

### Почему так

- **HEAD, а не GET.** PostgREST запрос всё равно выполняет, но тела не возвращает — в логи CI не попадёт ни один адрес из вайтлиста.
- **Секретный ключ (`service_role`), а не публикуемый.** Таблицы закрыты для `anon` наглухо (RLS без политик плюс отозванные гранты); публикуемым ключом ни одного запроса к ним не сделать — это проверялось отдельно. У `service_role` грант `select` на `public.waitlist_signups` есть по миграции `20261002230000_grant_tables_to_service_role.sql`.
- **Не заводим отдельную RPC-функцию `ping`.** Это новая поверхность доступа ради служебной задачи. Существующие две функции (`join_waitlist`, `register_waitlist_push_subscription`) не годятся: у обеих есть побочные эффекты.
- **Расписание `27 6 */3 * *`.** Известная особенность, которую пользователь уже документировал у себя: `*/3` в поле дня месяца срабатывает 1, 4, 7, …, 31 числа, то есть интервал сбрасывается на границе месяца (31 января → 1 февраля = один день). Для таймера на 7 дней это безопасно: максимальный разрыв остаётся 3 дня. Смещённая минута (`:27`) уводит прогон от пиковой нагрузки на `:00`.

## 4. `supabase-backup.yml` — ежедневный бэкап

**Назначение.** На бесплатном тарифе Supabase автоматических бэкапов нет, поэтому делаем сами. Образец — workflow, который пользователь уже отладил в `sole-trader-discovery`.

**Обязательное условие: репозиторий приватный.** Дамп содержит персональные данные — адреса электронной почты из вайтлиста и push-подписки. Если репозиторий когда-либо станет публичным, этот workflow надо сначала выключить.

**Триггеры.** `schedule` с `cron: "17 9 * * *"` — раз в день, отдельный час от health-ping, чтобы два задания не попадали в один пул раннеров; плюс `workflow_dispatch`.

**Права.** `permissions: contents: read`.

**Шаги.**

1. Установить `postgresql-client` мажорной версии, совпадающей с сервером Supabase, и **добавить его bin в `$GITHUB_PATH`**: на `ubuntu-latest` предустановлен клиент постарше, а обёртка `/usr/bin/pg_dump` по умолчанию выбирает самый старый установленный мажор. Версию клиента надо сверить с версией сервера облачного проекта перед первым запуском (в соседнем проекте это 17; здесь проверить отдельно, не копировать число на веру).
2. Посчитать метку времени и записать её в `$GITHUB_OUTPUT`.
3. `pg_dump --no-owner --no-privileges --schema=public --format=custom` в файл.
4. Проверка здравости: если файл меньше порога (например 512 байт) — ронять job. Пустой дамп, который молча уехал в артефакты, хуже отсутствия бэкапа.
5. Выгрузить каждую таблицу схемы `public` в отдельный CSV для чтения глазами, обнаруживая таблицы через `pg_tables` (тогда новая таблица попадает в бэкап сама, без правки workflow). Проверять, что файл непустой: строка заголовка есть даже у пустой таблицы, поэтому пустой файл означает обрыв соединения.
6. `actions/upload-artifact` с `retention-days: 90` и `if-no-files-found: error`.

**Секреты.** `SUPABASE_DB_URL` — строка подключения к облачной базе.

**Время.** Минуты; на нынешнем объёме данных — секунды.

### Честное ограничение

Артефакты GitHub живут максимум 90 дней, и это не настоящее внешнее хранилище. Для предзапускового масштаба достаточно, но это не замена полноценным бэкапам, если данных станет много или они станут важнее.

## 5. `supabase-deploy.yml` — деплой в прод, ТОЛЬКО руками

Это ответ на вопрос «можно ли пайплайн, который деплоит функции и миграции в прод Supabase, но запускается мной руками, а не по сливу в master». Да, и так даже правильнее: запись в прод остаётся осознанным действием человека, но выполняется воспроизводимо, из чистого окружения, с гейтом по тестам.

**Триггер.** **Только** `workflow_dispatch`. Никакого `push`. Запуск — кнопка Run workflow в интерфейсе GitHub или `gh workflow run`.

**`inputs`.**

- `target` (`type: choice`): `migrations`, `functions` или `both`.
- `confirm` (`type: boolean`): чекбокс-подтверждение, чтобы случайный запуск не прошёл. Шаги деплоя выполняются только при `confirm == true`.

**`environment: production`.** Даёт две вещи: во-первых, секреты можно держать на уровне environment, а не репозитория; во-вторых, в настройках environment включается **required reviewer**, и тогда запуск ждёт явного подтверждения в интерфейсе, даже если нажал его сам владелец. Рекомендуется включить.

**Параллелизм.** `concurrency` с `cancel-in-progress: false`: прерванный посередине `db push` хуже доведённого до конца.

**Права.** `permissions: contents: read`.

**Job'ы и шаги.**

1. Job `db-test` — тот же прогон pgTAP, что в `db-test.yml` (checkout → `supabase/setup-cli` → `supabase db start` → `supabase test db`). Вынести общее в reusable workflow (`workflow_call`) или продублировать — решить при реализации; дублирование допустимо, пока это четыре шага.
2. Job `deploy` с `needs: db-test` и `environment: production`:
   1. `actions/checkout`;
   2. `supabase/setup-cli` (пин по SHA);
   3. `supabase link --project-ref "$SUPABASE_PROJECT_REF"`;
   4. при `target` = `migrations` или `both` — `supabase db push`;
   5. при `target` = `functions` или `both` — `supabase functions deploy`.

**Гейт.** Деплой зависит от job с pgTAP. Автоматический пуш миграций в живую базу без прогона тестов схемы опаснее ручного запуска с машины, который хотя бы делает человек, видящий, что он делает.

**Секреты** (на уровне environment `production`). `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`.

> **Предупреждение из `CLAUDE.md`.** `supabase db reset --linked` (и вообще любой `db reset` на удалённом проекте) **уничтожает данные в облачной базе**. Этой команды в workflow быть не должно ни в каком виде — ни в шаге, ни в закомментированном блоке, ни как значение `inputs`.

Этот workflow закрывает временное состояние, прямо названное в `CLAUDE.md`: «как только появится CI, пуш миграций и деплой функций в прод должны переехать туда, а ручной запуск остаться только для экстренных случаев». После внедрения раздел «Деплой миграций в облачный Supabase» в `CLAUDE.md` нужно обновить (и зафиксировать решение в ADR, как требует правило проекта).

**Время.** pgTAP-гейт плюс несколько десятков секунд на `link`/`push`/`deploy`.

## Расход минут

Репозиторий приватный, поэтому минуты Actions расходуются из квоты (на тарифе Free — 2000 минут в месяц); на публичном репозитории они бесплатны. Порядок величин:

- `health-ping.yml` — около 10 прогонов в месяц по минуте: около 10 минут;
- `supabase-backup.yml` — около 30 прогонов по 1–3 минуты: 30–90 минут;
- `ci.yml` — по числу push'ей и PR, около минуты на прогон;
- `db-test.yml` — реже (только правки `backend/**`), но дольше, несколько минут на прогон.

Вывод: в 2000 минут тарифа Free это укладывается с большим запасом, но знать об этом надо. Отмена устаревших прогонов (`cancel-in-progress: true`) экономит минуты на частых push'ах.

## Порядок внедрения

1. **`ci.yml`** — первым: он дешёвый, не требует секретов и закрывает большую часть регрессий.
2. **`health-ping.yml` и `supabase-backup.yml`** — следом: они ни от чего не зависят и приносят пользу сразу (проект не уснёт, данные не потеряются). Перед первым запуском бэкапа сверить мажорную версию Postgres облачного проекта.
3. **`db-test.yml`** — третьим: он сам по себе полезен и нужен как гейт для следующего шага.
4. **`supabase-deploy.yml`** — последним, потому что он единственный пишет в прод. К этому моменту уже есть проверенный pgTAP-гейт; перед первым запуском настроить environment `production` с required reviewer.

## Спецификации

На каждый workflow после его появления создаётся формальная спецификация по скиллу `create-github-action-workflow-specification` в `docs/spec/spec-process-cicd-<имя>.md`. Скилл предлагает путь `/spec/` в корне репозитория, но в этом проекте вся документация живёт в `docs/`, поэтому берётся `docs/spec/` — отступление сознательное, ради единообразия.

## Чего в плане намеренно нет

- **Деплоя фронтенда** — его делает Vercel на каждый push.
- **Порогов покрытия тестами** — пока нет договорённости, что считать достаточным; пороги без неё только мешают.
- **Релизной автоматизации** — релизов в привычном смысле нет, приложение разворачивается на Vercel.
- **Матрицы версий Node** — версия одна и закреплена (Node 24).
