>
> Что здесь было не так — не то, что секрет не работал: он работал. Он
> решал проблему, которой при правильном прочтении рекомендаций Supabase
> не должно было существовать. Рекомендация такая: секретный ключ
> запрещён в **публичных клиентах / фронтенд-коде**, а серверное действие
> Next.js — не то и не другое, это доверенный сервер. Запрет ADR 0006 был
> про браузер, а не про сервер: он писался, когда у `web` вообще не было
> серверного пути записи. Вариант A ниже («`service_role`-ключ на
> сервере») был отвергнут по ошибочному прочтению этого запрета. Правильный
> дизайн — вызывать функции секретным ключом с доверенного сервера и
> отозвать `execute` у `anon`; общий секрет, `private`-схема и
> `set_rpc_secret` оказались лишним механизмом. Остальная часть файла
> оставлена как запись того, что было опробовано.

# ADR 0035: общий секрет для публичных RPC-функций вайтлиста

## Контекст

ADR 0033 сделал `public.join_waitlist` единственной дверью в закрытую
таблицу, а ADR 0034/миграции пуш-подписок добавили вторую такую дверь —
`public.register_waitlist_push_subscription`. Обе функции — `security
definer` с `execute` для `anon`.

URL Supabase и publishable-ключ по определению попадают в браузерный
бандл (`NEXT_PUBLIC_*`). Значит любой может вызвать обе функции напрямую
через PostgREST, минуя серверное действие Next.js — а вместе с ним и
rate limiter, который должен их защищать.

**Обход воспроизведён** на локальной базе: пять запросов
`POST /rest/v1/rpc/join_waitlist` с одним только publishable-ключом
вставили пять строк и выдали пять пуш-токенов примерно за секунду.
Лимитер уровня приложения при этом не участвовал вообще.

Security advisor Supabase отметил обе функции и обе таблицы. Два
предупреждения «RLS enabled, no policy» — **ложные срабатывания для
этого дизайна**: включённый RLS без политик и отозванные grants — это и
есть то, что закрывает таблицы (ADR 0033). Добавление политики их бы
открыло, поэтому «исправлять» эти предупреждения нельзя.

## Варианты

### A. `service_role`-ключ на сервере

Сервер вызывает функции секретным ключом, `execute` у `anon` отзывается.
Закрывает обход полностью, но прямо запрещено ADR 0006 и правилом
корневого `CLAUDE.md`, а главное — радиус поражения: утёкший
`service_role`-ключ даёт полный доступ ко всей базе в обход RLS.

### B. Общий секрет, проверяемый внутри функций — выбрано

Секрет знает только сервер Next.js; обе функции первым действием
сверяют его и отказывают при несовпадении. Утёкший секрет позволяет
вызвать две функции, не больше. ADR 0006 остаётся в силе.

## Решение

Миграция (файл больше не существует: вместе с миграцией ADR 0037 она
склеена в `20261002200000_trusted_server_only_rpc.sql`, где общего
секрета уже нет — см. ADR 0037, последний пункт «Последствий»):

- Схема `private`, недоступная PostgREST вообще (`config.toml` отдаёт
  только `public` и `graphql_public`); у `anon`/`authenticated` схема
  отозвана. Это сильнее, чем ещё одна закрытая таблица в `public`:
  выдавать нечего, ошибиться в grants негде, и advisor её не
  показывает.
- Таблица `private.rpc_secrets (name, value, updated_at)`: RLS включён,
  политик нет, grants отозваны. **Значение не засеивается** — настоящий
  секрет задаётся для каждого окружения отдельно и не коммитится.
- `private.rpc_secret_matches(text)` — `security definer`, единственное
  место сравнения. Без строки в таблице возвращает `false`:
  неподнастроенное окружение **закрыто по умолчанию**, а не открыто.
- Обе публичные функции получили первым параметром `p_secret text`
  (`join_waitlist(p_secret, p_email)`,
  `register_waitlist_push_subscription(p_secret, p_token, p_endpoint,
  p_p256dh, p_auth)`); старые сигнатуры удалены. Проверка стоит до
  всего остального; остальное тело функций не менялось. При несовпадении
  — `raise exception 'forbidden' using errcode = '42501'`
  (`insufficient_privilege`). Собственный errcode не вводился — ADR 0033
  объясняет, почему `40001` отправил бы PostgREST в бесконечный ретрай.
  Для регистрации подписки исключение, а не `false`: неверный секрет —
  это не «регистрация не удалась», а «вы не должны это вызывать».
  PostgREST отвечает на `42501` кодом 401 для `anon` (403 — для
  аутентифицированных ролей); важен код ошибки, не число.
- `public.set_rpc_secret(p_value)` — `security definer`, `execute`
  **только** у `service_role` (требует ≥ 32 символов). Через неё скрипт
  `backend/scripts/set-rpc-secret.mjs` (`pnpm db:set-secret`) записывает
  секрет: `private` PostgREST не виден, поэтому `supabase.from(...)`
  не подходит. Выбрано вместо `psql`: работает одинаково для локальной и
  облачной базы по тем же `SUPABASE_URL`/`SUPABASE_SECRET_KEY`, что уже
  использует скрипт рассылки, и не требует строки подключения к Postgres.
- Веб: `RPC_SHARED_SECRET` — серверный ключ в `env.ts`
  (`z.string().min(32)`, никогда не `NEXT_PUBLIC_*`); передаётся как
  `p_secret` в `persistWaitlistSignup` и `registerPushSubscription`.

Значение генерируется `openssl rand -base64 48` и должно быть одинаковым
в окружении приложения и в базе.

## Последствия

- Прямой вызов с одним publishable-ключом, без секрета или с неверным,
  отказывает с `42501`; строки не создаются.
- Секрет — предъявительский (bearer): он не идентифицирует вызывающего, и
  любой, кто читает окружение сервера, его имеет. Это делает rate limiter
  настоящим, но не делает endpoint аутентифицированным.
- Локальную базу нужно один раз настроить (`pnpm db:set-secret`), иначе
  каждый вызов вернёт отказ; после `pnpm db:reset` — повторить. То же для
  каждого облачного окружения после `db:push`. Окружение без секрета
  отказывает всем — так задумано.
- Предупреждения advisor «RLS enabled, no policy» не исправлять (см.
  Контекст).
- Смена секрета: новое значение в окружение приложения и
  `pnpm db:set-secret`; между этими шагами вызовы отказывают.
