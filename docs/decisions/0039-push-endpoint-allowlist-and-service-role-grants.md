# ADR 0039: белый список хостов push-сервисов и явные права `service_role`

## Контекст

Аудит нашёл два дефекта, не связанных между собой кодом, но одного рода:
оба держались на неявном допущении, а не на решении проекта.

### 1. Сервер ходит по любому адресу, который ему назовут

`web/src/features/push-notifications/model/schema.ts` проверял endpoint
подписки только как `z.url().max(4096)`, а в базе стоит лишь
`endpoint like 'https://%'`. Server Action
`register-push-subscription-action.ts` затем вызывает
`webpush.sendNotification(subscription, …)`, то есть сервер делает
HTTPS POST на тот хост, который указан в endpoint.

Токен регистрации (enrolment token) получает любой: достаточно записаться в
вайтлист новым адресом. Значит, любой человек мог заставить сервер
обратиться к произвольному хосту. Ответ к нему не возвращается, так что
примитив «слепой», но это всё равно исходящий запрос сервера по чужому
указанию.

Заодно: `webpush.sendNotification` вызывался без тайм-аута, и медленный
push-сервис держал Server Action открытым до тех пор, пока платформа его
не убьёт.

### 2. `service_role` имел доступ к таблицам только по умолчанию платформы

Ни одна миграция не содержит `grant … on table …`. `service_role` достигал
`public.waitlist_signups` и `public.push_subscriptions` только через
default privileges Supabase (`pg_default_acl`). Обе RPC-функции теперь
`security invoker` (ADR 0037), то есть выполняются с правами вызывающего, и
напрямую зависят от этого умолчания; так же скрипт рассылки. Supabase
движется к тому, чтобы отключить автоматические гранты и сделать открытие
таблиц явным; в проекте с таким умолчанием и функции, и скрипт запуска
упали бы с `42501`. Сегодня всё работало по наследству, а не потому, что
проект это заказал.

## Варианты

Для проверки endpoint:

1. **`check`-ограничение в базе со списком хостов.** Отвергнуто. Исходящий
   запрос делает процесс Node, и ограничение в базе не может его
   предотвратить. Кроме того, список хостов в `check` потребовал бы
   миграцию каждый раз, когда вендор браузера добавляет хост, и начал бы
   отвергать совершенно валидные подписки.
2. **Ничего не менять, полагаться на сетевые ограничения платформы.**
   Отвергнуто: у проекта нет такого контроля, и это то же неявное
   допущение.
3. **Белый список в прикладном слое.** Выбрано.

Для прав: оставить как есть (отвергнуто, см. контекст) или выдать явно.

## Решение

### Белый список хостов

`web/src/features/push-notifications/model/push-service-hosts.ts`:
множество точных хостов (`web.push.apple.com`, `fcm.googleapis.com`,
`android.googleapis.com` для старого FCM, `updates.push.services.mozilla.com`)
и два домена с региональными поддоменами (`notify.windows.com`,
`push.services.mozilla.com`). Предикат `isPushServiceEndpoint` разбирает
URL и возвращает `true` только для протокола `https:` и хоста из списка;
поддомены сопоставляются по границе точки, поэтому `evilnotify.windows.com`
отвергается (наивный `endsWith` его бы пропустил). Нераспознаваемая строка
даёт `false`, а не исключение. Предикат подключён в `schema.ts` через
`.refine()` после существующих проверок. Тесты лежат рядом
(`push-service-hosts.test.ts`, ADR 0021).

Существующее ограничение `endpoint like 'https://%'` в базе оставлено
как есть: это проверка здравого смысла, а не шлагбаум.

Новое пользовательское сообщение и ключ словаря **не добавлялись**: настоящий
браузер не производит endpoint вне списка, так что это не ошибка, которую
человек может исправить. Подходит существующий путь отказа
(`{ status: "error" }`).

В вызов `webpush.sendNotification` добавлен `timeout: 5000`. Подтверждение
best-effort и не должно держать ответ открытым.

### Явные права

Миграция `20261002230000_grant_tables_to_service_role.sql` выдаёт
`select, insert, update, delete` на обе таблицы роли `service_role`. Гранты
идемпотентны, на базе, где они уже есть, миграция безвредна. `anon` и
`authenticated` в ней намеренно не упомянуты: их права отозваны сознательно.
pgTAP-набор `waitlist_signups_test.sql` теперь проверяет это свойство, а не
предполагает: `service_role` имеет все четыре права на обе таблицы, а
`anon` и `authenticated` не имеют ни одного (план вырос с 33 до 45 проверок).

## Последствия

- Сервер обращается только к известным push-сервисам. Это граница того,
  куда он пойдёт, а не аутентификация: список ничего не доказывает о
  человеке, который подписывается, и токен по-прежнему выдаётся любому.
- Если вендор добавит новый хост push-сервиса, подписки из этих браузеров
  перестанут проходить, пока список не обновят. **Единственное место
  изменения — `push-service-hosts.ts`.**
- Подтверждающее уведомление теперь ограничено 5 секундами; запоздавший
  ответ push-сервиса не удерживает Server Action.
- Права `service_role` стали собственным свойством проекта и не зависят от
  изменения умолчаний платформы.
