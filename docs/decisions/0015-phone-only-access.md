# ADR 0015: Доступ только с телефона, только установленным приложением

> ⚠️ **Заменено ADR `0016-v1-ios-safari-only-access.md`.** v1 сузила
> требование до «только iPhone в Safari» (десктоп/планшет/iPad/Android/
> iPhone-не-Safari теперь блокирует сервер, `web/proxy.ts`, а не CSS) и
> добавила Coming soon вместо реального `/day`. Документ ниже оставлен
> как история решений по CSS-щиту и PWA-механике (`display-mode`,
> `beforeinstallprompt` и т.д.) — часть из них (принцип «CSS не мигает»,
> ограничения `display-mode` на iOS) унаследована ADR 0016, часть
> (три равноправных CSS-состояния, Android через `beforeinstallprompt`)
> в v1 больше не действует. Не удалено, чтобы не терять обоснования.

## Контекст

Приложение — личный учёт часов служения, рассчитан на один сценарий:
открыть на своём телефоне, отметить день, закрыть. На планшете и
десктопе у него нет пользы (не адаптирован под широкий экран, курсор,
клавиатурную навигацию) и есть риск — случайный/чужой заход с чужого
устройства не должен показывать данные пользователя как обычный экран
приложения. Дополнительное требование (добавлено по ходу работы, после
первой версии этого ADR): даже на телефоне приложение должно открываться
**только установленным как PWA** (запуск со значка на главном экране) —
обычный браузер на телефоне должен подталкивать к установке, не сразу
открывать приложение.

Итоговых состояния три:

| Где открыто | Что показываем |
|---|---|
| Десктоп, ноутбук, планшет (включая iPad) | «Откройте на телефоне» (`DesktopBlockScreen`) |
| Телефон, обычный браузер | «Установите приложение» + инструкция (`InstallAppScreen`) |
| Телефон, установленное PWA (standalone) | само приложение |

`DEV_MODE=true` по-прежнему отключает всё это целиком (см. ниже).
Исключение для `/styleguide` и `/components` — тоже.

## Решение: три независимых слоя

### 1. CSS-щит — основной механизм

`web/src/app/styles/globals.css`, три класса: `.app-shell` (само
приложение), `.install-shield` (`InstallAppScreen` — телефон, не
standalone), `.phone-shield` (`DesktopBlockScreen` — не телефон). Все три
дерева рендерит `root-layout.tsx` **всегда** — какое показать, решает
чистый CSS через `@media`, без JavaScript:

```css
.app-shell { display: none; }
.install-shield { display: none; }
/* .phone-shield виден по умолчанию (сама CenteredState уже ставит
   display:flex) — это фолбэк на случай, если ни одно из условий ниже
   не совпало. */

@media (pointer: coarse) and (hover: none) and (orientation: portrait) and (max-width: 599px),
  (pointer: coarse) and (hover: none) and (orientation: landscape) and (max-height: 599px) {
  .phone-shield { display: none; }
  .install-shield { display: contents; }
}

@media (pointer: coarse) and (hover: none) and (orientation: portrait) and (max-width: 599px) and (display-mode: standalone),
  (pointer: coarse) and (hover: none) and (orientation: portrait) and (max-width: 599px) and (display-mode: fullscreen),
  (pointer: coarse) and (hover: none) and (orientation: landscape) and (max-height: 599px) and (display-mode: standalone),
  (pointer: coarse) and (hover: none) and (orientation: landscape) and (max-height: 599px) and (display-mode: fullscreen) {
  .app-shell { display: contents; }
  .install-shield { display: none; }
}
```

Правило работает как две последовательные, всё более узкие проверки:
сначала «это телефон?» (переключает `phone-shield` → `install-shield`),
затем, только внутри этого условия, «телефон И standalone?» (переключает
`install-shield` → `app-shell`). Второе условие физически не может
сработать без первого (оно само содержит все условия первого плюс
`display-mode`), поэтому «стать приложением» на десктопе, даже если тот
почему-то сообщит `display-mode: standalone` (Chrome умеет ставить
десктопные PWA), невозможно — там первое условие (`pointer: coarse` и
т.д.) не выполняется в принципе.

**Почему CSS, а не JS-редирект или проверка в React**: media-фичи
резолвятся браузером синхронно, до первого paint — переключение
происходит без мигания одного экрана поверх другого и без ожидания
гидратации. Любой JS-подход (проверка в `useEffect`, `middleware`-
редирект по `User-Agent`) либо покажет на долю секунды не тот экран,
либо потребует блокирующий рендер на сервере.

**Почему не `@layer`**: правила щита объявлены вне `@layer`
(неслоёный CSS в каскаде весомее любого `@layer`, включая слои Tailwind
`theme/base/components/utilities`) — это даёт им побеждать над
`display: flex` из утилиты `flex`, которую `CenteredState` уже ставит на
том же элементе, без `!important`.

### `display-mode: standalone` — надёжность по платформам

По MDN, `display-mode` — Baseline-фича (широко доступна с января 2020),
но **у iOS Safari исторически бывают нестыковки**: домашний экран не
всегда отражается в `display-mode` корректно на старых версиях (в
отличие от Android Chrome, где `display-mode: standalone` — надёжный,
основной сигнал). Из-за этого:

- сам CSS-щит **полагается только на `display-mode`** — альтернативы для
  чистого CSS нет, а исключение iOS Safari из standalone-ветки означало
  бы, что честные пользователи с установленным приложением на iPhone
  старых версий иногда видели бы экран установки вместо самого
  приложения — компромисс того же рода, что и c foldables (см. ниже);
- JS-хелперы (`isStandalone()`/`useIsStandalone()`,
  `shared/lib/device/is-standalone.ts`), которым нужен точный ответ,
  **дополнительно** проверяют устаревшее нестандартное свойство
  `navigator.standalone` (только в Safari) — `matches || navigator
  .standalone === true`. Эти хелперы не участвуют в самом щите (у него
  нет доступа к JS до первого paint), они для остального клиентского
  кода.
- добавлен `display-mode: fullscreen` — на случай, если манифест
  когда-нибудь сменит `display` c `standalone` на `fullscreen`, щиту не
  придётся об этом узнавать отдельно.

### Порог: короткая сторона экрана ≤ 599px

Три условия одновременно: `pointer: coarse` (грубый указатель — палец, не
мышь), `hover: none` (нет наведения) и короткая сторона вьюпорта до
599px включительно, в любой ориентации:
`(orientation: portrait) and (max-width: 599px)` или
`(orientation: landscape) and (max-height: 599px)`.

Почему 599, а не 767 (частый брейкпоинт «планшет») или круглые 600:
крупнейшие iPhone (Pro Max, действующие и ближайшие следующие поколения)
не превышают ~430px по CSS-ширине портрета — 599 даёт запас, но
**iPad mini** (744px по короткой стороне) и любой iPad/Android-планшет
крупнее уже отсекаются. Число не идеальная физическая граница «это
телефон» — это практическая граница «айфоны точно проходят, iPad mini и
крупнее — точно нет», подобранная под актуальную линейку устройств.
Вынесено в константу с комментарием
(`web/src/shared/lib/device/constants.ts`, `PHONE_MAX_SHORT_SIDE`), чтобы
менять было легко — **но CSS-медиафичи не читают `var()`/JS-константы**,
поэтому число `599` продублировано вручную в `globals.css` и в
константе; оба места дают друг на друга перекрёстную ссылку в
комментариях. Более надёжного способа (например, PostCSS
`@custom-media`) в проекте сейчас нет — это осознанный, задокументированный
компромисс, не забытая рассинхронизация.

### Почему это НЕ защита

Щит отсекает случайные и добросовестные заходы не с телефона — не
злонамеренные. Любой может подделать `pointer`/`hover`/размер вьюпорта в
DevTools за один клик («Toggle device toolbar»), поэтому щит **не
заменяет авторизацию** и не может рассматриваться как контроль доступа к
данным — это разграничение UX, а не security-периметр.

### Складные телефоны (foldables)

Раскрытый Samsung Galaxy Fold (и похожие) имеют короткую сторону
экрана шире 599px — попадут под заглушку `DesktopBlockScreen`
(«Откройте на телефоне»), хотя формально это телефон. Осознанный
компромисс: без более точного сигнала (foldable — не то же самое, что
«большой экран», сегодняшние CSS-медиафичи не различают их надёжно)
сужать порог до значений, где Fold проходит, означало бы пропускать
реальные планшеты. `DesktopBlockScreen` в этом случае просто ошибается —
у него нет действия, которое могло бы это компенсировать (см. ниже,
почему у него теперь нет ни кнопки, ни инструкции).

### 2. Хелпер `web/src/shared/lib/device/`

Для кода, которому нужно знать тип устройства программно (а не только
визуально скрыть/показать блок через CSS-классы):

- `isPhone()` / `useIsPhone()` (`is-phone.ts`) — комбинация `matchMedia`
  (`pointer: coarse`, `hover: none`, короткая сторона) и
  `navigator.maxTouchPoints > 0`. `isPhone()` — чистая функция (SSR-safe:
  `false`, если `window` недоступен), `useIsPhone()` — хук поверх неё,
  подписан на `matchMedia().addEventListener("change")` (поворот экрана,
  resize окна). Начальное состояние хука — `false` и на сервере, и при
  первом клиентском рендере, уточняется в эффекте после маунта — без
  расхождений при гидратации.
- `usePhoneOs()` (`os.ts`) — только для выбора текста инструкции по
  установке (`ios | android | other`), не участвует в самом щите.
  **iPad (и любой браузер, представляющийся Macintosh) — НЕ `ios`**:
  iPadOS с версии 13 (2019) маскируется под macOS в `User-Agent` по
  умолчанию (`Safari` на iPad отправляет `Macintosh; Intel Mac OS X…`),
  так что различить честного пользователя Mac и iPad по UA-строке
  ненадёжно — сознательно не пытаемся, попадание iPad в `other`
  (нейтральный текст инструкции) — ожидаемое поведение, а не баг.
  Android-планшет отсекается токеном `Mobile` в UA (у планшетов его нет).
- Никаких regex-простыней по `User-Agent` ради определения «это
  телефон» — `User-Agent` используется только точечно, внутри
  `usePhoneOs()`, для выбора текста инструкции, не для решения
  «показывать приложение или нет».
- `isStandalone()` / `useIsStandalone()` (`is-standalone.ts`) — см. раздел
  про `display-mode` выше.
- `useInstallPrompt()` (`use-install-prompt.ts`) — ловит и сохраняет
  Chromium-событие `beforeinstallprompt` (нужно показать системную кнопку
  «Установить», см. ниже), слушает `appinstalled`. Чисто клиентский:
  `"use client"`, ничего не рендерит и не трогает серверный рендер —
  событие `beforeinstallprompt` не описано в `lib.dom.d.ts`, поэтому
  `WindowEventMap` аугментирован через `declare global` (тот же приём,
  что уже применялся для service worker в `src/app/sw.ts`).

### 3. Серверная пометка — `web/proxy.ts`

Next.js 16 переименовал `middleware.ts` → `proxy.ts` (экспорт `proxy`,
конфиг — `config`, не `middleware`/`proxyConfig`). Через `userAgent()`
из `next/server` вычисляется `device.type` и прокидывается дальше
заголовком `x-device-type` — **без жёсткого редиректа**. Причина та же,
что и для `usePhoneOs()`: iPad присылает `device.type` как `undefined`
(резолвится в `desktop`) чаще, чем как `tablet` — гейтить доступ по
этому значению означало бы иногда блокировать честных пользователей и
иногда пропускать то, что должно быть заблокировано. Заголовок сейчас
информационный, зарезервирован под будущий выбор первого экрана на
сервере (например, чтобы не отправлять клиенту разметку приложения,
которую CSS-щит всё равно скроет).

**Матчер `proxy.ts` не сузили до конкретных маршрутов** — исключены
только статика/`_next/image`/сервис-воркер/иконки, сама функция лёгкая
(один вызов `userAgent()`, без сетевых запросов), заметного эффекта на
статическую генерацию не дала (см. ниже).

## Почему щит НЕ реализован через `headers()`/`cookies()` в `root-layout.tsx`

Первый вариант: `proxy.ts` ставит заголовок с признаком «служебный
маршрут» (`/styleguide`, `/components`), `root-layout.tsx` читает его
через `headers()` (`next/headers`) и добавляет атрибут на `<html>`.
Отклонён: `headers()`/`cookies()` — динамические API, их вызов **в любом
месте** дерева layout, общего для всех маршрутов, помечает **все**
страницы приложения как динамические (`ƒ`, не `○`) — эффект от одной
проверки, нужной только двум внутренним страницам, распространился бы
на весь сайт, теряя статическую генерацию там, где она сейчас есть.

Решение вместо этого — структурный маркер в самом дереве компонентов:
`PhoneShieldBypass` (`shared/ui/phone-shield-bypass.tsx`) — невидимый
`<div data-phone-shield-bypass>`, который рендерят `StyleguidePage` и
`ComponentsPage`. Щит реагирует на него через `:has()`:

```css
body:has([data-phone-shield-bypass]) .app-shell { display: contents; }
body:has([data-phone-shield-bypass]) .phone-shield { display: none; }
```

`:has()` матчит по наличию узла в DOM независимо от его `display`
(включая случай, когда сам маркер лежит внутри `.app-shell`, а тот в
этот момент скрыт `display: none`) — работает без единой строчки JS и не
требует динамического рендера. Проверено сборкой: `pnpm build` (см.
живую проверку ниже) — `/styleguide` и `/components` остаются
статическими (`○`), как и раньше.

`:has()` — Baseline-фича (Safari 15.4+/Chrome 105+/Firefox 121+); на
более старых браузерах обход просто не сработает и щит на служебных
страницах будет виден и на десктопе — известное, некритичное
ограничение для внутреннего инструмента разработки.

## DEV_MODE — отключение щита для разработки

Дополнительное требование, добавленное по ходу работы: у щита должен
быть флаг полного отключения для разработки на любом устройстве,
включая десктоп/планшет.

- **Переменная** `DEV_MODE` (`envs/*.local.env`, схема —
  `web/src/shared/config/env.ts`), булева, по умолчанию `false`
  (переменная не задана → щит активен). Разбор строки в boolean —
  `z.stringbool()` (zod 4): принимает `"true"/"false"` (и синонимы
  `"1"/"0"`, `"yes"/"no"` и т.п.) без ручного `z.enum([...]).transform(...)`.
- **Server-only, без `NEXT_PUBLIC_`**: значение не должно попасть в
  клиентский бандл (проверяемое условие доступа не должно быть видно
  и подделываемо прямо в исходниках страницы). Клиентскому коду
  (`isPhone()`/`useIsPhone()`) флаг не нужен отдельным каналом — он уже
  передаётся тем же способом, что и самому CSS-щиту (см. ниже), поэтому
  `NEXT_PUBLIC_`-версия не понадобилась.
- **Где читается**: `root-layout.tsx` (серверный компонент) читает
  `env.DEV_MODE` и ставит атрибут `data-device-gate="off"` на `<html>`
  (`"on"` — по умолчанию). Это **не** динамический API (`headers()`/
  `cookies()`) — обычное чтение `process.env` через `@t3-oss/env-nextjs`,
  не переводит страницы в динамический рендер (см. сборку ниже — все
  маршруты остались `○`).
- **Единый источник и для CSS, и для JS**: тот же атрибут читает и CSS
  (`html[data-device-gate="off"] .app-shell { display: contents; }` и
  т.д. в `globals.css`), и `isPhone()` на клиенте
  (`document.documentElement.getAttribute("data-device-gate") === "off"`).
  Альтернатива — React-контекст, пробрасывающий флаг от `Providers` до
  хука, — отклонена как лишний слой: DOM-атрибут на `<html>` уже
  единственный канал, который одинаково доступен и чистому CSS (без
  JS), и любому клиентскому коду без пропсов/контекста.
- **Безопасность.** `DEV_MODE=true` в проде открывает приложение
  **всем** устройствам — щит перестаёт что-либо отсекать. Эта
  переменная — **только инструмент локальной разработки**; на Vercel её
  **нельзя** задавать в Production-окружении (Preview/Development —
  на усмотрение команды). Дополнительная защита: `env.ts` логирует
  `console.warn` при старте сервера, если одновременно `DEV_MODE=true` и
  `NODE_ENV=production`.

## Исключение: `/styleguide` и `/components`

Обе страницы — рабочие инструменты разработки (сверка токенов с
прототипом, живой каталог компонентов), их специально смотрят с
компьютера, не с телефона. Реализация — `PhoneShieldBypass`, см. раздел
про `:has()` выше. Другие внутренние маршруты, если появятся, включаются
тем же способом — один компонент, без правки CSS.

## Экран-заглушка `DesktopBlockScreen` (не телефон)

`web/src/pages/desktop-block/` — назван по имени экрана из ADR 0012 и
словаря (`showcase.components.matrix.screens.desktopBlock` = «Desktop
block»), а не «desktop-only»/«unsupported-device» и т.п., чтобы не
заводить второе имя для уже существующего в дизайн-системе понятия.

Собран из существующих `shared/ui` (не копирует разметку `only-mob.html`
— см. правило проекта «экраны собираются из компонентов»): `CenteredState`
(каркас), `AppMark` (знак, 88px elevated — как на Coming soon/О
приложении), `TextBlock` (эйбрау + заголовок `size="compact"` 30px, как в
ADR 0012 «Title M, Desktop block» + текст).

**Без кнопки и инструкции по установке** — они переехали на
`InstallAppScreen` (см. ниже), потому что с десктопа устанавливать
приложение всё равно нельзя (там нет самого приложения — только заглушка
про телефон), инструкция там была бы бесполезна. Текст экрана поэтому
тоже сменился с «Установите приложение на телефон» на «Откройте на
телефоне» — точнее описывает, что можно сделать именно с этого
устройства. Матрица использования (`usage-matrix-data.ts`) отражает это:
`Button`/`ActionStack` для `desktopBlock` — снова `0` (были кратко `1`,
пока кнопка ещё жила здесь, до появления install-app в этой же задаче).

Доступность: `CenteredState` рендерит единственный `<main>` на экран;
`TextBlock` даёт `h1` (заголовок `Title` по умолчанию — `as="h1"`).

## Экран `InstallAppScreen` (телефон, обычный браузер)

`web/src/pages/install-app/` — новый экран, не описан во внешнем
каталоге компонентов (ADR 0012 перечислял только шесть экранов), поэтому
отдельной колонки в `usage-matrix-data.ts` для него не заводилось; имя
слайса — по смыслу действия («установить приложение»), не привязано к
чужому словарю.

Собран из тех же `shared/ui`, что и `DesktopBlockScreen` (`CenteredState`
+ `AppMark` + `TextBlock`), плюс клиентский `InstallSteps`
(`ui/install-steps.tsx`) с самой логикой:

- **Инструкция видна сразу**, не за кнопкой (решение пользователя) —
  `usePhoneOs()` выбирает текст (iOS/Android) из словаря
  (`screens.installApp.instructions.*`); этот экран показывается ТОЛЬКО
  на телефоне, поэтому, в отличие от `DesktopBlockScreen` раньше,
  `usePhoneOs()` здесь реально различает платформу почти всегда (не
  только в редком случае foldable).
- **Системная кнопка установки — только на Android, только когда браузер
  её поддерживает.** `useInstallPrompt()` ловит `beforeinstallprompt`;
  кнопка «Установить» рендерится, только если событие пришло
  (`canInstall`). Нет события (iOS никогда не шлёт его; Android — если
  критерии устанавливаемости не пройдены, или приложение уже
  установлено, или браузер не Chromium) → кнопки нет, остаётся только
  текстовая инструкция — ровно то поведение, которое просили.
- **После установки** (`appinstalled`) экран переключается на «Готово!
  Откройте приложение со значка на главном экране» вместо инструкции —
  той же логикой, что и Chromium передаёт: `beforeinstallprompt` не
  придёт снова на этой загрузке страницы, а `display-mode` сам переведёт
  на `.app-shell` только при следующем полном заходе (переоткрытии со
  значка), не в текущей вкладке браузера.

Доступность: единственный `<main>` (`CenteredState`), `h1` — из
`TextBlock`, кнопка установки — `Button` (react-aria, доступное имя из
словаря).

### Манифест (`web/public/manifest.webmanifest`)

Добавлены `scope: "/"` и `id: "/"` — не менялись раньше, не были строго
обязательны для устанавливаемости Chrome, но рекомендованы (иначе
`scope` по умолчанию берётся из директории `start_url`, а `id` — из
самого `start_url`; лучше явно, чем неявно). Остальное уже
соответствовало критериям устанавливаемости Chrome: `name`/`short_name`,
`start_url`, `display: standalone`, иконки 192 и 512. Подтверждено живой
проверкой через `Page.getInstallabilityErrors` (см. ниже) — Chrome не
находит ошибок манифеста.

### Найденный по пути баг: дубль `/manifest.webmanifest` в precache

Первая попытка живой проверки (`next build && next start`) провалилась:
service worker падал при регистрации (`ServiceWorker script evaluation
failed`). Причина — `web/app/serwist/[path]/route.ts` явно добавлял
`/manifest.webmanifest` в `additionalPrecacheEntries` с ревизией
`git rev-parse HEAD`, **поверх** того же файла, который уже подхватывает
автоматическое сканирование `public/` (с ревизией по хэшу содержимого).
Два precache-элемента на один URL с разными ревизиями — Workbox
(`PrecacheController`) считает это конфликтующим дублем и бросает
исключение прямо при оценке скрипта воркера.

Это старый, никак не связанный с текущей задачей баг — в проекте раньше
никто не собирал `next start`/production-сборку с реально включённым
service worker (`next dev` его отключает, см. `SerwistProvider` в
`root-layout.tsx`), поэтому он ни разу не сработал до этой задачи, первой
потребовавшей живой проверки установки PWA. Исправлено удалением лишней
строки `additionalPrecacheEntries` — автоматического скана `public/`
достаточно. После фикса: 18 precache-элементов вместо 19, `next start`
регистрирует и активирует service worker без ошибок (проверено live,
см. ниже).

## Механизм переключения — в app-слое

`root-layout.tsx` (единственное место, общее для всех маршрутов)
рендерит все три дерева и расставляет CSS-классы/атрибут
`data-device-gate`. `DesktopBlockScreen`/`InstallAppScreen` (`pages`-слой)
при этом импортируются из `app` — это разрешённое направление импорта
FSD (`app` → `pages`), не нарушение. `BottomNav` — внутри `.app-shell`
вместе с `children`, чтобы скрываться/показываться вместе с приложением,
а не оставаться видимым поверх заглушки.

## Что произойдёт с пользователем, который удалил приложение

Откроет старую ссылку/закладку в обычном браузере телефона — CSS увидит
«телефон, не standalone» и покажет `InstallAppScreen` заново, с той же
инструкцией по установке. Никакого отдельного состояния «раньше было
установлено» не хранится и не нужно — щит смотрит только на текущий
`display-mode`, у него нет памяти.

## Живая проверка

`pnpm build` (Turbopack, Next 16.3.5) — все маршруты, включая
`/styleguide` и `/components`, остались `○` (static), кроме уже ранее
динамического `/day` (Supabase-статус, не связано с этой задачей) —
подтверждает, что ни щит, ни `DEV_MODE`, ни `proxy.ts` не перевели
приложение в динамический рендер. `pnpm lint` (ESLint + `steiger`) и
`pnpm typecheck` — чисто.

**Три состояния щита** — часть проверялась на реальном приложении
(`next start`, продовая сборка — dev отключает service worker, а без
него `beforeinstallprompt` в Chrome не приходит), часть — на выделенном
CSS-стенде:

- Десктоп (1440×900, без touch) → `DesktopBlockScreen` — проверено на
  реальном приложении.
- Телефон, браузер (390×844, `isMobile`+`hasTouch`, без переопределения
  `display-mode`) → `InstallAppScreen` с инструкцией — проверено на
  реальном приложении, включая правильный выбор текста по `User-Agent`
  (Android → «Через меню Chrome», iOS → «Через «Поделиться»»).
- Телефон, standalone → `.app-shell`: **не проверено на реальном
  приложении** — Chromium (в т.ч. версия, которой управляет Playwright,
  153.0.8010.53) не поддерживает переопределение `display-mode` через
  `Emulation.setEmulatedMedia` (проверено напрямую: тот же вызов с
  `prefers-color-scheme` работает, с `display-mode` — нет, ни для
  `standalone`, ни для `fullscreen`, при любом порядке вызовов). Открыть
  реальный `--app=`-режим или установленный экземпляр из-под
  автоматизации тоже не удалось — исполнение кода ограничено объектами
  уже существующей `page`/`browser`, без доступа к `require`/`import`
  для запуска второго процесса браузера. Вместо этого логика трёх
  взаимоисключающих состояний (включая переход phone-shield →
  install-shield → app-shell и оба обхода — `PhoneShieldBypass` и
  `DEV_MODE`) проверена на изолированном HTML-стенде с **точной копией**
  правил щита из `globals.css`, где `display-mode: standalone/fullscreen`
  заменён на `prefers-color-scheme: dark` (единственная реально
  переопределяемая фича, подходящая по семантике — булева "включено/
  выключено" настройка) — семь комбинаций (десктоп; телефон+светлая тема
  как прокси «не установлено»; телефон+тёмная как прокси «установлено»;
  планшет+тёмная — тест, что одного «standalone» без «телефона»
  недостаточно; оба обхода), в каждой ровно один из трёх экранов виден,
  ни разу два одновременно или ни одного. Это проверяет структуру
  селекторов и каскада, но не сам факт, что реальный `display-mode:
  standalone` в реальном Chrome на реальном телефоне отработает —
  за это отвечает Baseline-статус фичи (см. выше) и обычная логика CSS
  `@media`, которая для `pointer`/`hover`/`orientation`/`max-width`
  проверена на реальном приложении выше.
- `DEV_MODE=true` → приложение открывается и на десктопе (1440×900), и
  на телефон-эмуляции (390×844, `isMobile`+`hasTouch`) — проверено на
  реальном приложении в обоих случаях; третий вариант (телефон +
  DEV_MODE + фактический standalone) покрыт тем же CSS-стендом (комбинация
  «оба обхода» там подтверждает, что `data-device-gate="off"` побеждает
  независимо от прочих условий).
- `DEV_MODE=false` → щит снова активен (десктоп → `DesktopBlockScreen`).
- `/styleguide` и `/components` на десктопе (продовая сборка) — попадают
  в `.app-shell` через `PhoneShieldBypass`, проверено на реальном
  приложении.

**PWA-устанавливаемость** (продовая сборка, `next start`):

- Service worker регистрируется и активируется без ошибок (после фикса
  дубля precache-записи, см. выше) — проверено `navigator.serviceWorker
  .getRegistrations()`.
- `Page.getInstallabilityErrors` (CDP, официальная проверка Chrome)
  вернул единственную ошибку — `in-incognito` (Playwright создаёт
  изолированные, инкогнито-подобные контексты, которые Chrome
  принципиально не считает устанавливаемыми, независимо от манифеста и
  SW). Других ошибок нет — манифест, иконки, `start_url`, `display`,
  активный service worker проходят проверку Chrome.
- Реальный `beforeinstallprompt` **не пришёл** ни на одной проверке
  (ждали до 4 секунд после `networkidle` с реальным Android User-Agent)
  — известное ограничение автоматизированного/headless Chromium:
  внутренние эвристики "вовлечённости" (engagement heuristics),
  управляющие показом install-баннера, не срабатывают в таких контекстах
  вне зависимости от корректности PWA. Поэтому логика обработки события
  (`useInstallPrompt`/`InstallSteps`) проверена **синтетическим**
  событием: диспатч `beforeinstallprompt` с моком `prompt()`/
  `userChoice` → кнопка «Установить» появляется → клик вызывает
  `prompt()` → диспатч `appinstalled` → экран переключается на «Готово!
  Откройте приложение со значка на главном экране». iOS (реальный
  User-Agent) корректно не показывает кнопку никогда, только
  инструкцию — тоже проверено.
