# 0070. Скелетон на каждом переходе: включаем клиентский кэш роутера

- **Статус**: принято
- **Дата**: 2026-11-07
- **Контекст**: ADR 0059 (границы загрузки и скелетоны), ADR 0066 (решение 9
  — что ревалидация делает с клиентским кэшом)

## Контекст

Владелец заметил: заходишь на день, переходишь в профиль, возвращаешься на
день — и снова скелетон. Каждый раз, сколько бы раз подряд это ни делать.

Это не дефект нашего кода и не следствие того, как устроены чтения. Все
экраны приложения динамические — каждый читает cookie сессии, — а
клиентский кэш роутера в Next 16 по умолчанию держит динамический сегмент
**ноль секунд**.

«Ноль» здесь не означает «быстро устаревает». Проверено по исходникам
установленного Next 16.3.5:

1. `experimental.staleTimes.dynamic` запекается в клиентский бандл **на
   сборке** — `build/define-env.js` превращает его в
   `process.env.__NEXT_CLIENT_ROUTER_DYNAMIC_STALETIME`. Смена требует
   `pnpm build`, перезапуска сервера недостаточно.
2. → `DYNAMIC_STALETIME_MS` в
   `client/components/router-reducer/reducers/navigate-reducer.js`.
3. → читает его ровно один модуль:
   `client/components/segment-cache/bfcache.js`, функция
   `computeDynamicStaleAt`.
4. → записи оттуда берутся и при обычной навигации вперёд, не только по
   кнопке «назад»: `ppr-navigations.js` зовёт
   `readFromBFCacheDuringRegularNavigation`.
5. → свежесть решается в `segment-cache/cache-map.js`:

```js
function isValueExpired(now, currentCacheVersion, value) {
    return value.staleAt <= now || value.version < currentCacheVersion;
}
```

При `dynamic: 0` выходит `staleAt = now + 0`, то есть `staleAt <= now`
истинно в тот же миллисекунд. Запись невалидна с рождения, промах
гарантирован всегда. Отсюда и скелетон на каждом переходе.

Подтверждает это и PR самих Vercel про bfcache (#77992): «Normal
navigations only cache dynamic data if you opt in through
`experimental.staleTimes.dynamic`». То есть флаг — единственный штатный
способ включить то, что нужно.

## Варианты

### A. Оставить как есть

Ничего не делать. Скелетон при каждом переходе между экранами приложения.
Честно показывает, что данные перечитываются, но на телефоне это выглядит
так, будто приложение каждый раз загружается заново.

### B. React Query

Рассматривался и **отвергнут**. Он управляет клиентским состоянием
запросов, а данные здесь приходят серверными компонентами. Чтобы он
что-нибудь кэшировал, пришлось бы завести HTTP-ручки под каждый экран,
превратить `/day`, `/month`, `/year`, `/calendar` и `/profile` в
клиентские компоненты, потерять серверную отрисовку — и после этого
заново решать то, что сейчас решают `ROUTE_POLICY` и RLS. Замена
архитектуры ради тридцати секунд кэша, которые даёт строка конфига.

### C. `unstable_dynamicStaleTime` на отдельных страницах

В Next 16 появился экспорт со страницы — число секунд; `app-render.js`
берёт минимум по дереву, читает только у `page`, не у `layout`, и отдаёт
клиенту полем `d` флайт-ответа, падая на глобальное значение при
отсутствии. Точнее варианта D: можно включить кэш там, где устаревание
безвредно, и оставить `/day` всегда свежим.

Отвергнут: префикс `unstable_`, в публичной документации его нет вовсе
(нашёлся только в исходниках и в правилах TypeScript-плагина), значит и
ломаться он будет тише. Глобальный флаг задокументирован, и про него есть
кому написать в changelog.

### D. `experimental.staleTimes.dynamic` — принято

## Решение

```ts
experimental: { staleTimes: { dynamic: 30 } },
```

**Тридцать секунд, а не выдуманное число**: ровно столько Next держал
динамический сегмент по умолчанию до версии 15, где дефолт специально
опустили до нуля.

**Только `dynamic`.** Пример в документации выглядит как
`{ dynamic: 30, static: 180 }`, и скопировать его целиком — значит молча
ухудшить кэш статических страниц с 300 секунд до 180. Проверено в
`build/define-env.js`: если `static` не передан, `Number(undefined)` даёт
`NaN` и подставляется `5 * 60`.

### Почему это не делает экран лживым

Вторая половина `isValueExpired` — `value.version < currentCacheVersion`.
Версию поднимает `invalidateBfCache()`, и её зовёт любая ревалидация
внутри Server Action. В этом приложении ревалидируют: сохранение часов,
закрытие и переоткрытие месяца, смена статуса служения, вход и выход.
Плюс `router.refresh()` при возврате связи и при перевороте даты.

Значит окно в тридцать секунд может скрыть только изменение, сделанное
**с другого устройства**. Для изменений, сделанных здесь же, его не
существует вовсе — кэш выселяется в тот же момент.

И гейт от этого не слабеет: выход зовёт `revalidatePath("/", "layout")`,
версия растёт, ни одна запись не переживает. Вернуться назад на экран с
данными после выхода нельзя — ни до этой правки, ни после.

## Последствия

- Переход между экранами, уже посещёнными в последние тридцать секунд, —
  мгновенный, без скелетона.
- Два устройства одного человека могут до тридцати секунд показывать
  разные суммы. Это та же цена, что уже названа в обзоре: запись дня
  посылает абсолютное число, и расхождение между устройствами существует
  независимо от этого флага.
- **Флаг экспериментальный, и это единственное, чего тут стоит
  опасаться.** Не «стухших данных», а того, что поведение поменяется на
  минорном обновлении Next. В 16-й версии он уже переехал внутрь нового
  segment-cache и обслуживается bfcache-машинерией, хотя в «Version
  History» документации об этом ни строчки — там только запись про
  15.0.0. Проверять после каждого обновления Next; цена ошибки —
  скелетон вернулся, а не данные потерялись.
- Снимается одной строкой.

### Чего документация НЕ говорит

По сети ходит утверждение, что официальная документация не рекомендует
этот флаг для production. **Это неправда.** Живая страница
(`nextjs.org/docs/app/api-reference/config/next-config-js/staleTimes`,
`lastUpdated: 2026-03-03`) несёт бейдж `Experimental` и ни слова про
production; та же страница лежит в нашем `node_modules` — текст
совпадает дословно. Фраза «not recommended for production» происходит из
блог-постов, не от Vercel. Записано здесь, чтобы следующий читатель не
снял флаг по чужой цитате.
