# ADR 0010: Политика версий зависимостей

## Контекст

К этому моменту версии в `web/package.json` разъехались по стилю
(часть — точные версии, часть — диапазоны `^4`/`^19`/`^5`/`^20`,
оставшиеся от `create-next-app`/`shadcn init`), а сами версии не
пересматривались с момента добавления. Нужна явная политика: на что
опираться при выборе версии зависимости, и единый стиль записи.

## Решение

### Стиль записи версий

Точные версии (без `^`/`~`) — доминирующий стиль в проекте (большинство
записей в `package.json` уже так оформлены: `next`, `@serwist/turbopack`,
`@supabase/ssr`, `@t3-oss/env-nextjs`, `zod`, `esbuild`, `serwist`,
`steiger` и т.д.). Приведены к тому же стилю оставшиеся diapазоны:
`@types/node`, `@types/react`, `@types/react-dom`, `typescript`, `eslint`,
`tailwindcss`, `@tailwindcss/postcss`, `react`, `react-dom`, `zod`,
`lucide-react`.

Причина: точная версия — то, что реально протестировано (`pnpm lint` /
`pnpm typecheck` / `pnpm build` прогнаны именно на ней), а не диапазон,
который может резолвиться в разные версии на разных машинах/CI без
`pnpm-lock.yaml` под рукой. Обновление — осознанное действие
(`pnpm outdated` → `pnpm update --latest` → прогнать lint/typecheck/build
→ закоммитить `pnpm-lock.yaml` вместе с новой версией в `package.json`),
а не то, что происходит само по себе при случайном `pnpm install` без
lock-файла.

Пакеты, добавленные/управляемые `shadcn`/сторонними CLI (`@base-ui/react`,
`class-variance-authority`, `cn`, `shadcn`, `tw-animate-css`) оставлены как
есть — их диапазоны расставляет сам `shadcn init`/`shadcn add`, трогать их
вручную вне этого CLI не стоит.

### `minimumReleaseAge` (pnpm ≥ 11, см. ADR 0008) как supply-chain защита

pnpm по умолчанию отказывается устанавливать версию пакета младше суток
(1440 минут) — защита от компрометации пакета сразу после публикации
(типичный вектор supply-chain атаки: злоумышленник публикует вредоносную
версию, она быстро попадает в чьи-то `pnpm install` до того, как
сообщество успевает её отозвать/пожаловаться). При обновлении зависимостей
это означает: **новая версия должна быть опубликована минимум сутки
назад**, иначе `pnpm install` откажет
(`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`). Не добавлять пакеты/версии в
`minimumReleaseAgeExclude` — это исключение из самой защиты, а не способ
её "нормально" обойти при обновлении. Если нужная версия ещё не созрела —
либо подождать (обычно 1-2 дня), либо взять предыдущую, уже зрелую версию
(как сделано с `lucide-react`/`zod` в ADR 0008 на предыдущем раунде).

### Почему TypeScript не 7.x

На npm уже доступен TypeScript 7.0.2 (переписан на Go, значительно
быстрее), но `typescript-eslint@8.70.0` (то, что реально резолвится через
`eslint-config-next@16.3.5` → `^8.46.0`) объявляет peer-диапазон
`typescript: ">=4.8.4 <6.1.0"` — TypeScript 7.x в этот диапазон не
попадает. Выбрана последняя версия TypeScript **в этом диапазоне** —
**6.0.3** (не 6.0.2/6.0.1-rc — более старые; не 6.1+ — такого релиза пока
нет). Проверено: `pnpm lint`, `pnpm typecheck`, `pnpm build` проходят
чисто на 6.0.3 (единственное следствие — предупреждение `pnpm peers
check` про транзитивный `tsconfck@3.1.6` внутри `steiger`, который сам
объявляет `^5.0.0` и не используется для сборки/тайпчека приложения —
не блокирует установку и не влияет на реальную работу линтера).

Когда `typescript-eslint` расширит диапазон до `<7.x` (или
`eslint-config-next` перестанет тянуть typescript-eslint вовсе) — можно
пересмотреть переход на TypeScript 7.

### Почему eslint не 10.x

`npm view eslint version` показывает `latest: 10.10.0`, но
`eslint-config-next@16.3.5` тянет `eslint-plugin-react@^7.37.0`,
`eslint-plugin-import@^2.32.0`, `eslint-plugin-jsx-a11y@^6.10.0` —
все три объявляют поддержку ESLint только до `^9` (`eslint-plugin-react-hooks`,
для сравнения, уже поддерживает `^10.0.0`, но это не решает проблему двух
остальных плагинов). Зафиксирован **9.39.5** — последний релиз ветки 9.x
на момент правки.

### Почему Node/`@types/node` — 24, а не 26

Node 24 — текущий LTS (Active LTS на момент правки), это версия, на
которой реально работает локальная разработка (`node -v` на машине
разработчика) и которую поддерживает Vercel для прод-деплоя. Node 26 —
более новая мажорная ветка, но не LTS на момент правки (обычно становится
LTS через несколько месяцев после релиза, по циклу Node.js). Смысла
таргетить не-LTS ветку в `engines.node`/`@types/node` нет: тестовое
окружение (локально и на Vercel) — Node 24. `@types/node` зафиксирован на
последней 24.x (`24.13.4`), а не на диапазоне `^20` (устаревшая мажорная
версия типов относительно реально используемого рантайма) и не на `^26`
(типы для версии, на которой ничего не запускается). `engines.node` в
корневом `package.json` изменён с `>=20` на `>=24`.

### Как обновлять зависимости

1. `pnpm outdated` — посмотреть, что устарело.
2. `pnpm update --latest` (точечно — конкретный пакет, а не все сразу
   вслепую) в затронутом workspace-пакете (`pnpm --filter web update
   --latest <pkg>`).
3. Прогнать `pnpm lint && pnpm typecheck && pnpm build` — если что-то
   ломается, разбираться (peer-конфликт, breaking change в самом пакете),
   а не откатывать не глядя.
4. Если `pnpm install`/`update` упирается в `minimumReleaseAge` — см. выше
   (ждать или брать предыдущую зрелую версию, не добавлять исключение).
5. Коммитить `package.json` + `pnpm-lock.yaml` вместе, одним изменением.

## Последствия

- Версии в `web/package.json` теперь единообразно точные (кроме пакетов
  под управлением `shadcn`).
- TypeScript и ESLint осознанно "отстают" от последних мажорных релизов —
  это задокументированное, а не забытое решение; при снятии blocker'а
  (обновлении `typescript-eslint`/плагинов ESLint) стоит пересмотреть.
- `engines.node` в корне — `>=24`, соответствует Node LTS, на котором
  реально ведётся разработка и деплой.
