# ADR 0052: CI гоняется только на названных слияниях

Статус: принято, 2026-10-13. Решение владельца.
Меняет триггеры `ci.yml` и `db-test.yml` (ADR 0039 — что эти проверки
проверяют; здесь только о том, когда они запускаются).

## Контекст

До этого `ci.yml` и `db-test.yml` запускались на **каждом** pull request
любой базовой ветки и на каждом push в `develop`/`master`. Ветки в
проекте живут по схеме «фича → релизная ветка → develop → master», и на
нижнем участке этой цепочки проверки гонялись на каждый коммит каждой
фичи — минуты раннера за результат, который всё равно будет перепроверен
выше.

## Решение

Запускать только на тех слияниях, которые владелец назвал:

| База PR | Из какой ветки | Когда |
|---|---|---|
| ветка со словом `release` | любая | **только при открытии** PR (и переоткрытии) |
| `develop` | `release*` | открытие, переоткрытие и **каждый новый коммит** |
| `master` | `develop` | то же |
| `master` | `hotfix/*` | то же |
| всё остальное | — | не запускается |

Плюс `push` в `master` — но не в `develop`, см. ниже.

Условие стоит на job, а не в `on:`: `on:` не умеет задавать разные типы
событий для разных базовых веток, а job, пропущенный по `if:`, раннер не
занимает.

```yaml
if: >-
  github.event_name != 'pull_request'
  || (github.base_ref == 'develop' && startsWith(github.head_ref, 'release'))
  || (github.base_ref == 'master' && github.head_ref == 'develop')
  || (github.base_ref == 'master' && startsWith(github.head_ref, 'hotfix/'))
  || (contains(github.base_ref, 'release') && github.event.action != 'synchronize')
```

Имя релизной ветки заранее не известно — известно, что в нём есть слово
`release`, поэтому `contains`, а не точное совпадение.

`workflow_dispatch` добавлен в оба workflow: это способ перезапустить
проверку руками, и правило выше делает его необходимым (см. ниже).

Путевые фильтры `db-test.yml` продолжают работать поверх: фронтовая
правка по-прежнему не поднимает базу.

## Четыре решения, доуточнённые владельцем (2026-10-13)

Таблица выше отвечала только на вопрос «какие PR», и из неё следовали
четыре вопроса, которых правило не покрывало. Ответы владельца:

1. **`push` — только в `master`, не в `develop`.** Прогон на push
   проверяет не ветку, а **результат** слияния: два PR могут быть зелёными
   каждый и ломать сборку вместе. Но в `develop` сливается только релизная
   ветка, а она проверяется покоммитно, то есть тот же код проверялся
   минуту назад — это дублирование. В `master` прогон оставлен: там
   плохой мерж стоит прода.
2. **`ready_for_review` не добавляется** — владелец не пользуется
   draft-PR, поэтому ловушка «единственная проверка сгорела на черновике»
   в этом проекте не возникает. Если draft-PR когда-нибудь появятся,
   вернуться к этому пункту: иначе в релизную ветку поедет галочка от
   черновика.
3. **Проверки обязательны в branch protection для `develop` и `master`,
   и не обязательны для релизной ветки.** Там, где проверяется каждый
   коммит, требовать галочку безопасно. В релизной ветке проверка одна, в
   момент открытия, и GitHub принял бы её как действующую после любого
   числа новых коммитов — замок, который выглядит закрытым и не закрыт.
   Лучше честно не иметь замка, чем иметь поддельный.
4. **`hotfix/* → master` проверяется**, на тех же условиях, что
   `develop → master` (каждый коммит). Хотфикс минует `develop` по своей
   природе, и без этого пункта единственная правка, которая едет в прод
   быстрее всех и пишется в спешке, была бы единственной, которую не
   проверяет ничто. Событие редкое — раннер это не нагрузит.

## Последствия

- **Зелёная галочка на PR в релизную ветку может устареть.** Он
  проверяется один раз, в момент открытия; коммиты, добавленные после,
  не проверяются. Именно поэтому эти проверки **не** сделаны
  обязательными для релизной ветки (решение 3): GitHub принял бы
  устаревший результат и разрешил слить непроверенный код. Способ
  перепроверить — кнопка «Run workflow» (`workflow_dispatch`).
- Черновик (draft) PR даёт событие `opened`, то есть единственная
  проверка PR в релизную ветку сгорела бы на черновике. Сегодня это
  безопасно только потому, что draft-PR в проекте не используются
  (решение 2) — это условие, а не свойство схемы.
- PR в `develop` не из релизной ветки не проверяется вообще.
- Слияние в `develop` не проверяется после мержа (решение 1). Плохой
  результат слияния в `develop` поймает первый же PR из `develop` в
  `master` — то есть до прода, но не сразу.

## Что надо включить руками в GitHub

Решение 3 миграциями и файлами в репозитории не ставится — это
настройки репозитория, по той же природе, что ручные шаги в облаке
Supabase (CLAUDE.md, раздел «Что в облаке надо включить руками»).
Settings → Branches → Add branch ruleset (или Branch protection rule)
для `develop` и для `master`:

- Require status checks to pass → добавить **Lint, types, tests** и
  **pgTAP and generated types** (имена джобов, не workflow'ов);
- **не** включать «Require branches to be up to date before merging»:
  она требует прогона на каждый коммит, то есть ровно того, от чего
  уходит это ADR;
- для релизной ветки правило **не создавать** — см. решение 3.

### Измерено: на текущем тарифе включить нельзя

При попытке создать ruleset GitHub показывает баннер «Your rulesets won't
be enforced on this private repository until you move to GitHub Team
organization account», а REST API отвечает прямо:

```
GET /repos/<owner>/ministry-app/rules/branches/master
403 Upgrade to GitHub Pro or make this repository public to enable this
    feature.
```

Репозиторий приватный, аккаунт личный и бесплатный — значит защита веток
недоступна **ни рулсетами, ни классическим branch protection**. Форму
можно заполнить и сохранить, но она ничего не будет применять: баннер об
этом и предупреждает.

Варианты, из которых выбирать:

1. **Ничего не делать** (принято на сегодня). Репозиторием пользуется один
   человек, и branch protection защищал бы его от самого себя. Проверки
   гоняются, галочка видна в PR, дисциплина — ручная.
2. **GitHub Pro** (~$4/мес) — по тексту ошибки API этого достаточно для
   приватного репозитория. Включать, когда появится второй человек с
   правом записи: вот тогда «можно слить мимо красной галочки» перестаёт
   быть вопросом дисциплины.
3. Сделать репозиторий публичным — не рассматривается.

Пока ни один из них не выбран, правило живёт только в `if:` workflow'ов:
проверки гоняются, но слить мимо красной галочки технически можно, и
это **не** защищено ничем, кроме внимательности.
