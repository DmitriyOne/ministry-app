# ADR 0003: Локальный запуск — Next.js нативно на хосте + Supabase в Docker

> **Статус: частично заменено ADR 0009.** Общее решение этого ADR (Next.js
> нативно на хосте, Supabase — через Supabase CLI/Docker) остаётся в силе.
> Заменена только часть про опциональный `docker-compose` для самого
> `web` — от контейнерного запуска `web` отказались целиком, см. ADR 0009.

## Контекст

Нужно определить, как разработчик поднимает окружение локально: что бежит
нативно на хосте, а что — в контейнерах, и является ли Docker-Compose
основным или вспомогательным путём.

## Варианты

1. **Всё в Docker Compose** (и `web`, и Supabase) — единая команда для
   всего, но медленнее hot-reload у Next.js через bind-mount, сложнее
   дебажить, лишний слой абстракции для повседневной разработки.
2. **Всё нативно на хосте** — включая Postgres/GoTrue/Storage и т.д. вручную
   — нереалистично: Supabase поставляет свой стек только через Docker
   (Supabase CLI сам оборачивает `docker compose` под капотом).
3. **Next.js нативно на хосте, Supabase — через Supabase CLI (Docker)
   под капотом), Docker Compose для `web` — опциональный альтернативный
   путь.**

## Решение

Выбран вариант 3:
- `pnpm dev` = `supabase start` (сам поднимает нужные контейнеры Supabase
  через Docker) → дождаться готовности (`wait-on` на health-эндпоинт
  GoTrue) → `next dev` нативно на хосте.
- `ops/local/docker-compose.yml` + `ops/local/Dockerfile` — отдельный,
  необязательный путь: контейнеризованный `web`, обращающийся к локальному
  Supabase через `host.docker.internal`. Используется, когда нужно
  проверить поведение именно в контейнере (например, перед переносом на
  self-hosted Docker-инфраструктуру), но не является основным способом
  повседневной разработки.

Причины:
- Next.js dev-сервер нативно на хосте даёт быстрый hot-reload и прямой
  доступ к отладчику/IDE без наворотов bind-mount'ов.
- Supabase CLI и так требует Docker для эмуляции Postgres/Auth/Storage/Edge
  Functions локально — дублировать эту оркестрацию вручную в
  docker-compose не имеет смысла, CLI справляется лучше.
- Docker Compose для `web` пригодится, когда встанет вопрос
  self-hosted-деплоя (не Vercel) — тогда `ops/local/Dockerfile` можно
  использовать как отправную точку.

## Последствия

- Разработчику нужен Docker (для Supabase CLI) и Node.js/pnpm (для Next.js)
  локально — оба обязательны в любом случае.
- `ops/local/Dockerfile` — не прод-сборка (без multi-stage, без
  `output: standalone`); использовать для прод-образа нельзя без доработки.
- `pnpm docker:local` не поднимает Supabase — предполагается, что он уже
  запущен на хосте (`pnpm db:start`) до или параллельно с этой командой.
