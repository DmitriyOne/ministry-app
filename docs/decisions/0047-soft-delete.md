# ADR 0047: soft-delete во всех таблицах

Статус: принято, 2026-10-05.
Относится к v2 и ко всем будущим таблицам. Уточняет ADR 0033/0037
(модель доступа) и ADR 0043 (профили), связано с ADR 0045 (окно доступа
по выданному токену).

## Контекст

Требование владельца: в базе всё должно быть soft-delete. На момент
решения в схеме четыре таблицы — `profiles`, `user_roles`,
`waitlist_signups`, `push_subscriptions` — и ни одна строка физически не
удаляется из приложения: у `profiles` нет политики `delete`, у двух
закрытых таблиц нет политик вовсе. Удаляет сегодня только владелец
руками в Studio и скрипт рассылки (см. ниже).

То есть правило касается в первую очередь **будущих таблиц** и ручных
действий, а не существующего кода. Это не повод его не вводить: первое
же удаление в приложении будет написано по образцу, который заложен
сейчас.

## Решения

### «Удалить человека» = бан в Auth + `deleted_at` в профиле

`profiles.id` и `user_roles.user_id` ссылаются на `auth.users` с
`on delete cascade`. Таблицей `auth.users` владеет Supabase, колонку
`deleted_at` туда не добавить. Значит настоящее удаление из Auth снесло
бы и профиль, и роль — никакой soft-delete этого не предотвратит.

Поэтому строка в `auth.users` **не удаляется никогда**. Отключение
человека — это `banned_until` через Admin API плюс
`update public.profiles set deleted_at = now()`.

Каскад **оставлен** — не как рабочий путь, а как страховка: если кто-то
всё же удалит человека из Auth руками, висящих строк с битым внешним
ключом не останется. Рассматривался вариант снять каскад (`on delete set
null`), но тогда `profiles.id` перестаёт быть первичным ключом-ссылкой,
нужна отдельная колонка и переделка триггера — цена выше пользы.

### Охват — все четыре таблицы

```sql
alter table public.profiles           add column deleted_at timestamptz;
alter table public.user_roles         add column deleted_at timestamptz;
alter table public.waitlist_signups   add column deleted_at timestamptz;
alter table public.push_subscriptions add column deleted_at timestamptz;
```

Включая таблицы вайтлиста, которые уже работают в проде. Это осознанно
дороже варианта «только новые»: пришлось править две RPC-функции, хук,
скрипт рассылки и тесты.

### Уникальность — частичным индексом, иначе адрес занят навсегда

```sql
alter table public.waitlist_signups drop constraint waitlist_signups_email_key;
create unique index waitlist_signups_email_live_key
  on public.waitlist_signups (email) where deleted_at is null;
```

То же для `push_subscriptions.endpoint`. Без этого помеченная удалённой
запись продолжала бы занимать адрес, и человек никогда не записался бы
заново.

### Ловушка, из-за которой прод сломался бы молча

`register_waitlist_push_subscription` делает upsert через
`on conflict (endpoint)`. Вывод цели конфликта работает по индексам, и
**для частичного индекса предикат надо повторить**:

```sql
on conflict (endpoint) where deleted_at is null
```

Проверено: без предиката вставка падает с «there is no unique or
exclusion constraint matching the ON CONFLICT specification». То есть
замена ограничения на частичный индекс без правки функции сломала бы
подписку на уведомления, и упало бы это не в миграции, а у человека на
телефоне. Закреплено pgTAP-тестом `lives_ok` на повторную регистрацию
того же endpoint.

### Где гарантия настоящая, а где — договорённость

Выбран вариант «обеспечивать в RLS-политиках». Честная оговорка: это
выполнимо только для `profiles` — единственной таблицы с политиками.

| Таблица | Чем закрыто от выдачи удалённых строк |
|---|---|
| `profiles` | RLS-политики: `using (... and deleted_at is null)` — **база не отдаст** |
| `user_roles` | политик нет; фильтр в `custom_access_token_hook` |
| `waitlist_signups` | политик нет; фильтр в `join_waitlist` и `register_waitlist_push_subscription` |
| `push_subscriptions` | политик нет; фильтр в скрипте рассылки |

Для трёх последних гарантия **слабее**: в новой функции фильтр можно
забыть, и база не остановит. Компенсация — pgTAP-тесты на каждое
следствие и это правило в `CLAUDE.md`. Усилить можно было бы
представлениями с `security_invoker`, но это удваивает объекты у таблиц,
к которым всё равно никто, кроме `service_role`, не дотягивается.

### Что ещё пришлось поправить

- `join_waitlist`: поиск по адресу и **подсчёт номера в списке** —
  иначе удалённые записи раздували бы позицию живых.
- `custom_access_token_hook`: выборка роли — иначе роль, помеченную
  удалённой, он положил бы в JWT.
- `pnpm push:launch`: выборка подписчиков фильтрует удалённых, а его
  **жёсткое удаление мёртвых endpoint'ов (404/410) заменено на
  `update ... set deleted_at`**. Это нашлось только при реализации:
  правило «ничего не удаляем» нарушал сам скрипт.
- `execute` на двух триггерных функциях (`handle_new_user`,
  `set_updated_at`) отозван у `public`, `anon`, `authenticated`.
  Эксплуатировать его было нельзя — прямой вызов даёт «trigger functions
  can only be called as triggers», проверено, — но правило проекта
  «наружу выдаётся только нужный `execute`» действует и здесь. Отдельно
  проверено, что отзыв **не ломает триггеры**: создание человека через
  Admin API по-прежнему создаёт и профиль, и роль (Postgres проверяет
  `execute` при создании триггера, а не при каждом срабатывании).

## Последствия

- **Бан не отзывает уже выданный access-токен.** То же окно до часа, что
  описано в ADR 0045 для удаления: токен проверяется локально, и до
  `exp` человек продолжает ходить по приложению. Забанить и ждать
  мгновенного отключения нельзя; рычаг — уменьшить `jwt_expiry`.
- Данные не уменьшаются никогда. Политики удержания и чистки нет; когда
  объём станет заметен, это отдельное решение (партиционирование,
  архивная таблица или осознанный `delete` по расписанию).
- Восстановление — `update ... set deleted_at = null`. Отдельного
  механизма «восстановить человека» в приложении нет: для `profiles`
  надо ещё снять бан в Auth.
- Любая новая таблица обязана получить `deleted_at` и объявлять
  уникальность частичным индексом. Правило — в `CLAUDE.md`, раздел
  «Договорённости».
- Запросы по живым строкам опираются на частичные индексы, то есть
  индекс меньше таблицы — это скорее выигрыш, чем цена.
