# ADR 0014: Словарь текстов — next-intl, один язык, один файл

## Контекст

Все тексты интерфейса были захардкожены прямо в разметке: видимый текст,
`aria-label`/`title`/`alt`/`placeholder`, тексты ошибок zod-схемы демо-формы.
Задача — завести единый словарь и перенести туда абсолютно все строки, чтобы
в разметке не осталось ни одной; структура при этом не должна мешать
добавить второй язык позже, хотя сейчас поддерживается только русский.

Решения по объёму — пользователя, не переоткрываются:

1. Библиотека — **next-intl**.
2. Язык один — **русский**, без сегмента в URL, без переключателя, без
   определения языка браузера.
3. Словарь — **один файл** на всё приложение.
4. Контроль — правило ESLint, не пропускающее строковые литералы в разметке.

## Почему next-intl, а не свой словарь

Свой словарь (`const messages = {...}` + самодельный `t()`) не даёт того,
ради чего он вообще нужен в проекте на Next.js App Router:

- типизацию ключей по структуре JSON «из коробки» (через `declare module
  "next-intl" { interface AppConfig { Messages: typeof messages } }`) —
  свою версию пришлось бы поддерживать вручную и она бы рассинхронизировалась;
- ICU-плюрализацию (`{count, plural, one {…} few {…} many {…} other {…}}`)
  с корректными категориями CLDR для `ru` (`one/few/many/other`) — своя
  реализация плюрализации на функции-переключателе быстро превращается в
  россыпь `if`;
- форматтеры дат/чисел, привязанные к локали, а не к ручной сборке строк;
- интеграцию с RSC (`getTranslations` в серверных компонентах,
  `NextIntlClientProvider` — в клиентских) без самодельного прокидывания
  словаря через пропы на каждом уровне.

Альтернатива — `react-i18next`/`i18next` — тоже жизнеспособна, но у неё нет
специфичной для Next.js App Router интеграции (RSC, `next.config`-плагин),
которую даёt next-intl «из коробки»; `next-intl` активно поддерживается и
это референсная библиотека для App Router.

## Без i18n-роутинга

Один язык, без сегмента `/[locale]/` в URL: `web/next.config.ts` подключает
`createNextIntlPlugin` с путём к конфигу запроса
(`./src/shared/config/i18n/request.ts`) вместо `routing.ts` с
`defineRouting`/`locales`. `request.ts` жёстко возвращает `locale: "ru"` и
статически импортированный `messages/ru.json` — никакого чтения из
cookie/заголовка/URL.

**Готовность к расширению**: сама локаль вынесена в отдельный модуль
(`web/src/shared/config/i18n/locale.ts`, `export const locale = "ru"`), а не
разбросана строковыми литералами по `request.ts`/`root-layout.tsx`/
`types.ts`/лейауту `<html lang>`. Когда появится второй язык, меняется:

1. `locale.ts` → чтение из cookie/`Accept-Language`/URL вместо константы
   (по образцу примера `example-app-router-without-i18n-routing` из
   документации next-intl — читать `locale` cookie, писать её через
   `Server Action`);
2. `request.ts` → `messages/${locale}.json` вместо жёсткого `ru.json`;
3. добавляется `messages/<новый-язык>.json` — переносить сами тексты никуда
   не придётся, ключи уже вынесены.

Компонент выбора языка, роутинг `/[locale]/` — не заводились, так как не
нужны сейчас; это следующая задача, не блокирующая текущую архитектуру.

## Один файл словаря — когда стоит разбить по слайсам

Сейчас единственный файл `web/src/shared/config/i18n/messages/ru.json`
(решение пользователя) — оправдано объёмом проекта (несколько
экранов-заглушек и две служебные витрины). Разбивать по слайсам
(`pages/day/messages.ru.json` и т.п. с последующей склейкой в
`request.ts`) стоит, когда:

- файл станет неудобно листать/ревьюить (счёт на сотни строк на реальный
  экран, а не на заглушку);
- появятся фичи/сущности (`features/`, `entities/`) со своими текстами —
  тогда естественно вынести их тексты рядом с слайсом, как и остальной код
  (FSD: «код лежит рядом с использованием»), и подключать их в
  `request.ts` через `deepmerge` нескольких JSON.

До этого момента расщепление — преждевременная абстракция без
подтверждённой необходимости.

## Типизация ключей

`web/src/shared/config/i18n/types.ts`:

```ts
declare module "next-intl" {
  interface AppConfig {
    Locale: AppLocale;
    Messages: typeof messages;
  }
}
```

Файл не импортируется нигде явно — работает за счёт `tsconfig.json`
(`include: ["**/*.ts", ...]`), который и так включает все `.ts`-файлы
проекта в программу компиляции; next-intl подхватывает глобальную
аугментацy `AppConfig` и после этого `useTranslations`/`getTranslations`
типизируют `t("...")` по структуре `ru.json`.

**Проверено экспериментально**: в `password-field.tsx` ключ `t("show")`
временно заменён на заведомо несуществующий `t("shwo")` —
`pnpm typecheck` немедленно упал с `TS2345: Argument of type '"shwo"' is
not assignable to parameter of type 'NamespacedMessageKeys<...,
"a11y.passwordField">'`; после возврата ключа `pnpm typecheck` снова
чистый. Аналогично для `i18next/no-literal-string` (см. ниже).

## Схема ключей

Вложенная, по смыслу — не плоский список, не по слайсам (см. выше):

- `metadata.*` — `<title>`/`description` (`root-layout.tsx`);
- `common.*` — переиспользуемые между компонентами подписи действий
  (сейчас — `common.back`, дефолт `ScreenHeader.backLabel`);
- `a11y.*` — доступные подписи, которые сам компонент `shared/ui` даёт по
  умолчанию, если вызывающая сторона не передала свою: `a11y.passwordField.
  show/hide` (кнопка-глаз), `a11y.bottomNav.primary`;
- `screens.<slug>.*` — тексты экранов-заглушек `src/pages/*`
  (`screens.day.title`, `screens.login.title` и т.д.) — ключ на каждый
  реальный слайс страницы, а не общий список;
- `showcase.*` — внутренние служебные страницы (не часть UX приложения):
  - `showcase.styleguide.*` — `/styleguide` (палитра, типографика,
    иконки, кнопки, включая новый раздел `showcase.plurals.*` с
    демонстрацией ICU-плюрализации);
  - `showcase.components.*` — `/components` (матрица использования,
    карточки каталога `cards.<component>.*`, живые примеры
    `textRoles.*`).

Общее правило: ключ отражает **место использования и роль текста**, а не
дублирует русский текст транслитерацией. `common`/`a11y` — только для
текстов, которые компонент `shared/ui` может выдать сам по умолчанию (ADR
0013: «глупый» компонент, тексты — пропсами); реальный текст конкретного
экрана/формы передаётся пропом и живёт в `screens.*`/будущих
`features.*`, не в `a11y`/`common`.

## Множественные числа и форматы

ICU-плюрализация в `showcase.plurals.*` (`hours`/`minutes`/`studies`/
`daysLeft`) с полным набором категорий CLDR для `ru` (`one`/`few`/`many`/
`other`), не склейкой строк:

```json
"hours": "{count, plural, one {# час} few {# часа} many {# часов} other {# часа}}"
```

Продемонстрировано отдельным разделом «Числа и множественные числа» на
`/styleguide` (три образца — 4, 5, 21 — чтобы увидеть все три словоформы),
проверено вживую (Playwright): «4 часа / 5 часов / 21 час», «4 минуты / 5
минут / 21 минута», «4 изучения / 5 изучений / 21 изучение», «Осталось 4
дня / Осталось 5 дней / Остался 21 день» — все словоформы верны. Эти же
ключи понадобятся при сборке реальных экранов «День» (часы/минуты) и
«Месяц» (изучения, «осталось N дней»).

Строковые значения с фигурными/угловыми скобками, не являющиеся
ICU-аргументами или тегами `t.rich`, экранированы одинарными кавычками по
правилам ICU MessageFormat (`rows['{'label, ...'}']`,
`Список '<ul>'/'<li>' ...`) — иначе `next-intl` пытается распарсить их как
синтаксис (`INVALID_MESSAGE`, проверено на живом сервере, ошибка исчезла
после экранирования).

## Правило линтера

Рассматривались `react/jsx-no-literals` (только JSX-текст, не покрывает
атрибуты) и `eslint-plugin-i18next` (правило `no-literal-string`, отдельно
настраиваемые JSX-текст и список атрибутов). Выбран **`eslint-plugin-
i18next`** — из коробки различает JSX-текст и атрибуты, поддерживает flat
config (ESLint 9), и позволяет ограничить проверку атрибутов конкретным
списком (`jsx-attributes.include`), не трогая технические пропы вроде
`variant`/`className`/`data-*`.

Конфигурация (`web/eslint.config.mjs`):

```js
"i18next/no-literal-string": ["error", {
  mode: "jsx-only",
  "jsx-attributes": {
    include: ["aria-label", "aria-labelledby", "alt", "title", "placeholder"],
  },
  callees: { exclude: ["i18n(ext)?", "t", "t\\.rich"] },
}]
```

- `mode: "jsx-only"` — проверяются только строковые литералы внутри JSX
  (видимый текст и атрибуты), а не любой строковый литерал в кодовой базе.
  Сознательно не включён `mode: "all"`: он ловил бы и технические строки
  вне разметки — `variant="deep"`, `cn()`-классы, ключи объектов,
  тесто-`data-testid`, — превратив правило в исключения на каждый
  технический литерал вместо защиты словаря. Такие места (например,
  тексты ошибок zod) переносятся в словарь вручную, по чек-листу задачи,
  а не автоматической проверкой линтера — ловить их линтером по всему
  проекту нецелесообразно (см. рассуждение выше про `all`).
- `jsx-attributes.include` — узкий список ровно тех атрибутов, что
  указаны в задаче (`aria-label`/`title`/`alt`/`placeholder`, плюс
  `aria-labelledby` как тот же кейс доступного имени). Всё остальное
  (`className`, `data-*`, `variant`, `size`, `type`, `key`, `id` и т.д.) —
  не проверяется, они и так исключены дефолтным конфигом плагина
  (`jsx-attributes.exclude` по умолчанию) или не являются языковым
  текстом.
- `callees.exclude` — вызовы `t("key")`/`t.rich("key", {...})` пропускаются:
  строковый аргумент — путь в словаре, а не языковой текст.

**Проверено на живом примере**: в `BottomNav.tsx` `aria-label={t("primary")}`
временно заменён на литерал `aria-label="Основная навигация"` —
`pnpm lint` упал с `error disallow literal string:
aria-label="Основная навигация" i18next/no-literal-string`; после
возврата на `t("primary")` — `pnpm lint` снова чистый (`✔ No problems
found!`, включая `steiger`).

## Манифест PWA

`web/public/manifest.webmanifest` — статический JSON, не файл кода;
next-intl не умеет (и не должен) генерировать его на лету для одной
жёсткой локали. Тексты (`name`/`short_name`) оставлены как есть.

**На будущее** (при добавлении второго языка): манифест — один файл на всё
приложение, без сегмента локали в пути, поэтому со вторым языком его
придётся либо генерировать per-locale через `app/manifest.ts`
(динамический route handler Next.js, читающий текущую локаль и
возвращающий `MetadataRoute.Manifest`), либо смириться с тем, что имя/
описание PWA всегда на языке по умолчанию — статический файл в `public/`
для этого не подходит.

## Затронутые файлы (инфраструктура)

- `web/src/shared/config/i18n/locale.ts` — единственная локаль;
- `web/src/shared/config/i18n/request.ts` — конфиг next-intl
  (`getRequestConfig`), подключается плагином в `next.config.ts`;
- `web/src/shared/config/i18n/types.ts` — типизация `AppConfig`;
- `web/src/shared/config/i18n/messages/ru.json` — словарь;
- `web/src/shared/config/i18n/index.ts` + реэкспорт в
  `web/src/shared/config/index.ts` — публичное API сегмента (`steiger`
  требует импортировать `locale` через `@/shared/config`, не напрямую
  `@/shared/config/i18n`, — проверено: прямой импорт ловится правилом
  `fsd/no-public-api-sidestep`);
- `web/next.config.ts` — `createNextIntlPlugin("./src/shared/config/i18n/
  request.ts")`;
- `web/src/app/layout/providers.tsx` — `NextIntlClientProvider` без пропов
  (серверный компонент, локаль/сообщения берутся из `request.ts`
  автоматически);
- `web/src/app/layout/root-layout.tsx` — `generateMetadata` (async) вместо
  статического `export const metadata`, `<html lang={locale}>`.

## Побочные следствия

- `ScreenHeader` (`shared/ui/screen-header.tsx`) стал `"use client"` —
  раньше был серверным (ADR 0013), но дефолт `backLabel` теперь берётся
  через `useTranslations` (хук). Проброс `onBack` из настоящего Server
  Component (без `"use client"`) и раньше не работал бы для реальной
  кнопки «назад» (React не сериализует функции через границу RSC) — на
  практике вызывающая сторона всегда была клиентской, теперь это явно
  зафиксировано типом компонента, а не подразумевается.
- `BottomNav` стал асинхронным серверным компонентом (`getTranslations`)
  вместо синхронного — единственная причина, аналогично экранам-заглушкам
  `src/pages/*`.
