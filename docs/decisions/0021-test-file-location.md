# ADR 0021: Где лежат тест-файлы — рядом с кодом, не в `tests/`

## Контекст

Единственный тест в проекте сейчас — `web/src/shared/lib/access/
classify-access.test.ts`, рядом с `classify-access.ts`. Пользователь
предложил вынести тесты в отдельную папку `tests/` (зеркалирующую
структуру `src/`), но сам не был уверен, что это правильно — попросил
разобраться и решить.

## Варианты

1. **Co-location** (как сейчас) — `*.test.ts` рядом с файлом, который
   тестирует, внутри того же слайса/сегмента FSD.
2. **Отдельное дерево `tests/`**, зеркалирующее `src/` (например
   `tests/shared/lib/access/classify-access.test.ts`).

## Что говорят инструменты и методология

- **FSD** — официальный ответ авторов методологии (обсуждение
  `feature-sliced/documentation#435`, "Tests - Where to place?"):
  «TL;DR: Put them in segments next to the code that they are testing».
  Причина явно привязана к главному принципу FSD — низкой связности
  (low coupling): изменение одного аспекта проекта должно происходить в
  одной маленькой подпапке, а не в одном файле на файл across all
  folders. Зеркальное дерево тестов означает, что перенос/удаление
  слайса требует находить и переносить его "двойника" в другом дереве —
  ровно то расползание, с которым FSD борется public API и границами
  слайсов. Рекомендация FSD — при необходимости группировать тесты
  внутри сегмента (`spec/` или `tests/` *внутри* слайса), не поверх всех
  слайсов.
- **Vitest** — инструмент осознанно нейтрален: «There's no single
  "right" way to organize your test files… Vitest will find them either
  way» (`vitest.dev/guide/learn/writing-tests`), паттерн `include` по
  умолчанию матчит оба варианта. Единственная рекомендация Vitest —
  быть последовательными в рамках проекта.
- **Next.js** — не даёт собственной рекомендации по расположению unit-
  тестов вне `app/`/`pages/` роутинга; ничего не меняет для этого
  решения.

## Решение

**Оставляем co-location** — тесты остаются рядом с тестируемым файлом
внутри слайса/сегмента (`classify-access.test.ts` рядом с
`classify-access.ts` в `shared/lib/access/`), новые тесты — по тому же
принципу. Отдельная папка `tests/` не заводится.

Обоснование для конкретно этого проекта:
- Проект уже строго следует FSD (`steiger` в `pnpm lint`) — это прямая
  рекомендация авторов методологии, а не общий совет "как в экосистеме
  принято вообще".
- Публичный API слайса (`index.ts`) и так документирует, что видно
  снаружи; тест рядом с реализацией может (и должен, где полезно) видеть
  внутренности сегмента, не только re-export из `index.ts` — отдельное
  дерево `tests/` это не меняет и не даёт взамен ничего проекту.
- Перенос/удаление слайса (например, этим же изменением — `/styleguide`
  и `/components`) при co-location — это `rm -rf` одной папки. При
  зеркальном дереве пришлось бы отдельно искать и чистить тесты в другом
  месте — источник расхождения, которого не было в этом репозитории, но
  которое стоило бы избежать заранее.
- Единственный довод в пользу отдельной `tests/` — «tests как
  документация верхнего уровня, видно всё одним деревом» — не
  перевешивает: при одном тест-файле в проекте сканировать дерево
  незачем, а если тестов станет много, `grep`/IDE-поиск по `*.test.ts`
  решает эту задачу без отдельной папки.

## Последствия

- Конфигурация Vitest не меняется (`include` уже видит co-located
  файлы).
- Правило — в `CLAUDE.md` не выносится отдельным пунктом (там уже
  сказано, где лежит тест `classifyAccess`); при появлении новых слайсов
  с тестами — тот же принцип: `*.test.ts` рядом с файлом, который
  тестирует.
