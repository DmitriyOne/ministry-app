# ADR 0016: v1 — доступ только с iPhone в Safari

## Контекст

Разворот требований от пользователя поверх ADR 0015. Для первого релиза
(v1) сужаем аудиторию до одного, надёжно поддерживаемого пути — iPhone,
браузер Safari — и убираем экраны, которых пока нет (404/500, полноценный
`/day`). Реальное приложение по-прежнему не видно никому: после всех
проверок пользователь видит Coming soon, а `/day` остаётся в коде для
следующего этапа.

Итоговая модель, шесть состояний:

| Кто открывает | Экран |
|---|---|
| Десктоп, ноутбук, любой планшет (включая iPad, в т.ч. с UA macOS) | «Доступно только с телефона» |
| Любой Android | «Приложение доступно только для iOS» |
| iPhone, не Safari (Chrome/Firefox/Edge/Opera/Яндекс на iOS, встроенные браузеры мессенджеров) | «Доступно только в Safari» |
| iPhone, Safari, обычный браузер | экран установки (bottom sheet с инструкцией) |
| iPhone, Safari, установлено (standalone) | Coming soon |
| `DEV_MODE=true` | всё открыто, ничего из перечисленного не действует, `/day` доступен напрямую |

## Архитектура: два независимых шага

CSS не умеет отличить Safari от Chrome или iPhone от Android — оба живут
в одном и том же `pointer: coarse`/`hover: none`/маленьком экране. Раз
задача сузилась до «только один конкретный браузер на одной конкретной
платформе», единственный надёжный сигнал — `User-Agent`, а его видит
только сервер. Поэтому:

### 1. Сервер — `web/proxy.ts` + `classifyAccess`

`web/src/shared/lib/access/classify-access.ts` — чистая функция
`classifyAccess(userAgent: string): "desktop" | "android" |
"ios-not-safari" | "ios-safari"`, без побочных эффектов, поэтому легко
тестируется (`classify-access.test.ts`, 23 кейса — vitest, см. ниже).
`web/proxy.ts` классифицирует каждый запрос и, если это не
`"ios-safari"`, делает `NextResponse.rewrite` на соответствующую
статическую страницу-заглушку (`/access/desktop`, `/access/android`,
`/access/ios-browser`) — **не `redirect`**: URL в адресной строке не
меняется, а раз это `rewrite`, а не логика в самом layout, сами
заглушки остаются обычными статическими страницами (`pnpm build`
показывает их `○`), и общий layout не становится динамическим.

Порядок проверки внутри `classifyAccess` (см. подробные комментарии в
файле): Android по токену `Android` → iPad (в т.ч. по токену `iPad` —
основной случай, iPadOS 13+, разобран ниже, в default-ветку) → iPhone:
сначала известные не-Safari браузеры и встроенные браузеры приложений,
затем страховочный признак (WebKit-UA без токена `Safari/` — так себя
метят многие ещё не занесённые в список встроенные браузеры) → всё
остальное считается desktop.

**Список не-Safari токенов** (найден через публичные источники UA-строк,
не исчерпывающий по природе — новые браузеры и приложения появляются
постоянно):

- Браузеры на движке iOS WebKit со своим брендом: `CriOS` (Chrome),
  `FxiOS` (Firefox), `EdgiOS` (Edge), `OPiOS`/`OPT/` (Opera),
  `YaBrowser`/`YaApp` (Яндекс), `GSA/` (приложение Google), `DuckDuckGo`.
- Встроенные браузеры (WebView) приложений: `FBAN`/`FBAV` (Facebook),
  `Instagram`, `Line/`, `Twitter`, `VKClient`/`VK/`, `WhatsApp`,
  `Snapchat`, `TikTok`/`BytedanceWebview`, `MicroMessenger` (WeChat),
  `Pinterest`, `LinkedInApp`.
- Страховка: iPhone-UA без токена `Safari/` вообще — большинство
  WebView-браузеров опускают этот токен (настоящий Safari и даже
  CriOS/FxiOS и т.п. его сохраняют по историческим причинам совместимости).

**Как обновлять список**: добавить строку в `NON_SAFARI_IOS_BROWSER_TOKENS`
или `IN_APP_BROWSER_TOKENS` в `classify-access.ts` и тест-кейс в
`classify-access.test.ts` — обе константы и оба списка тестов читаются
сверху вниз, добавление не требует менять остальную логику.

**Матчер `proxy.ts`** исключает статику
(`_next/static`/`_next/image`/`favicon.ico`/`manifest.webmanifest`/
`icons`), сервис-воркер (`serwist`) и папку с плейсхолдер-картинками
установки (`install` — `public/install/ios/*.png`, next/image раздаёт их
напрямую, классификация им не нужна). `/styleguide` и `/components`
исключены **внутри** обработчика (не в матчере — матчер не может
обращаться к `DEV_MODE`) и пропускаются как есть независимо от
устройства — они гейтятся своей собственной проверкой `DEV_MODE`
(`notFound()`), не должны получать заглушку "только iPhone" (разработчик
должен видеть их с десктопа). При `DEV_MODE=true` `proxy` вообще не
классифицирует — пропускает всё (`NextResponse.next()`), см. код.

### 2. Клиент — CSS `display-mode`

За `proxy.ts` доходит только подтверждённый iPhone в Safari. Остаётся
один вопрос — установлено приложение или нет — и его решает тот же
принцип, что в ADR 0015: `display-mode: standalone`/`fullscreen`
переключает `.app-shell` (Coming soon либо `/day`, зависит от
`LAUNCH_MODE`, см. ниже) и `.install-shield` (экран установки). Пороги
по `pointer`/`hover`/короткой стороне экрана из ADR 0015 **убраны** —
они были нужны, чтобы отличать телефон от планшета самостоятельно;
теперь это уже сделал сервер, дублировать незачем (мёртвый код).
Реализация — `web/src/app/layout/access-gate.tsx` (компонент
`AccessGate`, подключён только для маршрутов внутри `app/(guarded)/`)
и упрощённое правило в `globals.css`.

### 3. `web/src/shared/lib/device/` — удалено целиком

`isPhone()`/`useIsPhone()`, `usePhoneOs()`, `useInstallPrompt()`,
`isStandalone()`/`useIsStandalone()`, `PHONE_MAX_SHORT_SIDE` — всё это
были JS-хелперы под старую модель (телефон против не-телефона на клиенте,
подсказка ОС для Android/iOS-инструкции, Android install-prompt). В v1
ничего из этого не используется: экран установки всегда точно знает, что
он на iPhone Safari (сервер уже проверил), Android заблокирован раньше,
до JS. Правило проекта «оставь только то, что реально используется» —
удалено целиком, не оставлено под будущее: если понадобится снова, его
проще написать заново под актуальные требования, чем разбираться, что из
старого кода ещё имеет смысл.

## Компромисс: iPhone с «Запросить настольный сайт»

Safari на iPhone при включённой настройке «Запросить настольный сайт»
подменяет `User-Agent` на полноценную строку Macintosh — неотличима от
настоящего Mac по построению. Такой пользователь попадёт в «Доступно
только с телефона», даже будучи на iPhone. Осознанный, задокументированный
компромисс (как и iPad-под-Mac в ADR 0015) — единственная альтернатива,
проверка через `navigator.maxTouchPoints`/`ontouchstart` на клиенте, была
бы возможна только после первого рендера (не на сервере, `proxy.ts` не
видит DOM) и всё равно не отличила бы iPad от iPhone в этом режиме.
Зафиксировано тестом (`iphoneRequestDesktopSite` в
`classify-access.test.ts`) — поведение ожидаемое, не баг.

## iPad — всегда «desktop»

iPadOS с версии 13 (2019) маскируется под macOS в `User-Agent` по
умолчанию, без токена `iPad` вовсе — такой UA идентичен обычному Mac
Safari и уже отсекается default-веткой `classifyAccess`. Явная проверка
на буквальный токен `iPad` в начале функции — для UA, где он всё же есть
(старые версии iPadOS, нестандартные браузеры) — не полагается только на
то, что default-ветка случайно её ловит.

## Почему Android заблокирован

Не техническое ограничение — решение объёма v1: экран установки
рассчитан на один путь (Safari → «Поделиться» → «На экран «Домой»»), а у
Android другой процесс (`beforeinstallprompt`, разные браузеры с разной
поддержкой). Раньше (ADR 0015) в проекте уже был `useInstallPrompt()`,
ловящий `beforeinstallprompt` для системной кнопки «Установить» на
Android — он полностью удалён вместе с остальным `shared/lib/device/`
(см. выше), а не оставлен неиспользуемым. Когда Android войдёт в объём,
писать эту часть заново разумнее, чем размораживать код, ни разу не
проверенный в текущей архитектуре.

## Экран установки: bottom sheet

Макет требует нижнюю панель с ручкой, свайпом вниз (порог ~90px),
закрытием по фону/Esc, запертым фокусом и каруселью из 4 шагов.

**Компонент — `shadcn` `sheet` (реестр `aria-nova`), не `drawer`.**
`pnpm dlx shadcn@latest view @shadcn/drawer` показал компонент на
`@base-ui/react` — второй primitives-библиотеке в проекте вдобавок к
`react-aria-components`, которую ADR 0012/0013 уже сознательно исключили
(«не `@base-ui/react`»). `sheet` в том же реестре построен на
`react-aria-components` (`ModalOverlay`/`Modal`/`Dialog`) — совпадает со
стеком, который уже использует `shared/ui/button.tsx`, `field.tsx`,
`item.tsx` и т.д. Взят `sheet`, адаптирован под стиль проекта
(стрелочные функции, именованные типы, `cn` из `@/shared/lib/cn`, свой
`CloseIcon` вместо `lucide-react`).

**Свайп-закрытие — добавлено поверх, готового в комплекте нет** (ровно
тот случай, для которого в задаче было явное разрешение: «если свайпа из
коробки нет — добавь его поверх»). `react-aria-components` не даёт
drag-жестов. Реализация — `web/src/pages/install-app/ui/install-sheet.tsx`:
`onPointerDown`/`onPointerMove`/`onPointerUp` на отдельной ручке сверху
панели (`data-slot="sheet-drag-handle"`), `translateY` через inline
`style`, порог закрытия `CLOSE_DRAG_THRESHOLD = 90`. `shared/ui/sheet.tsx`
получил проброс `style`/`onPointer*` до самого позиционированного
элемента панели (`ModalPrimitive`) — без этого свайп двигал бы только
внутреннее содержимое, а не саму панель. Закрытие по фону и `Esc`, запертый
фокус — уже есть в react-aria `ModalOverlay`/`Modal` (`isDismissable`),
ничего не добавлялось.

**Карусель** (`install-carousel.tsx`) — свой стейт `step` (0–3), не
компонент из реестра: четыре шага с номером/текстом/картинкой, стрелки
`ChevronLeftIcon`/`ChevronRightIcon` (новые файлы в `shared/ui/icons/`,
второй иконки не было), `isDisabled` на краях, точки-индикаторы —
активная точка `h-2 w-5` (20px), остальные `h-2 w-2` (8px), по клику —
переход к шагу (`role="tab"`/`aria-selected`, контейнер `role="tablist"`).

## Плейсхолдеры скриншотов

`web/public/install/ios/step-1.png` … `step-4.png` — нейтральный
тёплый серый фон (375×667, без текста), сгенерированы `imagemagick`.
Выводятся через `next/image` (`fill` + `sizes="343px"` + `object-cover`
в фиксированном контейнере `h-48`, не исходные 667px высоты — иначе
панель на маленьком экране (390×844) занимает почти весь вьюпорт, не
оставляя видимой области фона для теста «закрыть по тапу на фон»,
обнаружено живой проверкой ниже). `alt` — из словаря
(`screens.installApp.sheet.steps.step*.imageAlt`), описывает, что должно
быть на настоящем скриншоте. Замена на реальные скриншоты пользователя —
просто перезапись файлов по тем же путям, без правки кода.

## Уборка страниц

Удалены: `web/app/{login,cal,month,year,status,over}`,
`web/src/pages/{login,cal,month,year,status,over}`, их ключи словаря
(`screens.login` и т.д.). 404/500 сознательно не делались — следующий
этап.

**`widgets/bottom-nav` удалён целиком** (не просто убран из layout) —
вёл на удаляемые страницы, второго использования не было (сам виджет был
пустым каркасом, «Empty scaffold until the screens it links to exist»).
Вернётся вместе с реальными экранами навигации.

**`/styleguide` и `/components`** — раньше щит на них не действовал
через `PhoneShieldBypass` (невидимый маркер + `:has()` в CSS, ADR 0015).
Теперь щит для НЕ-iPhone-Safari работает на сервере (`proxy.ts`), CSS
`:has()`-обход ему не поможет (запрос до всякого CSS уже переписан на
другую страницу) — `PhoneShieldBypass` удалён, и обе страницы вместо
этого сами проверяют `env.DEV_MODE` и вызывают `notFound()`
(`next/navigation`), если `DEV_MODE` не включён — обычный Next.js
паттерн вместо CSS-трюка, ортогонален устройству: разработчик на
десктопе с `DEV_MODE=true` видит их, кто угодно другой без `DEV_MODE` —
получает настоящий 404, независимо от того, iPhone это или нет.

## `/` → `/day`, `/day` → Coming soon (пока не решили иначе)

`app/(guarded)/page.tsx` — тот же `redirect("/day")`, что и раньше,
просто перемещён в новую route group. `app/(guarded)/layout.tsx`
подключает `AccessGate`; маршруты **вне** этой группы (`/styleguide`,
`/components`, `/access/*`) её не получают — рендерятся сразу под
истинным корнем (`app/layout.tsx` → упрощённый `RootLayout`, теперь
только `html`/`body`/провайдеры, без какой-либо логики доступа).

**`LAUNCH_MODE`** (`web/src/app/config/launch-mode.ts`) — единственное
место переключения `"coming-soon" | "app"`. `AccessGate` подставляет
`ComingSoonScreen` вместо `children` (реального `/day`), пока значение
`"coming-soon"`; смена на `"app"` — одна строка, без затрагивания
`proxy.ts`, CSS или самого `/day`. `DEV_MODE=true` обходит `AccessGate`
целиком (`if (env.DEV_MODE) return children`) — `/day` виден напрямую,
что бы ни стояло в `LAUNCH_MODE`.

## Тесты классификатора

`web/vitest.config.mts` + `pnpm test` (корень и `web/`) —
`classify-access.test.ts`, 23 кейса, включая обе строки из этого ADR
(iPad-под-Mac, iPhone с настольным сайтом) и по одному случаю на каждый

## Живая проверка

`pnpm lint`, `pnpm typecheck`, `pnpm test` (23/23), `pnpm build` — чисто.
Таблица маршрутов сборки: `/access/desktop`, `/access/android`,
`/access/ios-browser`, `/styleguide`, `/components` — все `○` (static);
`/day` — `ƒ` (Supabase-статус, не связано с этой задачей); `proxy.ts` —
`ƒ Proxy (Middleware)`, ожидаемо.

Проверено в браузере (Playwright MCP, `next dev -p 3106`, подмена
`User-Agent`/`isMobile`/`hasTouch` через `browser_run_code_unsafe`, по
образцу ADR 0015):

- Десктоп Chrome (1440×900) → «Доступно только с телефона».
- iPad-под-Mac UA (820×1180, touch) → «Доступно только с телефона».
- Android Chrome (390×844, touch) → «Приложение доступно только для iOS».
- iPhone Chrome/CriOS (390×844, touch) → «Доступно только в Safari».
- iPhone Instagram webview (390×844, touch) → «Доступно только в Safari»
  + кнопка «Скопировать ссылку» (Clipboard API доступен в тестовом
  браузере) — клик переключает текст на «Ссылка скопирована».
- iPhone Safari (390×844, touch) → экран установки; проверено:
  открытие панели по кнопке «Как установить», навигация стрелками
  «Назад»/«Далее» (отключены на краях — `aria-disabled` на первом/
  последнем шаге), переход по точкам-индикаторам (клик на 4-ю точку →
  шаг 4/4), закрытие по клику на фон, закрытие по `Escape`, свайп вниз
  на ручке — **до порога (30px) панель остаётся открытой, после (140px)
  закрывается** (оба варианта проверены раздельно, до и после фикса
  адресации элемента ручки — см. ниже).
- `DEV_MODE=true`: `/day` (даже с Chrome-UA на десктопе), `/styleguide`,
  `/components` — все открываются напрямую, без заглушек.
- `DEV_MODE=false`: `/styleguide` и `/components` — 404.

**Coming soon — не эмулируется вживую**, той же причине, что и в ADR
0015: Chromium (в т.ч. версия под управлением Playwright,
153.0.8010.53) не поддерживает переопределение `display-mode` через
CDP `Emulation.setEmulatedMedia` (перепроверено для этой задачи —
идентичный вызов с `prefers-color-scheme` работает, с `display-mode` нет
эффекта). Экран визуально подтверждён другим способом — временный CSS
(`display:contents!important` на `.app-shell`, `display:none!important`
на `.install-shield`, инжектирован в уже загруженную страницу через
`page.addStyleTag`, снимок сделан и это явно помечено как ручной
оверрайд видимости, не эмуляция реального `display-mode`): заголовок,
текст, форма `PillForm` — заполнение email, отправка, переключение на
текст успеха — всё проверено и работает.

**Найдено и исправлено по ходу живой проверки**: заглушки скриншотов
375×667 без ограничения по высоте контейнера растягивали панель почти на
весь экран 390×844 — «свайп-закрытие по фону» и «клик по фону» физически
не на что было кликнуть (весь экран занимала сама панель). Именно так
обнаружилась необходимость ограничить контейнер картинки высотой
(`h-48` + `object-cover`, см. раздел «Плейсхолдеры скриншотов» выше) —
без живой проверки на реальном размере экрана эта проблема осталась бы
незамеченной до прихода настоящих скриншотов.

Скриншоты — `.playwright-mcp/v1-*.png` в основном репозитории.

## Обновление: чёрный список меток браузеров заменён на белый список формы Safari

Живая проверка на настоящем iPhone показала, что чёрный список
(`NON_SAFARI_IOS_BROWSER_TOKENS`/`IN_APP_BROWSER_TOKENS`, описанный
выше) пропускает Brave и DuckDuckGo как Safari:

- Brave дописывает `" Brave"` в самый конец строки — токена `Brave` в
  списке не было.
- Текущая версия DuckDuckGo метит себя `Ddg/26.6`, а в списке значился
  `DuckDuckGo` (старая форма UA) — токена `Ddg/` не было.

Патч «добавить `Brave` и `Ddg/` в список» решил бы именно эти два
случая и ничего больше — завтрашний браузер с ещё одной меткой прошёл
бы точно так же. Природа чёрного списка такая: он может перечислить
только то, что кто-то уже когда-то посмотрел и вписал.

### Решение — одна проверка вместо перечисления

`classifyAccess` для iPhone задаёт ровно один вопрос — «эта строка
побайтово совпадает с формой настоящего Safari» — и всё, что не
совпадает, получает `ios-not-safari`, без выяснения, какой именно это
браузер. Оба списка токенов (`NON_SAFARI_IOS_BROWSER_TOKENS`,
`IN_APP_BROWSER_TOKENS`) и страховочный признак «нет токена `Safari/`»
**удалены из кода целиком**, не оставлены второй линией — по итоговой
договорённости с пользователем: раз ни одному экрану не важно, какой
конкретно не-Safari браузер обратился (у всех один и тот же экран
«Safari only, for now»), перечисление конкретных браузеров не несёт
пользы, только риск устареть. `classifyAccess` теперь:

```ts
if (ua.includes("iPhone")) {
  return IOS_SAFARI_UA_PATTERN.test(ua) ? "ios-safari" : "ios-not-safari";
}
```

Различение Android/iPad/десктопа (какую из трёх заглушек показать)
осталось прежним — это отдельный вопрос, чёрных списков там никогда не
было.

**Форма настоящего Safari** (`IOS_SAFARI_UA_PATTERN`,
`web/src/shared/lib/access/classify-access.ts`), проверена на живых
замерах пользователя (iPhone, iOS 18.7/26.6.x):

```
Mozilla/5.0 (iPhone; CPU iPhone OS 18_7 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/26.6.1 Mobile/15E148 Safari/604.1
```

Регулярное выражение требует совпадения **целиком** (`^...$`), а не
отсутствия «плохих» слов — именно это отличает белый список от чёрного:

1. `Version/` должен идти сразу после блока WebKit/KHTML. Любой браузер
   на WebKit со своим брендом (Chrome, Edge, Opera, Яндекс, Brave,
   DuckDuckGo) вставляет собственный токен (`XxxiOS/…`, `Ddg/…`) —
   Chrome вообще убирает `Version/`, Edge/Opera/Яндекс вставляют свой
   токен **перед** `Version/`, что рвёт непосредственное соседство,
   которое требует шаблон.
2. Строка должна **заканчиваться** на `Safari/604.1` — ничего после.
   Именно здесь спотыкаются Brave и DuckDuckGo: остальная часть их UA
   побайтово совпадает с настоящим Safari, выдаёт их только хвост
   (`" Brave"`, `" Ddg/26.6"`).
3. Финальная сборка должна быть `604.1`, не любая другая — Firefox на
   iOS (`FxiOS`) заканчивает строку на `Safari/605.1.15`, что тоже не
   проходит якорь конца строки.

Обойти любой из трёх пунктов по одному — легко; обойти все три сразу
означает быть побайтово идентичным настоящему Safari, и в этот момент
различить уже нечем ни этим методом, ни каким-либо другим (см. ниже про
`SFSafariViewController`) — считать такую строку Safari корректно, не
ложное срабатывание.

### Что сознательно перестали различать

Раньше «Доступно только в Safari» мог (хотя нигде в коде это не
использовалось для решения, что показать) быть привязан к конкретному
токену — теперь неизвестно, какой именно браузер отклонён, только факт
отклонения. Если понадобится показывать разный текст для разных
браузеров (например, отдельная подсказка для Chrome с прямой ссылкой на
App Store для Safari) — это будет новая задача с новым устройством
хранения причины отказа, не восстановление списков.

`liveDuckDuckGo`, `liveChrome`, `liveFirefox`, `liveEdge`) — Safari

Safari — классификатор осознанно относит такой визит к `ios-safari`
(комментарий в тесте и коде это фиксирует явно, как и раньше). Именно
для этого случая на `/install` добавлена статическая подсказка «если
это предпросмотр в мессенджере — откройте страницу в самом Safari» —
не попытка распознать его на сервере (см. следующий пункт задачи, экран
установки), а признание, что распознать нельзя в принципе.

### Рассмотрен и отклонён `ua-parser-js`

Пользователь просил рассмотреть `ua-parser-js` вместо самодельной
проверки. Итог — не брать, по двум независимым причинам:

**Лицензия.** С версии 2.0 (2024) `ua-parser-js` — двойная лицензия
AGPLv3 (copyleft, «заразная» — требует открывать исходники любого ПО,
которое его использует как сетевой сервис) либо платная PRO-лицензия
($12 personal … $500 enterprise). MIT остался только на замороженной
ветке 1.x, которая не получает новых браузерных сигнатур. Смена вызвала
заметный протест сообщества (issue с сотнями комментариев, форки вроде
`my-ua-parser` от участника Node.js TSC, миграции проектов на `bowser`).
Для закрытого коммерческого кода 2.x либо требует покупки лицензии,
либо не подходит вовсе — а именно 2.x получает актуальные обновления.

**Не решает саму задачу.** Даже отбросив лицензию: по данным из issues
самого проекта (`faisalman/ua-parser-js#750`, «Brave is faking UA to
hide identity», и `#788`, где мейнтейнер прямо пишет «we cannot detect
… Brave browser … as it relies on feature detection» о серверном
(Node.js) использовании) — определение Brave/DuckDuckGo на iOS
завязано на **feature detection в браузере** (`navigator.brave`,
`userAgentData` и т.п.), которых на сервере просто нет: у нас `proxy.ts`
видит только заголовок `User-Agent`, ничего больше. То есть библиотека
либо не различит Brave/Safari на сервере вообще (тот же провал, что и у
самодельного чёрного списка), либо потребовала бы протаскивать
клиентские сигналы на сервер отдельным каналом — заметно сложнее, чем
задача того стоит. Отдельно у DuckDuckGo была задокументированная
история ошибочного детекта (`#513`, мобильный DuckDuckGo определялся
как desktop).

Для одной конкретной задачи («это ровно iOS Safari или нет») строгое
совпадение с побайтовой формой — не только не хуже специализированной
библиотеки, но и не имеет ни одной из её слабостей (лицензия, отсутствие
серверного feature detection, необходимость пополнять базу браузеров,
которая нам не нужна — нас не интересует, какой конкретно браузер
пришёл).
