# ADR 0037: секретный ключ на доверенном сервере вместо общего секрета

Заменяет ADR 0035. Сужает запрет ADR 0006.

## Контекст

`public.join_waitlist` и `public.register_waitlist_push_subscription`
(ADR 0033 и миграции пуш-подписок) были `security definer` с `execute` для
`anon`. URL Supabase и publishable-ключ попадают в браузерный бандл, так
что любой мог вызвать обе функции напрямую через PostgREST, минуя серверное
действие Next.js и его rate limiter.

**Обход был воспроизведён**: пять запросов `POST /rest/v1/rpc/join_waitlist`
с одним publishable-ключом вставили пять строк и выдали пять
пуш-токенов примерно за секунду.

ADR 0035 закрыл это общим секретом, проверяемым внутри функций. Он
работал, но был лишним механизмом (см. ниже).

Предупреждения security advisor «RLS enabled, no policy» на обеих таблицах
остаются **намеренными**: включённый RLS без политик и отозванные grants —
это и есть защита таблиц (ADR 0033). Добавление политики их бы открыло,
поэтому «исправлять» эти предупреждения нельзя.

## Варианты

### A. Общий секрет внутри функций (ADR 0035)

Проверка секрета в функциях, `private`-схема, `set_rpc_secret`. Закрывает
обход, но добавляет хранилище секрета в базе, ручную настройку каждого
окружения и функцию-сеттер. Выбран первым из-за ошибочного прочтения ADR
0006: запрет секретного ключа в `web` был понят как запрет на любой
серверный код. На деле Supabase запрещает секретный ключ в **публичных
клиентах / фронтенд-коде**; Server Action Next.js — не публичный клиент, а
доверенный сервер. ADR 0006 писался до того, как у `web` появился
серверный путь записи, и говорил о браузере.

### B. Секретный ключ на доверенном сервере, `execute` только для `service_role` — выбрано

Сервер вызывает функции секретным ключом; у `anon`/`authenticated`
`execute` отозван. Никакого дополнительного секрета, схемы и сеттера.

### C. Перенести функции в скрытую схему

Совет Supabase держать `security definer`-функции в неэкспонируемой схеме
здесь не работает: PostgREST экспонирует только `public`
(`backend/supabase/config.toml`), поэтому функция в скрытой схеме
недоступна **никому**, включая доверенный сервер.

## Решение

Миграция `20261002200000_trusted_server_only_rpc.sql`:

- Обе функции остаются в `public` (по причине варианта C), сигнатуры без
  `p_secret`: `join_waitlist(p_email)` и
  `register_waitlist_push_subscription(p_token, p_endpoint, p_p256dh,
  p_auth)`. Тела не менялись, кроме снятой проверки секрета; сохранён
  `set search_path = ''`.
- Обе стали **`security invoker`**. `service_role` обходит RLS и уже имеет
  grants на таблицы, так что привилегии владельца ему не нужны. Это
  следует правилу «не использовать `security definer`, чтобы замазать
  ошибку прав», а предупреждение advisor «Public Can Execute SECURITY
  DEFINER Function» исчезает потому, что условие действительно перестало
  выполняться, а не потому, что его заглушили.
- `revoke all ... from public, anon, authenticated; grant execute ... to
  service_role`.
- Удалены `public.set_rpc_secret`, `private.rpc_secret_matches`,
  `private.rpc_secrets` и сама схема `private` (в ней ничего больше не
  было). Удалены `backend/scripts/set-rpc-secret.mjs`, скрипт
  `db:set-secret` и `RPC_SHARED_SECRET`.
- Веб: `web/src/shared/api/supabase/admin.ts` —
  `createAdminSupabaseClient` (`import "server-only"`, `supabase-js`, не
  `@supabase/ssr`: сессии нет; `persistSession`/`autoRefreshToken`/
  `detectSessionInUrl` выключены). `SUPABASE_SECRET_KEY` — серверный ключ
  `env.ts`, никогда не `NEXT_PUBLIC_*`. Им пользуются
  `persistWaitlistSignup` и `registerPushSubscription`.

## Последствия

- Прямой вызов с одним publishable-ключом даёт `42501` / HTTP 401
  («permission denied for function join_waitlist»), строки не создаются.
  Проверено вручную и pgTAP-тестом под ролью `anon`.
- **Единственное, что теперь защищает эти записи, — rate limiter на
  уровне приложения.** База сама ничего не ограничивает, а `anon` до
  функций не дотягивается вообще. Ошибка в серверном действии — это теперь
  ошибка с полными правами на базу за спиной: клиент обходит RLS, и база
  не перепроверит вызов. Любой код, работающий через
  `createAdminSupabaseClient`, сам отвечает за авторизацию.
- Клиент нельзя реэкспортировать туда, куда может дотянуться Client
  Component; новые места его использования — только с отдельным ADR.
- Утечка `SUPABASE_SECRET_KEY` теперь означает полный доступ к базе, а не
  к двум функциям (как было с общим секретом). Ключ задаётся для каждого
  окружения отдельно (`supabase status` локально, Dashboard → API Keys в
  облаке) и проверяется на отсутствие в клиентских чанках сборки.
- Предупреждения «RLS enabled, no policy» не исправлять (см. Контекст).
- Эта миграция — результат слияния двух. Сначала была отдельная миграция
  общего секрета ADR 0035, `20261002200000_rpc_shared_secret.sql`, затем
  отдельная миграция, снимавшая его,
  `20261002220000_secret_key_instead_of_shared_secret.sql`. Обе склеены в
  одну, `20261002200000_trusted_server_only_rpc.sql`, **до того как любая
  из них покинула машину разработчика**: в git эти файлы не попадали
  (они и сейчас неотслеживаемые), в удалённый репозиторий — тем более.
  Применялись ли они к облачной базе, записей нет, а `db:push`
  выполняется вручную (см. «Деплой миграций» в `CLAUDE.md`). Переписывать
  неопубликованную историю безопасно, а держать в ней миграцию, которая
  вводит механизм и сразу его убирает, незачем. Теперь ни один файл в
  `backend/supabase/migrations/` не упоминает общий секрет.
