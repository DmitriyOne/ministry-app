# ADR 0034: публичный API сегмента не должен смешивать среды выполнения

> **Обновление: список клиентов в `shared/api` вырос, а граница стала
> тоньше.** Раздел «Решение» говорит, что `shared/api` содержит только
> `client.ts`, `server.ts` и `database.types.ts`, а `index.ts` экспортирует
> два клиента. Теперь там есть и `supabase/admin.ts`
> (`createAdminSupabaseClient`, секретный ключ, ADR 0037), и `index.ts`
> экспортирует все три клиента.
>
> Напряжение с правилом этого ADR, названное прямо. Правило — про среды
> выполнения: публичный API сегмента не должен смешивать их. Баррель
> `shared/api` теперь именно смешивает: браузерный клиент и два
> серверных (`server.ts`, `admin.ts`) в одном `index.ts`. Смягчает одно:
> оба серверных файла начинаются с `import "server-only"`, поэтому
> клиентский импорт любого из них — громкая ошибка сборки, а не тихая
> утечка (секретный ключ при этом не попадёт в браузерный бандл, потому
> что до этого сборка не дойдёт). Но это тот же вид мины, ради снятия
> которой писался ADR: следующий, кто возьмёт `createBrowserSupabaseClient`
> из `@/shared/api` в клиентском компоненте, получит упавшую сборку с
> сообщением про `server-only`, а не про свою ошибку. Это осознанно
> принятая ловушка, а не недосмотр: вариант A (отдельный сегмент для
> серверных клиентов) уже пробовали и отменили, потому что клиенты
> разных сред должны лежать рядом. Ограничение ADR 0037 — не
> реэкспортировать `admin.ts` туда, куда дотянется Client Component, —
> этим баррелем формально нарушено; удерживает его только `server-only`.

## Контекст

Клиентский компонент `pages/day/ui/DayPage.tsx` импортировал одну
константу с URL из `@/shared/api`. Публичный API этого сегмента
(`index.ts`) заодно реэкспортировал серверный Supabase-клиент
(`server.ts`), а тот импортирует `next/headers`. Turbopack, разворачивая
баррель для клиентского бандла, втянул в браузер и `server.ts`, и сборка
упала с ошибкой «You're importing a component that needs next/headers».

Корень проблемы не в одной константе, а в самой форме барреля: один
`index.ts` отдаёт и то, что безопасно в браузере, и то, что работает
только на сервере. Любой клиентский импорт из такого барреля — мина.

## Варианты

### A. Отдельный сегмент `shared/api-server` для серверного клиента

Серверный клиент уезжает в свой сегмент, баррель `shared/api` остаётся
«чистым». Попробовано. Линтер (`steiger`) это устраивало, но два файла,
которые принадлежат друг другу (браузерный и серверный Supabase-клиент),
оказались в разных сегментах, хотя в каждом примере из документации
Supabase они лежат рядом. Отменено.

### B. Оставить всё в `shared/api`, а константы не импортировать оттуда

Держится на дисциплине: следующий, кто возьмёт константу из `@/shared/api`
в клиентском компоненте, снова сломает сборку. Не решает причину.

### C. Константы — в `config`, клиенты — в `api`, `import "server-only"` в серверном клиенте

Константы не имеют среды выполнения, поэтому им место в `config`; клиенты
её имеют, поэтому остаются в `api`. Серверный файл помечен
`server-only`, и случайный импорт из клиентского кода ломает сборку с
понятным сообщением, а не с косвенным про `next/headers`.

## Решение

Вариант C. Общее правило, которое проект берёт из этого случая:
**публичный API сегмента не должен смешивать среды выполнения.**

Что сделано:

- `web/src/shared/api/` теперь содержит только Supabase-клиенты:
  `supabase/client.ts`, `supabase/server.ts`, `supabase/database.types.ts`;
  `index.ts` экспортирует оба клиента, как их и раскладывает документация
  Supabase — рядом друг с другом.
- `web/src/shared/api/supabase/server.ts` получил `import "server-only"`.
- Константы URL, жившие в `shared/api/supabase/routes.ts` и
  `shared/api/web/routes.ts`, переехали в один файл
  `web/src/shared/config/api-routes.ts` (`WEB_API_ROUTES`,
  `SB_API_ROUTES`) и экспортируются из публичного API `shared/config`.

## Последствия

- Клиентский код берёт URL-константы из `@/shared/config` и не затрагивает
  `@/shared/api`; серверный клиент не может попасть в браузерный бандл
  незаметно.
- Новые константы такого рода (пути, префиксы эндпоинтов) идут в
  `shared/config`, а не в `shared/api`.
- **Известный долг:** `shared/config` сам смешивает серверный по природе
  `env` с универсальными `locale`/`routes` — тот же запах. Проверки
  `typeof window === "undefined"` внутри `env.ts` существуют только из-за
  этого. Разделение оставлено на отдельное изменение.

## Обновление 2026-10-14: измерено, что уезжает в браузер через `shared/config`

Ревью релиза подняло гипотезу: баррель `@/shared/config` импортируют
около десятка клиентских файлов ради `routes`, а он реэкспортирует ещё и
`env` (схема `@t3-oss/env-nextjs` со **всеми** переменными, включая
серверные) и `route-policy`. ES-модули реэкспортируют жадно, так что всё
это должно оказываться в клиентском бандле.

Гипотеза проверена сборкой, а не рассуждением:

```
$ grep -rl "SUPABASE_SECRET_KEY\|WEB_PUSH_VAPID_PRIVATE_KEY" .next/static/chunks/
.next/static/chunks/2b10r0r_l9n37.js
$ grep -rl "deviceShield\|adminOnly" .next/static/chunks/
.next/static/chunks/37r898niful7q.js
$ grep -rl "sb_secret_" .next/static/
(пусто)
```

Что это значит и чего НЕ значит:

- **Утечки нет.** В браузер уезжают **имена** переменных из схемы и
  таблица маршрутных политик — то есть структура, а не значения.
  Секретного ключа в клиентской сборке нет; `createEnv` бросает при
  обращении к серверному ключу из браузера, и этот механизм работает.
  Содержимое `ROUTE_POLICY` секретом не является: оно выводится из
  поведения приложения за пару минут.
- **Цена есть, но она не измерена по отдельности.** Схема лежит в чанке
  на 150 КБ (41 КБ gzip), где рядом живёт zod, который в клиенте нужен и
  так — формы без него не работают. Отделить вклад барреля этим методом
  нельзя.

**Решение: ничего не меняем.** Лечение дороже болезни. Разорвать связь
можно двумя способами, и оба плохи: импортировать `@/shared/config/routes`
в обход `index.ts` — это ровно то, что запрещает правило публичного API
FSD, то есть обмен измеримых килобайт на размывание границы; либо разнести
`env` в отдельный сегмент — тогда правку получат все серверные файлы, а
ошибка «импортировали не тот сегмент» станет возможной там, где сейчас
невозможна.

Пересматривать, когда появится настоящий анализ бандла и станет видно
вклад каждого модуля. До тех пор это записанный, измеренный компромисс, а
не недосмотр.
