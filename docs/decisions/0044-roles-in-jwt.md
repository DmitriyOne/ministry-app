# ADR 0044: роль в JWT через `custom_access_token_hook`

Статус: принято, 2026-10-05.
Относится к v2. Продолжает ADR 0043 (профили и роли).

## Контекст

ADR 0043 завёл `public.user_roles` и закрыл её наглухо: RLS включён,
политик нет, grants у `anon` и `authenticated` отозваны. Значит роль
нельзя узнать запросом из приложения — и это намеренно. Остаётся
единственный разумный канал: положить роль в сам токен.

Фронтенду роль нужна в трёх местах: `proxy.ts` (решение о доступе),
серверные компоненты (что показывать) и клиент (`/profile` выводит
название роли).

## Варианты

### A. Запрашивать роль из базы на каждый запрос

Потребовало бы политики на `user_roles` или RPC-обёртки. Плюс сетевой
вызов на каждую навигацию, включая `proxy.ts`, который выполняется до
рендера.

### B. Роль в JWT через `custom_access_token_hook` — выбрано

Штатный механизм Supabase. Роль приезжает в access-токене, читается
локально, запросов к базе не требует вообще.

### C. Роль в `app_metadata` через Admin API

Работает без хука, но значение проставляется вручную при создании
человека и живёт отдельно от таблицы — два источника правды, которые
обязательно разойдутся.

## Решение

### Хук

```sql
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb language plpgsql stable security definer set search_path = '';

grant usage on schema public to supabase_auth_admin;
grant execute on function public.custom_access_token_hook(jsonb) to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook(jsonb)
  from public, anon, authenticated;
```

`execute` отозван у `public`, `anon` и `authenticated`: функция по
запросу возвращает роль **любого** человека, и право её выполнить было
бы способом прочитать `user_roles` в обход отсутствующих у неё политик.

**Человек без строки в `user_roles` должен входить.** Если строку
удалили руками, хук возвращает claims нетронутыми, а не падает: иначе
правка таблицы в Studio лишала бы человека входа. Роль по умолчанию
подставляет фронтенд (`shared/lib/auth`, `DEFAULT_APP_ROLE = "user"` —
наименее привилегированная). Покрыто pgTAP-тестом.

### Грант `supabase_auth_admin` на `user_roles` избыточен и оставлен сознательно

Миграция выдаёт `grant select on public.user_roles to
supabase_auth_admin`, как в примере Supabase. **Хуку он не нужен.**
Функция объявлена `security definer` и принадлежит `postgres`, поэтому
её тело читает таблицу от имени владельца, к которому не применяются ни
гранты, ни RLS.

Проверено, а не предположено: грант отозван, выполнен настоящий вход
паролем через Auth API — claim `user_role` всё равно приехал. Повторено
трижды (грант есть → отозван → возвращён), результат одинаковый.

Грант всё же оставлен, потому что цена ошибки несимметрична. Если
владелец функции когда-нибудь окажется не владельцем таблицы — а
проверить это в облачном проекте миграция не может — хук поднимет
`insufficient_privilege`, GoTrue не сможет выпустить токен, и войти не
сможет **никто**. Лишний `select` для роли, которая и так администрирует
`auth.users`, стоит несравнимо дешевле. Комментарий в миграции говорит
именно это, а не пересказывает документацию.

### Без `role_permissions` и `authorize()`

Вторая половина примера Supabase — таблица разрешений и функция
`authorize(permission)` в RLS-политиках — не делается. При двух ролях и
отсутствии таблиц данных проверять `authorize('records.delete')` негде:
нет ни `records`, ни политики, которая бы её вызывала. Это слой без
единого потребителя.

Вернётся вместе с первыми таблицами служения — и тогда у решения будет
обоснование из настоящих политик, а не из примера в документации.

### Форма будущего помощника для политик — решена заранее

Вопрос «не сделать ли `authorize()`/`is_admin()`, чтобы не проверять
claim в каждой политике» разобран сейчас, пока контекст свежий, хотя
**код не пишется**: в проекте нет ни одной политики, смотрящей на роль
(`profiles` — по `auth.uid() = id`, `user_roles` — без политик), так что
у помощника было бы нуль вызывающих.

Когда появится первая таблица служения с ролевой политикой, помощник
делается так — по странице Supabase «RLS performance and best
practices»:

```sql
create schema if not exists private;

create or replace function private.is_admin()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.user_roles
    where user_id = (select auth.uid()) and role = 'admin'
  );
$$;

revoke execute on function private.is_admin() from public, anon;
grant usage on schema private to authenticated;
grant execute on function private.is_admin() to authenticated;
```

И вызывается **только так**:

```sql
using ( (select private.is_admin()) or (select auth.uid()) = user_id )
```

Три вещи, которые легко сделать неправильно, и каждая — по делу:

1. **Обёртка в `select` обязательна.** Без неё функция вызывается на
   **каждую строку**; `(select ...)` заставляет планировщик построить
   initPlan и вычислить один раз на запрос. Документация говорит это
   прямо и про `auth.jwt()`, и про `security definer`-функции. Работает
   только пока результат не зависит от данных строки — функция с
   аргументом-колонкой так обёрнута быть не может.
2. **Схема `private`, не `public`.** Функция в `public` с `execute` у
   `authenticated` вызываема через REST как RPC: PostgREST выставляет
   функции схемы `public`. Та же страница предупреждает: «Remember
   functions you use in RLS can be called from the API. Secure your
   functions in an alternate schema if their results would be a security
   leak». Для `is_admin()` утечка мала, но `authorize(permission)` дал
   бы любому перебрать матрицу прав своей роли.
3. **Читать роль из таблицы, а не из claim, если нужна свежесть.**
   Вариант через `auth.jwt() ->> 'user_role'` дешевле (без обращения к
   таблице), но наследует последствие этого ADR: роль в токене обновится
   только при следующем входе. Решать по месту; если выбран claim,
   приведение неизвестной строки к enum ловится как
   `invalid_text_representation`, а не `when others` — отсутствующий
   claim даёт `null`, а не исключение, и широкий `when others` проглотил
   бы и настоящую ошибку.

Мультироль при этом **не** предполагается: PK `user_roles` — `(user_id)`,
одна роль на человека, и claim в JWT — строка, а не массив (ADR 0043).
Переход на несколько ролей потребует менять и хук, и `hasRole`, и это
будет отдельное решение.

### `getClaims()`, а не `getUser()`

`getClaims()` проверяет подпись и срок действия токена локально.
`getUser()` на каждый вызов обращается к Auth-серверу и даёт
дополнительно ровно одно: обнаружение сессии, отозванной на другом
устройстве. В официальном примере middleware Supabase используется
`getClaims()`, и в документации прямо сказано, что для авторизации
запроса его достаточно.

При одном человеке на устройство разница в защите мала, а разница в
задержке — сетевой вызов на каждую навигацию, включая `proxy.ts` до
рендера.

**Оговорка, без которой это утверждение неверно.** «Проверяет локально»
справедливо только при **асимметричной** подписи токена. В исходниках
`@supabase/auth-js` 2.116 у `getClaims()` есть ветка:

```js
const signingKey = !header.alg || header.alg.startsWith('HS') || !header.kid || !webcrypto
  ? null : await this.fetchJwk(header.kid, ...);
// If symmetric algorithm or WebCrypto API is unavailable, fallback to getUser()
if (!signingKey) { const { error } = await this.getUser(token); ... }
```

То есть при симметричной подписи (HS256, легаси JWT-секрет) клиенту
нечем проверить подпись, и `getClaims()` **вызывает `getUser()`** — тот
самый сетевой запрос, которого мы избегали, на каждую навигацию.

Проверено на локальном стеке: токен приходит с заголовком
`{"alg":"ES256","kid":"..."}`, то есть Supabase CLI 2.117.0 по умолчанию
подписывает асимметрично, и проверка действительно локальная.

**Для облачного проекта это надо подтвердить отдельно** (Dashboard →
JWT Keys): если он остался на легаси-секрете HS256, обоснование этого
решения не действует — каждая навигация будет дёргать Auth-сервер, а
его недоступность будет мгновенно выбрасывать людей на `/login` (см.
последствия в ADR 0045). Лечится миграцией проекта на асимметричные
ключи, а не правкой кода.

### Гвард написан, но в v2 ничего не охраняет

`hasRole` (`shared/lib/auth`) покрыт юнит-тестами и используется ровно в
одном месте — `/profile` выводит название роли. Ни один маршрут по роли
не закрыт, `/admin` не создаётся. Так решил владелец: инфраструктура
готова, поверхность для неё появится вместе с администрированием.

`hasRole(claims, "user")` для администратора возвращает `false`
намеренно: иерархии прав в v2 нет (нет `role_permissions`), поэтому
проверка спрашивает про конкретную роль и получает ответ про неё же.
Зафиксировано тестом, чтобы «admin — надмножество user» не появилось
само собой.

### Ручные шаги, которые миграции не делают

Включение хука — **настройка проекта**, а не часть схемы:

- локально — `[auth.hook.custom_access_token]` в `config.toml`
  (`uri = "pg-functions://postgres/public/custom_access_token_hook"`);
- в облаке — Authentication → Hooks в дашборде.

Там же выключается регистрация (`enable_signup = false`, ADR 0043).

Две ловушки, обе проверены на живом стеке:

1. **Правка `config.toml` не подхватывается `supabase db reset`** —
   настройки Auth читаются при старте контейнеров. Нужен
   `pnpm db:stop && pnpm db:start`, иначе хук молча не включится, и
   отсутствие claim выглядит как дефект миграции.
2. **`enable_signup` в `config.toml` встречается дважды** — под `[auth]`
   и под `[auth.email]`. Выключать надо только первый. Второй — это
   выключатель самого способа входа: при `false` вход по паролю
   отвечает `email_provider_disabled`, «Email logins are disabled».
   Глобального достаточно: `POST /auth/v1/signup` отвечает
   `signup_disabled`.

## Последствия

- Роль читается бесплатно и локально, в том числе в `proxy.ts`.
- **Роль меняется только при следующем входе.** Правка `user_roles` в
  Studio не затрагивает уже выданные токены; при `jwt_expiry = 3600` до
  часа человек проработает со старой ролью, пока не обновит токен. Для
  двух ролей и выдачи прав вручную это приемлемо; первый же сценарий,
  где роль должна меняться на лету, потребует пересмотра решения.
- Хук выполняется на каждом выпуске токена, то есть и при обновлении
  сессии. Это один `select` по первичному ключу.
- Отказ хука означает невозможность выпустить токен — то есть
  невозможность войти. Поэтому единственная ветка, где он мог бы
  упасть (нет строки в `user_roles`), обработана явно.
- pgTAP проверяет права и возвращаемые claims, но **не** путь через
  GoTrue: включённость хука проверяется только живым входом. Это
  осознанный пробел в автотестах — в CI нет шага, который поднимал бы
  Auth и логинился.

## Обновление (2026-10-08): `/profile` — единственное место, где роль видна

Экран сделан: имя из `profiles` (запрос под сессией человека, политика
«read own profile»), роль — из claims через `hasRole`. Это и есть
обещанное единственное применение гварда в v2: ничего на роли не
ветвится, экран её просто называет — `User` или `Administrator`.

Экран сам проверяет `getSessionClaims()` и без сессии уходит на
`/login`, хотя до него без сессии не добраться: `proxy.ts` не пускает.
Строка стоит не из недоверия к гейту, а потому что экран, читающий
личность, не должен зависеть от того, что проверку выше не сломали.
Цена — одно сравнение; альтернатива — отрисованный профиль неизвестно
кого. Неудачное чтение `profiles` имя не показывает, но экран не роняет:
роль и выход — то, ради чего сюда приходят.

**Выход — форма с Server Action, без клиентского кода.** План намечал
`SignOutButton` с `onPress`, но `<form action={signOut}>` делает то же
самое и не требует `"use client"` вовсе — выход работает и до того, как
загрузится JavaScript. Сам `signOut` при ошибке всё равно уводит на
`/login`: оставить человека на экране профиля с ошибкой, которую он не
может исправить, хуже, чем отправить туда, где сессия проверяется
заново (а если она уцелела, гейт вернёт его на `/day`). `redirect()`
стоит **вне** `try/catch` — он работает броском `NEXT_REDIRECT`, и
`catch` вокруг него проглотил бы переход.

Чего я не проверил и проверить не могу: что после смены роли в Studio
экран покажет `Administrator` **только** после повторного входа. Это
следствие решения D4 (роль едет в токене), и увидеть его должен
владелец — для этого нужен живой вход с реальной сессией.

## Обновление (2026-10-08): роль наконец что-то решает — `/admin/users/new`

Выше было записано, что в v2 гвард не закрывает ни одного маршрута.
Это больше не так: владелец попросил экран создания пользователя, видимый
только админу. Регистрации в приложении нет (решение D1), аккаунты
выдаёт владелец — до сих пор руками в Studio, теперь формой.

**Проверок три, и они не дублируют друг друга — каждая закрывает своё.**

1. `proxy.ts` → `resolveGate`: путь в `ADMIN_PATHS`, роль берётся из тех
   же проверенных claims, что и наличие сессии, так что лишнего обращения
   к auth-серверу нет. Не админ с сессией уходит на `/profile`, а не на
   `/login`: он аутентифицирован, и `/login` вернул бы его обратно своим
   же правилом — получился бы цикл. Все четыре сочетания закреплены
   тестами.
2. **Server Action проверяет роль сама.** Это главное: Server Action —
   отдельная публичная ручка, доступная любому, кто умеет составить
   запрос, независимо от того, какие экраны ему открываются. Гейт экрана
   защищает экран; эта строка защищает таблицу аккаунтов.
3. Экран проверяет ещё раз перед отрисовкой — чтобы не показывать форму,
   которую читающий всё равно не смог бы отправить.

Ссылка на экран в `/profile` видна только админу, но это **оформление, а
не защита**: смысл в том, чтобы не предлагать дверь, которая захлопнется
перед носом.

**Как устроено создание.** `createAdminSupabaseClient` (единственный
клиент с секретным ключом, ADR 0037) вызывает
`auth.admin.createUser` с `email_confirm: true` — письма не уходит,
креды владелец передаёт лично, а без этого флага аккаунт создаётся, но
войти по нему нельзя. Имя едет в `user_metadata.display_name`, откуда
его читает триггер `handle_new_user` и пишет строку `profiles`. Роль
триггер всегда ставит наименьшую, поэтому админ получается **обновлением**
строки `user_roles`, не вторым insert'ом: строка на человека одна, и
второй вставкой был бы конфликт.

Если аккаунт создан, а повышение до админа не прошло, форма показывает
ошибку, а не успех, и называет адрес: аккаунт уже существует и войти по
нему можно, так что создавать второй не надо — надо дописать роль в
Studio.

**Пароль — те же правила, что на входе.** Схема переехала в
`shared/lib/auth/account-password.ts` и используется обеими формами.
Разойдись они — выдали бы аккаунт с паролем, который на экране входа
ввести нельзя; такое обнаруживается только в деле.

**Первый админ в проде делается не этим экраном** — его там ещё нет.
Порядок: создать пользователя в Supabase Studio (Authentication → Add
user, с подтверждённым адресом), триггер заведёт `profiles` и
`user_roles` с ролью `user`, затем в SQL Editor:

```sql
update public.user_roles set role = 'admin'
where user_id = (select id from auth.users where email = 'вы@jw.fenko.dev');
```

И обязательно **выйти и войти заново**: роль едет в токене, старый токен
о ней не знает. Дальше второго админа уже можно заводить формой.

## Обновление 2026-10-12: админское действие не верит токену

Ревью v2 (план `docs/superpowers/plans/2026-10-12-v2-review.md`) уточнило
границу «роль едет в токене».

Для **навигации** она остаётся как решено: гейт читает роль из токена,
без обращения к auth-серверу. Цена — окно до `jwt_expiry` (сейчас час), в
которое токен утверждает старое.

Для **создания аккаунта** этого мало, и это измерено, а не выведено. На
живой БД после бана:

| Чем проверяем | Ответ по уже выданному токену |
|---|---|
| `GET /auth/v1/user` (GoTrue) | **403** |
| `GET /rest/v1/profiles` (PostgREST) | **200** |
| `grant_type=refresh_token` | 400 `user_banned` |
| новый вход по паролю | 400 `user_banned` |

То есть бан немедленно закрывает продление и новый вход, но **уже
выданный access-токен продолжает работать против базы до `exp`**:
PostgREST проверяет только подпись и про баны не знает. Снятая роль
стареет так же.

Поэтому `features/create-user/api/create-user-action.ts` спрашивает два
вопроса, которых в токене нет:

1. `getUser()` — жива ли сессия. Единственный, кто знает про бан и про
   выход на другом устройстве, — auth-сервер. 401/403 — отказ; любая
   другая ошибка — недоступность, и её нельзя показывать как «вам
   нельзя» (ADR 0046).
2. `user_roles` админским клиентом — та ли ещё роль, что в токене.

Оба — на пути, который проходит один раз на выданный аккаунт. Правило,
которое из этого следует: **критичная мутация перечитывает источник
истины, навигация — нет.**
