# ADR 0044: роль в JWT через `custom_access_token_hook`

Статус: принято, 2026-10-05.
Относится к v2. Продолжает ADR 0043 (профили и роли).

## Контекст

ADR 0043 завёл `public.user_roles` и закрыл её наглухо: RLS включён,
политик нет, grants у `anon` и `authenticated` отозваны. Значит роль
нельзя узнать запросом из приложения — и это намеренно. Остаётся
единственный разумный канал: положить роль в сам токен.

Фронтенду роль нужна в трёх местах: `proxy.ts` (решение о доступе),
серверные компоненты (что показывать) и клиент (`/profile` выводит
название роли).

## Варианты

### A. Запрашивать роль из базы на каждый запрос

Потребовало бы политики на `user_roles` или RPC-обёртки. Плюс сетевой
вызов на каждую навигацию, включая `proxy.ts`, который выполняется до
рендера.

### B. Роль в JWT через `custom_access_token_hook` — выбрано

Штатный механизм Supabase. Роль приезжает в access-токене, читается
локально, запросов к базе не требует вообще.

### C. Роль в `app_metadata` через Admin API

Работает без хука, но значение проставляется вручную при создании
человека и живёт отдельно от таблицы — два источника правды, которые
обязательно разойдутся.

## Решение

### Хук

```sql
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb language plpgsql stable security definer set search_path = '';

grant usage on schema public to supabase_auth_admin;
grant execute on function public.custom_access_token_hook(jsonb) to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook(jsonb)
  from public, anon, authenticated;
```

`execute` отозван у `public`, `anon` и `authenticated`: функция по
запросу возвращает роль **любого** человека, и право её выполнить было
бы способом прочитать `user_roles` в обход отсутствующих у неё политик.

**Человек без строки в `user_roles` должен входить.** Если строку
удалили руками, хук возвращает claims нетронутыми, а не падает: иначе
правка таблицы в Studio лишала бы человека входа. Роль по умолчанию
подставляет фронтенд (`shared/lib/auth`, `DEFAULT_APP_ROLE = "user"` —
наименее привилегированная). Покрыто pgTAP-тестом.

### Грант `supabase_auth_admin` на `user_roles` избыточен и оставлен сознательно

Миграция выдаёт `grant select on public.user_roles to
supabase_auth_admin`, как в примере Supabase. **Хуку он не нужен.**
Функция объявлена `security definer` и принадлежит `postgres`, поэтому
её тело читает таблицу от имени владельца, к которому не применяются ни
гранты, ни RLS.

Проверено, а не предположено: грант отозван, выполнен настоящий вход
паролем через Auth API — claim `user_role` всё равно приехал. Повторено
трижды (грант есть → отозван → возвращён), результат одинаковый.

Грант всё же оставлен, потому что цена ошибки несимметрична. Если
владелец функции когда-нибудь окажется не владельцем таблицы — а
проверить это в облачном проекте миграция не может — хук поднимет
`insufficient_privilege`, GoTrue не сможет выпустить токен, и войти не
сможет **никто**. Лишний `select` для роли, которая и так администрирует
`auth.users`, стоит несравнимо дешевле. Комментарий в миграции говорит
именно это, а не пересказывает документацию.

### Без `role_permissions` и `authorize()`

Вторая половина примера Supabase — таблица разрешений и функция
`authorize(permission)` в RLS-политиках — не делается. При двух ролях и
отсутствии таблиц данных проверять `authorize('records.delete')` негде:
нет ни `records`, ни политики, которая бы её вызывала. Это слой без
единого потребителя.

Вернётся вместе с первыми таблицами служения — и тогда у решения будет
обоснование из настоящих политик, а не из примера в документации.

### `getClaims()`, а не `getUser()`

`getClaims()` проверяет подпись и срок действия токена локально.
`getUser()` на каждый вызов обращается к Auth-серверу и даёт
дополнительно ровно одно: обнаружение сессии, отозванной на другом
устройстве. В официальном примере middleware Supabase используется
`getClaims()`, и в документации прямо сказано, что для авторизации
запроса его достаточно.

При одном человеке на устройство разница в защите мала, а разница в
задержке — сетевой вызов на каждую навигацию, включая `proxy.ts` до
рендера.

### Гвард написан, но в v2 ничего не охраняет

`hasRole` (`shared/lib/auth`) покрыт юнит-тестами и используется ровно в
одном месте — `/profile` выводит название роли. Ни один маршрут по роли
не закрыт, `/admin` не создаётся. Так решил владелец: инфраструктура
готова, поверхность для неё появится вместе с администрированием.

`hasRole(claims, "user")` для администратора возвращает `false`
намеренно: иерархии прав в v2 нет (нет `role_permissions`), поэтому
проверка спрашивает про конкретную роль и получает ответ про неё же.
Зафиксировано тестом, чтобы «admin — надмножество user» не появилось
само собой.

### Ручные шаги, которые миграции не делают

Включение хука — **настройка проекта**, а не часть схемы:

- локально — `[auth.hook.custom_access_token]` в `config.toml`
  (`uri = "pg-functions://postgres/public/custom_access_token_hook"`);
- в облаке — Authentication → Hooks в дашборде.

Там же выключается регистрация (`enable_signup = false`, ADR 0043).

Две ловушки, обе проверены на живом стеке:

1. **Правка `config.toml` не подхватывается `supabase db reset`** —
   настройки Auth читаются при старте контейнеров. Нужен
   `pnpm db:stop && pnpm db:start`, иначе хук молча не включится, и
   отсутствие claim выглядит как дефект миграции.
2. **`enable_signup` в `config.toml` встречается дважды** — под `[auth]`
   и под `[auth.email]`. Выключать надо только первый. Второй — это
   выключатель самого способа входа: при `false` вход по паролю
   отвечает `email_provider_disabled`, «Email logins are disabled».
   Глобального достаточно: `POST /auth/v1/signup` отвечает
   `signup_disabled`.

## Последствия

- Роль читается бесплатно и локально, в том числе в `proxy.ts`.
- **Роль меняется только при следующем входе.** Правка `user_roles` в
  Studio не затрагивает уже выданные токены; при `jwt_expiry = 3600` до
  часа человек проработает со старой ролью, пока не обновит токен. Для
  двух ролей и выдачи прав вручную это приемлемо; первый же сценарий,
  где роль должна меняться на лету, потребует пересмотра решения.
- Хук выполняется на каждом выпуске токена, то есть и при обновлении
  сессии. Это один `select` по первичному ключу.
- Отказ хука означает невозможность выпустить токен — то есть
  невозможность войти. Поэтому единственная ветка, где он мог бы
  упасть (нет строки в `user_roles`), обработана явно.
- pgTAP проверяет права и возвращаемые claims, но **не** путь через
  GoTrue: включённость хука проверяется только живым входом. Это
  осознанный пробел в автотестах — в CI нет шага, который поднимал бы
  Auth и логинился.
