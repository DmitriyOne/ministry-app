# ADR 0043: авторизация по email и паролю, профили и роли

Статус: принято, 2026-10-05.
Относится к v2. Дополняется ADR 0044 (роль в JWT), 0045 (маршруты и
гейты), 0046 (классы отказов).

## Контекст

v1 — релиз Coming soon: приложения за `LAUNCH_MODE` нет, людей в системе
нет, единственная таблица — вайтлист, и пишет в неё анонимный
посетитель. v2 открывает приложение, и у него впервые появляются
учётные записи.

Условия, заданные владельцем:

- регистрации нет, учётные данные он выдаёт лично;
- вход без Google и прочих провайдеров;
- нужна отдельная таблица с данными людей;
- нужны роли, и роль должна приезжать в JWT.

Макет `login.html` показывает два поля: «Эл. почта» (`inputmode="email"`,
placeholder `имя@почта.ру`) и «Пароль», плюс кнопку «Забыли пароль?».

## Что именно нужно решить

1. Чем человек входит — email или username.
2. Как хранить профиль и роль и кто имеет к ним доступ.
3. Как заводится учётная запись, чтобы владелец делал это одним
   действием.
4. Что делать с «Забыли пароль?», пока отправки писем нет.

## Вариант входа: email, а не username

Изначальная формулировка задачи была «только юзернейм + пароль». Она
отклонена, и вот почему.

Supabase Auth не умеет username нативно. Остаются два обхода:
подставлять синтетический адрес (`имя@ministry.local`) или держать
таблицу-справочник `username → email`. Оба ломают сброс пароля
**навсегда**: восстановить доступ самостоятельно человек не сможет
никогда, единственным каналом останется владелец. Кроме того,
синтетический адрес расходится с макетом, где поле прямо подписано как
почта.

Email — штатный путь (`signInWithPassword({ email, password })`), он же
оставляет дверь для будущего восстановления доступа открытой. Владелец
подтвердил выбор.

Регистрация выключена: `enable_signup = false`. Без этого «креды выдаю
я» не выполняется — зарегистрироваться смог бы любой.

## Варианты модели доступа к профилям

### A. Как в v1: таблица закрыта, наружу — `security definer`-функция

Правило v1 (ADR 0033, уточнено ADR 0037): RLS включён, политик нет,
grants отозваны, доступ выдаётся `execute` на функцию. Последовательно,
но здесь это означало бы `get_my_profile()` и `update_my_profile()` —
две функции, которые внутри делают ровно то, что сделала бы политика
`auth.uid() = id`, плюс свои pgTAP-тесты. Слой есть, выигрыша нет.

### B. Настоящие RLS-политики — выбрано

Политика `using ((select auth.uid()) = id)` выражает правило там, где
оно проверяется, и работает для любого запроса, а не только для того,
который предусмотрела функция-обёртка.

### C. Всё через `service_role` с доверенного сервера

Как сделано для вайтлиста (ADR 0037). Но там это было нужно, потому что
записывает анонимный посетитель, которому нельзя доверять. Здесь
запрашивает сам владелец строки под своим JWT — обход RLS секретным
ключом ради этого снимает защиту вместо того, чтобы её использовать.

## Решение

### Почему это отступление от правила v1 — и где его граница

ADR 0033 требует: «Если позже у таблицы появится политика, это должно
быть осознанным решением с отдельной записью, а не побочным эффектом
правки миграции». Это она.

Правило v1 выведено из конкретной задачи: **анонимный посетитель пишет
строки, которые не должен читать**. При таком условии любая политика —
это дверь, которую нужно сторожить, и проще двери не делать.

У профиля условие другое: **строка принадлежит тому, кто её читает, и
читается под его собственным JWT**. Правило доступа формулируется одной
строкой и целиком выражается политикой. Обёртка в `security
definer`-функцию здесь не добавляет безопасности — она добавляет код,
который нужно писать, тестировать и не забывать править вместе с
политикой, которой больше нет.

Граница отступления проведена узко:

| Таблица | Модель | Почему |
|---|---|---|
| `profiles` | RLS + две политики | строку читает её владелец под своим JWT |
| `user_roles` | RLS, **ни одной политики**, как в v1 | роль человек узнаёт из своего токена, а не чтением таблицы |

То есть исключение касается одной таблицы, а не отменяет правило.

### Таблицы

```sql
create type public.app_role as enum ('user', 'admin');

create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text not null check (length(trim(display_name)) > 0),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.user_roles (
  user_id uuid primary key references auth.users on delete cascade,
  role public.app_role not null default 'user'
);
```

- **`app_role` — enum, не `text`.** Опечатка в роли должна падать на
  вставке, а не всплывать позже как не сработавшая проверка прав.
- **`on delete cascade`** на обеих: удаление человека в Studio не должно
  оставлять висящие строки.
- **`check` на `display_name`** — последняя линия обороны против пустого
  имени, по тому же принципу, что `check`-ограничения в ADR 0033.
- **`updated_at`** — потому что `display_name` правит сам человек, и
  поддерживает поле триггер (ниже).
- Больше никаких колонок — YAGNI. Телефон, собрание, часовой пояс
  появятся вместе с экранами, которым они понадобятся.

### Политики

```sql
revoke all on table public.profiles   from anon, authenticated;
revoke all on table public.user_roles from anon, authenticated;
grant select on table public.profiles to authenticated;
grant update (display_name) on table public.profiles to authenticated;

create policy "read own profile" on public.profiles
  for select to authenticated using ((select auth.uid()) = id);

create policy "update own profile" on public.profiles
  for update to authenticated using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);
```

- **`revoke all` обязателен** по той же причине, что в ADR 0033: grants
  выдаются новой таблице автоматически и политиками не отбираются.
- **`(select auth.uid())`, а не `auth.uid()`.** Обёрнутый в подзапрос
  вызов планировщик вычисляет один раз на запрос, а не на каждую строку.
- **`with check` на `update` написан явно, хотя сегодня он
  избыточен.** Проверено на живой базе: если у UPDATE-политики опустить
  `with check`, Postgres применяет выражение `using` и к новой строке —
  переписать `id` своей строки на чужой не выйдет и без него. Здесь
  `with check` стоит не ради сегодняшнего поведения, а потому что оно
  зависит от совпадения двух условий: стоит в будущем появиться
  политике с более широким `using` (например, `using (true)` для
  администратора), и неявная проверка новой строки станет такой же
  широкой. Явная строка не даст этому произойти незаметно.

  Первая редакция этого ADR утверждала обратное — что без `with check`
  строку можно отдать другому человеку. Это неверно, и проверка
  мутацией (политика пересоздана без `with check`, попытка угона
  повторена) это показала.
- **Grant на `update` — колоночный, а не табличный.** Политика
  ограничивает, какие **строки** можно менять, и ничего не говорит про
  **колонки**. Первая редакция миграции выдавала
  `grant select, update on table`, и этого хватило, чтобы клиент выполнил
  `update profiles set created_at = '1970-01-01'` и переписал свою
  отметку времени — проверено на живой базе, именно так дефект и был
  найден. `display_name` — единственное поле, которое человек вправе
  менять, поэтому grant выдан только на него, а проверка мутацией
  (возврат табличного grant → угон `created_at` снова проходит)
  подтвердила, что pgTAP-тест на это не пустой.
- **`insert` и `delete` политик не получают.** Учётные записи выдаёт
  владелец: человек не может ни создать себе профиль, ни удалить его.
  Отсутствие политики — это запрет, а не недоработка.

### `updated_at` поддерживает общий триггер

```sql
create or replace function public.set_updated_at()
returns trigger language plpgsql security invoker set search_path = '' as $$
begin
  new.updated_at := now();
  return new;
end;
$$;

create trigger profiles_set_updated_at
  before update on public.profiles
  for each row execute function public.set_updated_at();
```

Триггер `updated_at` часто добавляют по инерции; здесь у него есть
конкретное основание. `profiles` — **первая таблица в проекте, которую
клиент правит напрямую**, а не через RPC. У остальных единственная дверь
— функция, и она сама пишет `updated_at` (так и сделано в
`push_subscriptions`: `updated_at = now()` руками в трёх местах
миграций). У `profiles` такой двери нет, а колоночный grant выше
намеренно не даёт клиенту писать это поле — значит выставить его может
только триггер.

Функция **не привязана к таблице**: любая следующая таблица с
`updated_at` переиспользует её же. `security invoker`, в отличие от
`handle_new_user` ниже, — она только присваивает `new` и чужих прав не
требует. `now()` разрешается при пустом `search_path`, потому что
`pg_catalog` просматривается всегда неявно; что-либо вне него пришлось
бы писать полным именем.

Оговорка, которую поймал pgTAP-тест: `now()` — время **начала
транзакции**, поэтому внутри одной транзакции `updated_at` никогда не
окажется больше `created_at`. Проверять «время выросло» бессмысленно;
тест проверяет наблюдаемое и действительно важное — что триггер
перебивает значение, подсунутое писателем, даже обладающим полными
правами на колонку.

`push_subscriptions` на этот триггер **не переводится** в рамках v2: там
`updated_at` уже пишется внутри RPC, и переделка — отдельная задача со
своей проверкой, а не правка «заодно».

### Профиль и роль создаёт триггер

```sql
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

`handle_new_user()` — `security definer` с `set search_path = ''`
(иначе у неё нет прав на запись в `public`, а пустой `search_path`
заставляет писать все имена полностью). Создаёт строку в `profiles`
(`display_name` из `raw_user_meta_data ->> 'display_name'`, иначе —
локальная часть адреса) и строку в `user_roles` с ролью `user`.

Без триггера «создать человека» было бы тремя действиями в Studio, из
которых два легко забыть, — и забытая строка в `user_roles` тихо
превратилась бы в человека без роли.

### «Забыли пароль?» пока пишет в лог

Отправки писем ещё нет. Экран `/forgot-password` и серверное действие
делаются сразу, но действие пишет запрос в серверный лог, а не
отправляет письмо. Это тот же временный компромисс, что в ADR 0027, где
адрес вайтлиста сначала писался открытым текстом, — с той разницей, что
здесь лог и есть рабочий механизм: владелец видит запрос и меняет пароль
в Studio.

Три свойства заложены сразу, потому что доделать их позже, не меняя
поведения, нельзя:

- **ответ одинаковый, есть такой аккаунт или нет** — иначе страница
  становится способом проверить, кто зарегистрирован;
- **ответ одинаковый и при срабатывании лимитера** — по той же причине;
- **лимитер обязателен** — это неаутентифицированная ручка, которая
  пишет в лог.

Условие снятия: подключена отправка писем → лог сводится к факту без
адреса, как уже сделано в вайтлисте после ADR 0033.

## Последствия

- Доступ к профилю проверяется в базе и действует для любого запроса, а
  не только для предусмотренного обёрткой.
- Модель доступа перестала быть однородной: в проекте теперь два
  образца — «закрытая таблица + RPC» (вайтлист, `user_roles`) и
  «политика на владельца строки» (`profiles`). Это цена решения, и
  поэтому таблица границ выше — часть решения, а не пояснение к нему.
  Новая таблица по умолчанию берёт модель v1; отступление требует такой
  же отдельной записи, как эта.
- Роль меняется правкой `user_roles` в Studio, но **в токене она
  появится только после повторного входа** — следствие ADR 0044, где
  роль кладётся в JWT. Для двух ролей и выдачи прав вручную это
  приемлемо; при первом же сценарии, где роль должна меняться на лету,
  решение придётся пересматривать.
- Восстановление доступа до подключения писем идёт только через
  владельца.

## Оговорка: адрес в логе — персональные данные

Пока лог сброса пароля содержит адрес, он попадает в логи Vercel со
всеми их сроками хранения. Это осознанно и временно, ровно как в ADR
0027. Проверить при подключении писем: не утекает ли этот лог в Sentry
(ADR 0041 — «только ошибки», `console.info` туда попадать не должен, но
это надо подтвердить, а не предположить).
