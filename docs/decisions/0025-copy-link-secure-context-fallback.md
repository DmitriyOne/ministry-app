# ADR 0025: Кнопка «Copy link» и защищённый контекст

## Контекст

Баг с живого iPhone: пользователь открыл приложение по локальной сети
(`http://192.168.1.176:3000`, не `https://` и не `localhost`) и нажал
«Copy link» на экране `/access/ios-browser` («Safari only, for now»,
ADR 0016). В консоли:

```
[copy-link] Failed to copy the link TypeError: undefined is not an object
(evaluating 'navigator.clipboard.writeText')
  at src/features/copy-link/model/use-copy-link.ts:25
```

**Причина** — `navigator.clipboard` существует только в защищённом
контексте (MDN, "Secure contexts"): `https://` либо `localhost`
(включая `127.0.0.1`). По обычному `http://` на IP-адрес (ровно так, как
приложение открывали по локальной сети для отладки с телефона) свойство
`clipboard` на `navigator` отсутствует вовсе — не `null`, не отклонённый
`Promise`, а `undefined`. Старый код обращался к нему напрямую
(`navigator.clipboard.writeText(...)`) внутри `try/catch`: `TypeError`
действительно ловился, но человек получал только сообщение об ошибке,
без единого способа продолжить — адрес нигде не показан, скопировать
или хотя бы увидеть его было нельзя.

Это не только баг локальной отладки. Экран `/access/ios-browser`
существует ровно для случая, когда человек открыл ссылку во встроенном
браузере мессенджера (Instagram, WhatsApp, Telegram и т.д., см. список
токенов в `classify-access.ts`, ADR 0016) — и у части таких браузеров
доступа к буферу обмена нет даже по `https://`: они либо не реализуют
`navigator.clipboard` вовсе, либо реализуют, но конкретный вызов
`writeText` тихо проваливается. То есть кнопка регулярно бесполезна
именно у той аудитории, которой этот экран адресован.

## Решение

### 1. Проверка доступности заранее, не через падение

`web/src/features/copy-link/model/use-copy-link.ts`: `canUseClipboardApi()`
проверяет `window.isSecureContext && typeof
navigator.clipboard?.writeText === "function"` **до** попытки вызова —
не постфактум в `catch`. Различие важно: `window.isSecureContext` —
собственный флаг браузера, не эвристика (протокол + хост уже разобраны
браузером с учётом всех особых случаев, включая `localhost`/loopback);
если он `false`, `navigator.clipboard` гарантированно не существует, и
незачем даже пробовать.

### 2. Запасной путь — `document.execCommand("copy")`, с честной оговоркой о надёжности

Если Clipboard API недоступен (незащищённый контекст **или** сам объект
`navigator.clipboard`, при `isSecureContext === true`, не даёт
`writeText`), `copyWithExecCommand()` создаёт временный `<textarea>`,
выделяет его текст и вызывает `document.execCommand("copy")`.

**Статус по документации (MDN, проверено для этой задачи):**
`execCommand()` помечен как *deprecated* — "avoid using this feature in
new projects", "not implemented consistently or fully by user agents",
кандидат на удаление из стандартов/браузеров без объявленного срока.
Тем не менее он ещё широко работает, в т.ч. в Safari, и это
единственное, что вообще может сработать по `http://` (Clipboard API там
недоступен по определению, второго пути нет). На iOS Safari у
`execCommand("copy")` есть известные ограничения:

- команда обязана выполниться **синхронно** внутри обработчика клика
  (в отличие от `navigator.clipboard.writeText`, которому разрешён
  `await`) — иначе браузер теряет привязку к пользовательскому жесту;
- элемент, чьё содержимое выделяется, не должен быть невидимым
  (`display: none`/нулевой размер) — iOS Safari не выделяет текст в
  таком элементе. Поэтому временный `<textarea>` спрятан `opacity: 0` +
  `position: fixed`, а не `display: none`;
- требуется явный `setSelectionRange`, одного `.select()` недостаточно
  на части версий iOS Safari.

Код это учитывает, но **не выдаёт себя за надёжное решение**: часть
встроенных браузеров мессенджеров блокирует `execCommand("copy")` так
же, как и Clipboard API, независимо от протокола. Поэтому запасной путь
— это попытка её сделать проще, не единственная линия защиты.

### 3. Единственный по-настоящему надёжный путь — показать адрес текстом

`web/src/features/copy-link/ui/copy-link-button.tsx`: адрес страницы
(`window.location.href` по умолчанию, тот же источник, что копирует
кнопка) выводится как обычный, доступный для выделения текст —
**всегда**, не только когда копирование не удалось.

**Почему всегда, а не только при ошибке**: показ по условию «копирование
не сработало» требует либо ждать реального провала (проверено: даже
`isSecureContext === true` не гарантия — Clipboard API может быть
формально доступен и всё равно тихо отклонить `writeText` в части
встроенных браузеров, см. контекст выше), либо самостоятельно
угадывать это по эвристикам, которые не покрывают все браузеры. Тексту
не нужно угадывание: он корректен и полезен в любом случае — тому, кто
успешно скопировал кнопкой, он не мешает (можно перепроверить глазами
или переслать текстом вручную), а тому, у кого копирование не сработало
(тихо или явно), он не оставляет ни секунды без выхода. Постоянное
присутствие также убирает лишний скачок раскладки между состояниями
«до» и «после» ошибки.

Реализация: `useState("")`, заполняется в `useEffect` (не читается
напрямую при рендере — первый клиентский рендер должен совпасть с
серверным, где `window` не существует; тот же приём, что у `ShellGate`,
`web/src/app/layout/shell-gate.tsx`, ADR 0019). `setState` обёрнут в
`queueMicrotask` — не сырой вызов в теле эффекта — чтобы пройти
`eslint-plugin-react-hooks`' правило `set-state-in-effect`, тем же
способом, что уже применён в `ShellGate`.

Вёрстка — токены проекта, не хардкод: `Caption` (`shared/ui/caption.tsx`)
для подписи «Address», `text-caption font-520 text-ink` для самого
адреса, `break-all` (чтобы длинный URL без пробелов переносился на
узком экране, а не вылезал за пределы контейнера) и `select-all`
(упрощает выделение всего текста одним тапом/кликом). Проверено на
375px — не ломает раскладку (скриншот ниже).

### Текст ошибки обновлён под новый экран

`copyLinkError` раньше говорил «Select the address in the browser bar
and copy it manually» — эта инструкция была в принципе неверной для
встроенного браузера мессенджера (адресной строки может не быть видно
или не быть вовсе) и вдобавок теперь избыточна — адрес уже показан на
самом экране. Новый текст: «Couldn't copy the link automatically —
select the address below and copy it manually» (`en-GB.json`). Новый
ключ `addressLabel` — «Address», подпись над самим адресом.

## Другие места, зависящие от защищённого контекста

Проверено (`grep -rn` по `web/src`/`web/app` на `navigator\.`,
`clipboard`, `serviceWorker`, `geolocation`, `share`, `mediaDevices`,
`permissions` и т.п.):

- **Геолокация, `navigator.share`, `mediaDevices` и т.п. — не
  используются нигде в проекте.** Проверять больше нечего.
- **Сервис-воркер регистрируется безопасно уже сейчас** —
  `SerwistProvider` (`@serwist/turbopack/react`, подключён в
  `web/src/app/layout/root-layout.tsx`) внутри себя проверяет
  `"serviceWorker" in navigator` **до** вызова `new Serwist(...)`/
  `.register()` (см. `node_modules/@serwist/turbopack/src/index.react.tsx`).
  По `http://` на IP-адрес это условие просто `false` — регистрация
  тихо пропускается, ни исключения, ни консольной ошибки. Проверено
  живьём (Playwright, `http://192.168.1.176:3125/access/ios-browser`,
  раздел «Живая проверка» ниже) — `browser_console_messages` пуст в
  обоих сценариях. Отдельного фикса не потребовалось — только
  подтверждение, что это действительно так, не предположение.

## Живая проверка

`pnpm lint`, `pnpm typecheck`, `pnpm test` (26/26) — чисто.

`pnpm build` изначально падал на **не связанном с этой задачей**
плейсхолдере `throw new Error("Not implemented")` в
`web/src/pages/day/ui/DayPage.tsx` (сознательная заглушка «на
следующий этап», ломает статическую генерацию `/day`). Для живой
проверки продакшен-сборки эта строка была временно закомментирована,
сборка и `next start -p 3125` проверены, после чего строка возвращена
на место **дословно** — `git diff` по этому файлу после отката пуст.
Отдельная проблема, не эта задача.

Playwright, `next start -p 3125`, iPhone UA (Instagram in-app
браузер), экран `/access/ios-browser`:

- **`http://192.168.1.176:3125`** (LAN IP, не `localhost` — иначе
  контекст был бы защищённым и баг не воспроизвёлся бы):
  `window.isSecureContext === false`, `navigator.clipboard === undefined`
  — подтверждено `page.evaluate`. Адрес виден на экране сразу, до
  всякого клика. Клик «Copy link» → `execCommand`-путь сработал (кнопка
  переключилась на «Link copied»), консоль пуста (`browser_console_messages`
  — 0 сообщений любого уровня). Даже если бы в реальном встроенном
  браузере `execCommand` был заблокирован — адрес уже был на экране до
  клика, человек не остаётся ни с чем.
- **`http://localhost:3125`** (защищённый контекст):
  `window.isSecureContext === true`, `navigator.clipboard` определён.
  Клик «Copy link» → состояние «Link copied», `navigator.clipboard.readText()`
  вернул реально скопированный адрес, консоль пуста.
- **375×667** (`http://192.168.1.176:3125`, длинный query-параметр для
  проверки переноса): `document.documentElement.scrollWidth === clientWidth
  === 375` — горизонтальной прокрутки нет, длинный адрес переносится
  по `break-all`, вёрстка не ломается.
