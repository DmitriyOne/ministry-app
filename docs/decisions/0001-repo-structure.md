# ADR 0001: Структура монорепозитория — web/backend/ops/envs, а не apps/*

## Контекст

Нужно было выбрать верхнеуровневую структуру монорепо для Next.js-фронтенда
и Supabase-бэкенда. Распространённый шаблон в pnpm-монорепо — каталог
`apps/*` (иногда вместе с `packages/*` для общих библиотек).

## Варианты

1. **`apps/web`, `apps/backend`** (+ возможно `packages/*` для общего кода) —
   типичный шаблон Turborepo/Nx.
2. **`web/`, `backend/`, `ops/`, `envs/`** — плоская структура по назначению
   каталога, без промежуточного `apps/`.

## Решение

Выбран вариант 2: `web/` (Next.js), `backend/` (Supabase CLI-проект), `ops/`
(инфраструктура для локального запуска — Docker), `envs/` (шаблоны
переменных окружения), `docs/` (ADR).

Причины:
- В проекте всего два деплоймых юнита (фронт и бэкенд), общих пакетов пока
  нет — экстра-уровень `apps/` не даёт выгоды, только лишнюю вложенность.
- Явные имена по назначению (`web`, `backend`, `ops`, `envs`) понятнее для
  новых участников, чем универсальное `apps`.
- `pnpm-workspace.yaml` тривиально перечисляет `["web", "backend"]" — не
  нужен glob по `apps/*`.

## Последствия

- Если в будущем появится общий код между `web` и `backend` (типы, схемы
  валидации), потребуется либо новый workspace-пакет (например,
  `packages/shared`), либо генерация/копирование (уже частично решено через
  `db:types`, генерирующий типы БД прямо в `web/`).
- Добавление третьего деплоймого юнита (например, мобильного клиента)
  потребует пересмотра этой структуры — но это осознанный компромисс ради
  простоты на de-facto двух пакетах сейчас.
