# ADR 0009: Отказ от контейнерного запуска `web` (заменяет ADR 0003 частично, ADR 0007 целиком) + возврат к дефолтному имени auth-cookie

## Контекст

В предыдущих раундах (ADR 0003, 0007) появился опциональный
`docker-compose`-путь запуска `web` в контейнере — параллельно основному
способу (`pnpm dev`, Next.js нативно на хосте). Он решал вопрос
"как проверить `web` в контейнере", но на практике:
- Ежедневная разработка полностью покрывается `pnpm dev` — Supabase и так
  бежит в Docker (через Supabase CLI), а Next.js нативно на хосте даёт
  быстрый hot-reload без лишних слоёв.
- Контейнерный `web` тянул за собой постоянную сложность: два разных URL
  Supabase (`NEXT_PUBLIC_SUPABASE_URL` для браузера на хосте vs
  `SUPABASE_INTERNAL_URL`/`host.docker.internal` для сервера в
  контейнере), из-за чего пришлось фиксировать имя auth-cookie
  (`SUPABASE_AUTH_COOKIE_NAME`) — иначе браузер и сервер писали/читали
  разные cookie для одной сессии (см. ADR 0007, раздел "Имя auth-cookie").
  Плюс отдельный класс проблем с правами на `node_modules` под non-root
  пользователем при переходе на pnpm 12 (`verifyDepsBeforeRun`, см. тот же
  ADR).
- Отдельные стенды (staging/preview окружения и т.п.), если понадобятся —
  это другая задача с другими требованиями (не "проверить web в
  контейнере локально"), и её стоит решать отдельно, когда она реально
  появится, а не заранее поддерживать контейнерный локальный путь "про
  запас".

## Решение — часть 1: удалить контейнерный запуск `web`

Удалено целиком:
- `ops/` (весь каталог — `ops/local/Dockerfile`, `ops/local/docker-compose.yml`).
- Корневой `.dockerignore`.
- Скрипт `docker:local` из корневого `package.json`.
- `SUPABASE_INTERNAL_URL` — из схемы `@t3-oss/env-nextjs`
  (`web/src/shared/config/env.ts`), из `envs/web.local.env(.example)`.
- Функция `getSupabaseServerUrl()` — серверный Supabase-клиент
  (`shared/api/supabase/server.ts`) и health-запрос в `DayPage` снова
  используют напрямую `env.NEXT_PUBLIC_SUPABASE_URL`, как и браузерный
  клиент.

Локальная разработка — только `pnpm dev`: Supabase поднимается через
Supabase CLI (сам использует Docker под капотом — это не меняется, см.
ADR 0003), Next.js — нативно на хосте.

ADR 0003 и ADR 0007 **не удалены** — история решений (включая то, что
контейнерный вариант пробовался, какие баги при этом нашлись и как они
чинились) остаётся полезной, если контейнерный запуск понадобится снова.
Оба помечены статусом "заменено/частично заменено ADR 0009" с указателем
сюда.

## Решение — часть 2: имя auth-cookie возвращено к дефолту

Единственная причина фиксировать `SUPABASE_AUTH_COOKIE_NAME` была в том,
что браузер и сервер резолвили Supabase через разные хосты
(`127.0.0.1` vs `host.docker.internal`) — с уходом контейнерного `web`
причина исчезла: теперь и браузер, и сервер всегда используют один и тот
же `NEXT_PUBLIC_SUPABASE_URL` (`127.0.0.1` локально, `<ref>.supabase.co`
в проде), поэтому дефолтное имя cookie у `@supabase/ssr`
(`` sb-${hostname.split('.')[0]}-auth-token ``) у них автоматически
совпадает — фиксировать нечего.

Удалено: `web/src/shared/api/supabase/constants.ts`,
`SUPABASE_AUTH_COOKIE_NAME`, `cookieOptions: { name }` в `client.ts` и
`server.ts` — оба клиента снова выглядят как в официальном гайде Supabase
для Next.js (`createBrowserClient(url, key)` /
`createServerClient(url, key, { cookies })`, без кастомных
`cookieOptions`).

**Оговорка на будущее**: инвариант "браузерный и серверный клиенты
обязаны использовать один и тот же `NEXT_PUBLIC_SUPABASE_URL`" — жёсткое
условие для того, чтобы имя cookie по умолчанию совпадало. Если у
Supabase-проекта в проде появится custom domain (например,
`api.<домен>` вместо `<ref>.supabase.co`), дефолтное имя cookie
изменится вместе с хостнеймом — существующие пользователи один раз
разлогинятся при переключении. Если это неприемлемо, тогда имя cookie
нужно будет зафиксировать явно (вернуть паттерн из ADR 0007) — то есть
"зафиксировать явно" остаётся не догмой, а конкретным решением под
конкретную причину, которой сейчас нет.

`site_url`/`additional_redirect_urls` в `backend/supabase/config.toml`,
выровненные на `http://127.0.0.1:3000` (тот же origin, что видит
браузер) — это отдельное и по-прежнему верное исправление, оставлено как
есть (см. ADR 0007).

## Последствия

- Меньше поверхности для багов: один URL Supabase на оба клиента, один
  (дефолтный) паттерн имени cookie, никакого разделения
  публичного/внутреннего адреса.
- Если понадобится проверить `web` именно в контейнере (например, перед
  выбором self-hosted Docker-инфраструктуры вместо Vercel) — исходная
  точка есть в истории git и в ADR 0007, переиспользовать оттуда, а не
  начинать с нуля.
- Любой будущий кастомный домен Supabase — повод перечитать оговорку
  выше и, возможно, вернуть фиксированное имя cookie.
