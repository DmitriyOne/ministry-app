# ADR 0011: Дизайн-система — токены цветов, типографики, радиусов, теней и иконки

## Контекст

Нужна была базовая дизайн-система проекта (токены, а не готовые экраны):
цвета, типографическая шкала, шрифт, радиусы, тень и иконки — строго по
прототипу-стайлгайду, полученному от заказчика (`index.html` +
4 SVG-файла: `lock-closed-svgrepo-com.svg`, `lock-open-svgrepo-com.svg`,
`sharp-solid-rabbit-running.svg`, `turtle-animal-icon.svg`; файлы не в
репозитории, только как первоисточник для этой задачи). Прототип — это
статичный HTML-снимок экспорта из инструмента дизайн-прототипирования
(с инжектированным служебным JS/CSS этого инструмента, не относящимся к
самому продукту), а не код проекта — переносить нужно было только
дизайн-решения, не разметку как есть.

## Палитра

| Токен (globals.css) | HEX | Назначение | Где используется |
|---|---|---|---|
| `--palette-warm-gray` → `--background`/`--muted`/`--secondary` | `#F6F5F3` | Фон всех экранов, вдавленные поля | `bg-background` |
| `--palette-deep-green` → `--hero` | `#1E4A40` | Карточки-герои, вход, экран перевыполнения | `bg-hero` |
| `--palette-muted-green` → `--primary` | `#2E6F5E` | Действия, «+», прогресс, состояние «в графике» | `bg-primary` |
| `--palette-ink` → `--foreground`/`--ink` | `#22302C` | Весь текст; приглушённый текст — две ступени, `--ink-muted` (.72) и `--ink-faint` (.67, см. «Сведение приглушённого текста к двум ступеням» ниже), плюс декоративный `--ink-a55` (.55, только иконки) — подписи, `.09/.07/.05` — границы/разделители/тень | `text-foreground`, `text-ink-muted`, `text-ink-faint` и т.д. |
| `--palette-terracotta` → `--negative`/`--destructive` | `#9A5238` | Отставание, ошибка 500, отрицательная дельта | `bg-negative`, `text-negative` |
| `--palette-mint` → `--positive-hero` | `#8FD4B4` | **Только** поверх `--hero` (глубокий зелёный): часы сверх плана | `text-positive-hero` |
| `--palette-white` → `--card` | `#FFFFFF` | Карточки | `bg-card` |

Соответствие HEX проверено визуально (Playwright-скриншот `/styleguide`) и
по исходному коду — токены объявлены как прямой HEX в `:root`
(`web/src/app/styles/globals.css`), без прохода через `oklch`, поэтому
совпадение точное по построению, а не приближённое конвертацией
цветового пространства.

### Цвета, найденные в прототипе сверх таблицы

- **`#245549`** — встречается как `a:hover{color:#245549}` в служебном CSS
  прототипа. Это hover/pressed-состояние приглушённого зелёного
  (`#2E6F5E`), не самостоятельный цвет палитры. Заведён как производный
  токен `--palette-muted-green-hover` / `--color-accent-hover`, а не как
  отдельная строка палитры.
- **`#B00020`** — встречается в `.sc-logic-error{background:#b00020;...}`.
  Это цвет баннера ошибки самого инструмента предпросмотра прототипа
  (внешний preview-harness, инжектируется в служебный `<style>` в начале
  файла), не часть дизайна продукта. Токеном **не стал** — решение
  сознательное, задокументировано здесь, чтобы не переоткрывать вопрос.

## Типографическая шкала

Источник — таблица «размер / вес / назначение» из задания, сверено с
прототипом:

| Токен (`@theme inline`) | px / вес / трекинг | Назначение |
|---|---|---|
| `text-display` / `font-620` / `tracking-display` | 56 / 620 / −0.04em, `line-height:1` | Главный показатель («2:15») |
| `text-totals` / `font-620` / `tracking-totals` | 44 / 620 / −0.04em, `line-height:1` | Итоги («279:15») |
| `text-screen-title` / `font-640` / `tracking-screen-title` | 34 / 640 / −0.03em | Заголовок экрана |
| `text-day-title` / `font-640` / `tracking-day-title` | 30 / 640 / −0.025em | Заголовок дня («2 июня») |
| `text-list-row` / `font-580` / `tracking-list-row` | 17 / 580 / −0.015em | Строка списка |
| `text-caption` / `font-540` + `text-ink-muted` | 13 / 540 | Пояснение |
| `text-eyebrow` / `font-600` / `tracking-eyebrow` + `uppercase` + `text-ink-faint` | 11 / 600 / 0.12em, UPPERCASE | Надзаголовок секции |

Дополнительно заведён `font-560` (13px/560) — используется в прототипе для
подписей под иконками; в исходную таблицу задания не входит, но встречается
в стайлгайде, поэтому добавлен как ещё один шаг шкалы весов, а не как
магическое число в разметке.

Все числовые значения — через utility-класс `tabular-nums`
(`font-variant-numeric: tabular-nums`, встроен в Tailwind, отдельный
токен не нужен). Часы в интерфейсе — формат `2:15`; в текстах о цели и
отклонении — словами («27 ч 45 мин», «(−9 ч)») — это соглашение
контента, а не CSS-токен, поэтому в токенах не отражено, только здесь.

### Почему системный шрифт, а не Geist

Прототип задаёт `font-family: -apple-system, system-ui, sans-serif` —
никакого кастомного шрифта в дизайне нет. Решение пользователя: убрать
`Geist`/`Geist_Mono` (`next/font/google`) из `root-layout.tsx` и задать
системный стек напрямую через CSS-переменные:

```
--font-sans: -apple-system, system-ui, "Segoe UI", Roboto, Helvetica, Arial, sans-serif;
--font-mono: ui-monospace, "SF Mono", "Cascadia Code", "Roboto Mono", Menlo, Consolas, monospace;
```

Следствия: нет сетевого запроса/self-hosted файла шрифта — меньше веса
страницы и нет FOUT/FOIT; шрифт выглядит нативно на каждой ОС (это и есть
цель прототипа — «в манере SF Symbols»); специально проверено, что после
удаления `Geist`/`Geist_Mono` в коде не осталось ссылок на
`--font-geist-mono` (`grep -rn "geist" web/src` — только в комментариях,
поясняющих само решение).

## Почему нет тёмной темы

Решение пользователя: продукт сейчас сознательно light-only. Прототип не
содержит тёмной версии. Чтобы не блокировать тёмную тему в будущем,
класс `.dark` в `globals.css` **оставлен пустым** (а не удалён) с
комментарием, а `@custom-variant dark (&:is(.dark *))` — сохранён. Когда
решение о тёмной теме будет принято, потребуется только заполнить `.dark`
переопределениями семантических токенов из `:root` — структура файла и
разметка (`bg-background`, `text-foreground` и т.д.) менять не придётся,
потому что разметка уже ссылается на семантические токены, а не на
`--palette-*`/HEX напрямую.

## Токены shadcn/ui ↔ палитра проекта

`web/components.json` задаёт `"baseColor": "neutral"` — компоненты shadcn
изначально сгенерированы на нейтральной OKLCH-палитре
(`oklch(...)` серые тона). Все переменные, которые читают примитивы
shadcn (`--background`, `--foreground`, `--card`, `--primary`,
`--secondary`, `--muted`, `--accent`, `--destructive`, `--border`,
`--input`, `--ring`, `--radius`, `--sidebar-*`, `--chart-*`), переписаны в
`:root` на палитру проекта (см. таблицу выше — `--primary` = приглушённый
зелёный, `--destructive` = терракота и т.д.), поэтому компонент вроде
`<Button variant="destructive">` сразу выглядит в стиле приложения без
дополнительных классов. Цветовое пространство — HEX (не `oklch`), чтобы
совпадение с таблицей палитры было точным по построению, а не
приближённым через конвертацию; Tailwind v4 одинаково поддерживает
модификаторы прозрачности (`bg-primary/80` и т.п.) для HEX через
`color-mix()`, так что переход на HEX ничего не ломает.

`--radius` (база для `--radius-sm/md/lg/xl` в исходном шаблоне shadcn)
заменена на прямую шкалу токенов прототипа (см. ниже) — исходная формула
`calc(var(--radius) * k)` не воспроизводила бы набор 12/13/18/20/22/26/28/32
(не арифметическая прогрессия).

## Радиусы и тень

Прототип использует фиксированный, не прогрессивный набор радиусов:
12, 13, 18, 20, 22, 26, 28, 32 (px) и одну тень:
`0 1px 2px rgba(34,48,44,0.05)`. Заведены как:

- `--radius-12` … `--radius-32` (сырые значения) → подключены к
  Tailwind-шкале радиусов `--radius-xs/sm/md/lg/xl/2xl/3xl/4xl` в
  `@theme inline`, поэтому доступны как обычные utility-классы
  (`rounded-xs` … `rounded-4xl`), без произвольных `rounded-[Npx]` в
  разметке;
- `--shadow-card` → `shadow-card` (Tailwind v4 генерирует utility из
  любого ключа `--shadow-*` в теме).
- Нажатие (`transform: scale(0.93–0.98)`) — не токен, а поведенческое
  соглашение (диапазон, не фиксированное число); показано на `/styleguide`
  как рабочий пример (`active:scale-[0.95]`), не как CSS-переменная.

## Иконки

11 иконок вынесены в `web/src/shared/ui/icons/` (один файл — одна
иконка, kebab-case имя файла, PascalCase имя компонента, экспорт через
`index.ts`):

`calendar-icon.tsx`, `month-icon.tsx`, `year-icon.tsx`, `profile-icon.tsx`,
`check-icon.tsx`, `rabbit-icon.tsx`, `turtle-icon.tsx`,
`lock-closed-icon.tsx`, `lock-open-icon.tsx`, `app-mark-icon.tsx`,
`eye-icon.tsx`.

Правила:

- **Единый API пропсов**: `size?: number` (default — как в прототипе для
  каждой иконки: 18 для вкладок/галочки, 16 для замков, 20 для зайца, 22
  для черепахи по ширине — высота считается по соотношению сторон исходного
  viewBox, 24 для знака входа — аналогично, 26 для глаза), `className?`,
  остальные пропсы `<svg>` — через `...props`. Общий тип — внутренний файл
  `icon-props.ts` (не часть публичного API слоя, импортируется только
  соседними файлами иконок).
- **`currentColor` вместо хардкода**: все цвета (`#22302C`,
  `rgba(34,48,44,0.55)`, `#2E6F5E`, `#1E4A40`, `#9A5238`, белый) заменены
  на `currentColor`, цвет задаётся снаружи через Tailwind-класс текста
  (`text-primary`, `text-hero`, `text-negative`, `text-white` и т.п.).
  Единственное исключение — `app-mark-icon.tsx` (знак для входа): в
  прототипе это два уровня непрозрачности одного и того же белого
  (`#fff` / `rgba(255,255,255,0.5)`), не два разных цвета. Заменено на
  `currentColor` + `currentColor` c `fillOpacity="0.5"` для боковых фигур —
  эффект идентичен прототипу при `text-white` на зелёном фоне, но цвет
  остаётся наследуемым, а не зашитым. Настоящих многоцветных (разнородных
  по оттенку) иконок в прототипе нет.
- **Геометрия сохранена 1:1**: viewBox, `stroke-width` (1.5, ушки
  календаря — 1.6), `rx` контейнеров 4.2, `rx` столбиков графика 1.45,
  `r` точек 0.9–0.95, круглые окончания линий (`stroke-linecap="round"`)
  — скопированы из прототипа без изменений.
- **Заяц и черепаха** (`sharp-solid-rabbit-running.svg`,
  `turtle-animal-icon.svg`) прогнаны через `svgo --multipass`:
  заяц 4.07 КБ → ~1.0 КБ (−75.6%), черепаха 6.08 КБ → ~4.7 КБ (−22.8%).
  Проверено визуально (скриншот `/styleguide` рядом с исходным
  прототипом) — геометрия не изменилась, `svgo` только упростил кривые и
  срезал точность координат.

## Объединение классов: `cn` не видит `@theme` — свой `shared/lib/cn.ts`

### Симптом и диагноз

Найдено на экране-заглушке (ADR 0015): кнопка «Как установить»
(`variant="deep" size="role-lg"`) рендерилась тёмным текстом на тёмно-
зелёном фоне (контраст ≈1.1:1). В `button.tsx` вариант `deep` даёт
`text-hero-foreground`, размер `role-lg` — `text-list-row`; в итоговом
`className` `text-hero-foreground` отсутствовал. Подтверждено
экспериментально (`node`, пакет `cn` версии из `package.json`):

```
> const { cn } = require("cn");
> cn("text-hero-foreground", "text-list-row")
'text-list-row'
> cn("text-hero-foreground", "text-display")
'text-display'
> cn("text-hero-foreground", "text-caption")
'text-caption'
```

Причина: `cn` (drop-in замена clsx + tailwind-merge, shadcn) определяет
конфликтующие группы классов по **своему статичному, скомпилированному
снимку стандартной палитры Tailwind** — он не читает `@theme` в
`globals.css` и ничего не знает о наших именах (`list-row`, `display`,
`caption`…). Суффикс после `text-`, не входящий в этот снимок, не
совпадает ни с одним известным паттерном размера (`text-{keyword}`,
`text-[Npx]`) и по правилам классификации `cn` попадает в группу с более
мягким, permissive-валидатором — оказавшуюся группой **цвета**
(`text-{цвет}` тоже принимает почти любое имя, потому что в реальных
проектах кастомные цвета — частый случай). Из-за этого `text-list-row`
конфликтует с `text-hero-foreground` (тоже кастомный цветовой токен) —
при конфликте `cn` оставляет только последний по порядку класс.

Экспериментально подтверждено, что это **не только текстовые размеры**:
таким же образом безымянные суффиксы `font-{вес}` (наши `font-500`…
`font-640`) попадали в группу `font-family` (конфликт с `font-sans`/
`font-serif`), а `rounded-mark-sm`/`rounded-button`/`rounded-field-card`
и `shadow-card`/`shadow-mark-elevated` вообще не попадали ни в одну
известную `cn` группу (не конфликтовали даже друг с другом и со
стандартными `rounded-xl`/`shadow-lg` — при попытке переопределить их
через `className` осталось бы **два** класса вместо ожидаемой замены).

### Решение: `web/src/shared/lib/cn.ts`

`cn` (с версии, используемой в проекте) сам компилируется из конфига —
экспортирует `createCn`/`ConfigExtension`/`CreateCnInput` из `cn/config`
именно для этого. Заведена своя обёртка:

```ts
// web/src/shared/lib/cn.ts
import { createCn } from "cn/config";

export const cn = createCn({
  extend: {
    classGroups: {
      "font-size": [{ text: [...] }],   // наши --text-* имена
      "font-weight": [{ font: [...] }], // наши --font-weight-* имена
      rounded: [{ rounded: [...] }],    // наши --radius-mark-*/button/field-card
      shadow: [{ shadow: [...] }],      // наши --shadow-* имена
    },
  },
});
```

`extend` (не `override`) **добавляет** наши имена в существующие группы
`font-size`/`font-weight`/`rounded`/`shadow` рядом со стандартными
Tailwind-паттернами — не переопределяет всю группу и не отключает
валидацию остального. Проверено (см. также live-проверку в ADR 0015):

```
cn("text-hero-foreground", "text-list-row") → "text-hero-foreground text-list-row"  ✓ оба сохраняются
cn("text-list-row", "text-caption")          → "text-caption"                        ✓ конфликт между двумя размерами по-прежнему разрешается
cn("font-sans", "font-620")                  → "font-sans font-620"                  ✓ семейство и вес больше не конфликтуют
cn("rounded-mark-sm", "rounded-full")        → "rounded-full"                        ✓ теперь корректно взаимозаменяемы
cn("shadow-card", "shadow-red-500")          → "shadow-red-500 shadow-card"          ✓ blur и цвет тени — независимые оси, как в реальном Tailwind
```

Почему `extend`, а не безопаснее-выглядящий «переименовать наши утилиты
в отдельное пространство имён через `@utility`» (второй вариант,
предложенный как альтернатива): пришлось бы переименовать каждый класс
во всех местах использования (`text-list-row` → например
`text-size-list-row`) и разойтись с естественными именами Tailwind
(`text-*`/`font-*`/`rounded-*`/`shadow-*`), а сам класс конфликтов
(`cn`) не единственный потребитель этих строк — `@apply`, будущие
статические подсчёты бандла и т.д. ожидают обычные Tailwind-утилиты.
Правка конфигурации `cn` в одном файле — источник истины один раз,
никаких переименований в разметке.

### Что сделано

- Все 22 файла `web/src/shared/ui/*.tsx`, использовавшие
  `import { cn } from "cn"`, переведены на
  `import { cn } from "@/shared/lib/cn"`.
- `web/components.json` → `aliases.utils` указывает на
  `@/shared/lib/cn` — следующий `shadcn add` сам сгенерирует импорт
  нашей функции, а не пакета `cn` напрямую.
- Проверены все места, где через `cn()` в одном вызове сходятся кастомный
  размер текста и цвет (или другая пара токенов одной физической группы):
  `button.tsx` (variant+size — сам баг), `title.tsx` (SIZE+TONE, `Title`
  — `h1` почти каждого экрана), `body-text.tsx` (SIZE+TONE),
  `status-glyph.tsx` (TONE), `section-label.tsx`, `eyebrow.tsx`,
  `caption.tsx`, `inline-error.tsx` — во всех цвет **терялся** при каждом
  рендере (не только при определённых пропах), потому что размер и цвет
  заданы в одной строке класса по умолчанию. `list-card.tsx`
  (`ItemDescription`, дефолт `item.tsx` + `text-caption`+`text-ink-a50`) —
  терялся **размер** (обратное направление: побеждал более поздний
  `text-ink-a50`), возвращая случайно похожий `text-sm` вместо
  `text-caption`. Компоненты, где размер/цвет заданы **статической
  строкой без вызова `cn()`** (например, `<p>` в `hero-card.tsx`,
  весь `pages/*`-слой витрин) — не затронуты: конфликт возникает только
  при runtime-слиянии через `cn()`, обычная Tailwind CSS не «теряет»
  классы, если их не сливает JS.
- Контраст замерен в браузере (`getComputedStyle` + композиция alpha
  поверх фона + относительная яркость WCAG) после фикса: все 5 вариантов
  `Button` (`deep`/`action`/`alert`/`plain`/`heroGhost`) — от 5.77:1 до
  13.75:1; `InlineError` на `--hero` — 5.44:1 (с 2026-10-29 компонент
  залит `--negative` и пишет белым, 5.76:1 — ADR 0012); `HeroCard` текст
  (`text-hero-foreground/60` на `--hero`) — 4.74:1. Все ≥ 4.5:1 (WCAG AA).
  Отдельно найдено (не связано с этим багом, значения не менялись фиксом
  — просто перестали теряться): часть caption/eyebrow-текста на светлом
  фоне использует `text-ink-a40`/`a45`/`a50` и даёт контраст 2.2–3.9:1 —
  осознанный дизайн приглушённых подписей из этого же ADR, пересмотр
  палитры этих токенов на AA — отдельная, не связанная с этим багом
  задача (не решалась здесь, чтобы не менять дизайн-систему негласно).

### Правило на будущее

**Каждый новый именованный токен в `@theme inline`** (`globals.css`) —
новый размер текста, вес шрифта, радиус, тень — **добавляется в
соответствующий список в `web/src/shared/lib/cn.ts`**, иначе он рискует
молча конфликтовать с классом из другой, физически не связанной группы
(это не гипотетический риск — так и был найден баг с кнопкой). Способ
проверить конкретную пару после добавления — `node -e` с `cn` из
`@/shared/lib/cn` (см. примеры выше) до того, как класс уйдёт в разметку.

## Итоговое правило (зафиксировано также в корневом `CLAUDE.md`)

Цвета, размеры шрифтов, радиусы и тени берутся **только** из токенов
(`@theme inline` / `:root` в `web/src/app/styles/globals.css`) —
utility-классами (`bg-hero`, `text-negative`, `text-display`, `font-620`,
`tracking-eyebrow`, `rounded-2xl`, `shadow-card` и т.д.). Хардкод HEX,
`rgba(34,48,44,...)` или магических px-значений размера шрифта/радиуса
вне `globals.css`, файлов иконок (`shared/ui/icons/`, где `currentColor`
+ геометрия — осознанное исключение) и `/styleguide` (эталон сравнения с
прототипом) — не допускается.

## Контраст приглушённого текста: `--ink-a50`/`--ink-a45`/`--ink-a40` подняты до WCAG AA

Найдено при правке этого же участка `globals.css` (раздел «Объединение
классов» выше уже фиксировал этот провал как отдельную, не связанную с
тем багом задачу — вот она): прозрачности `0.5`/`0.45`/`0.4` из
прототипа не проходят WCAG AA (4.5:1) для текста на `--background`
(`#F6F5F3`). `a40` сначала пропустили в первом проходе (проверялись
только `a50`/`a45`, потому что именно их провал изначально указал
пользователь) — сам провал `a40` нашли живой проверкой уже собранного
`/install` (порт 3119, `DEV_MODE=false`): надпись «Учёт служения»
(`Eyebrow`, `web/src/shared/ui/eyebrow.tsx`, класс `text-ink-a40`) —
видимый текст реального экрана v1, не только витрины.

| Токен | Было (α) | Контраст на `--background` | Стало (α) | Контраст на `--background` | Контраст на `--card`/`--popover` (белый) |
|---|---|---|---|---|---|
| `--ink-a50` | 0.5 | 2.90:1 | **0.72** | **5.36:1** | 5.60:1 |
| `--ink-a45` | 0.45 | 2.55:1 | **0.68** | **4.75:1** | 4.94:1 |
| `--ink-a40` | 0.4 | 2.26:1 | **0.67** | **4.69:1** | 4.87:1 |

Решение пользователя: поднять непрозрачность так, чтобы **все три**
токена проходили 4.5:1 на `--background` (самый частый фон приглушённого
текста в проекте — caption/eyebrow/hint/field-label на экранах и в
`shared/ui`), сохранив исходный порядок `a40 < a45 < a50` (каждый
следующий темнее, но все — над порогом). Минимальная альфа для 4.5:1 на
`--background` — ≈0.661; `--ink-a40` взят с запасом, `0.67`, но всё равно
меньше `--ink-a45` (`0.68`) — разница между ними теперь **0.01**
(практически один и тот же цвет на глаз, см. предупреждение ниже). Имена
токенов не менялись, только значения alpha.

**Побочный эффект, о котором предупреждали заранее и который
подтвердился**: `a40` (0.67) и `a45` (0.68) визуально почти неотличимы
— три ступени приглушения из прототипа (0.6/0.5/0.4 условно «средний/
слабый/самый слабый») после подгонки под AA на `--background` сжались в
диапазон 0.67–0.72, потому что нижняя граница диапазона задаётся самим
порогом контраста, а не дизайном. Решение пользователя пока не
принято: токены **не удалены и не переименованы** (могут понадобиться
как самостоятельные семантические имена, даже если рендерятся похоже) —
вопрос «нужны ли все три ступени приглушения дальше» оставлен на потом,
как отдельное решение, не часть этого фикса.

### Исправлено: `Caption` и плейсхолдер `PillForm`

Второй проход (по прямому запросу пользователя, после первого прохода
выше, где оба провала были найдены, но сознательно не тронуты — решение
поднять их оставлено на потом). Тот же принцип, что и для `--ink-a*`:
поднять непрозрачность до порога AA (4.5:1), не меняя цвет-источник и

  (`ComponentsPage`) — проверено, не поплыл (см. живую проверку ниже).
  Было 2.16:1 → стало 4.69:1 на `--background` (то же значение, что и

## Сведение приглушённого текста к двум ступеням: `--ink-muted`/`--ink-faint`

Третий проход (решение пользователя, после того как предыдущий раздел
оставил вопрос «нужны ли все три ступени» на потом). После подгонки под
AA `--ink-a50` (0.72) и `--ink-a45`/`--ink-a40` (0.68/0.67) сжались в
диапазон шириной 0.05 — `a45` и `a40` отличались друг от друга всего на
0.01 и были неотличимы на глаз (см. предупреждение выше). Три
числовых суффикса, привязанные к исходной прозрачности прототипа
(`.5`/`.45`/`.4`), к этому моменту уже не описывали фактическую
прозрачность (`a40` давно не 40%) и создавали ложный выбор при вёрстке
новых экранов — неясно, чем `a45` отличается от `a40`, если визуально
это один и тот же цвет.

### Решение: две ступени, семантические имена

| Ступень | Токен (новый) | Токен (был) | α | Контраст на `--background` | Контраст на `--card`/`--popover` |
|---|---|---|---|---|---|
| «Приглушённый» | `--ink-muted` | `--ink-a50` | 0.72 | 5.36:1 | 5.60:1 |
| «Сильно приглушённый» | `--ink-faint` | `--ink-a45` и `--ink-a40` (слиты в один) | 0.67 | 4.62:1 | 4.79:1¹ |

¹ Контраст `--ink-faint` на `--card`/`--popover` пересчитан для 0.67
(в предыдущей таблице для 0.67 было указано 4.87:1 при опечатке в
подписи «`a40`» — фактическая формула та же: `rgba(34,48,44,0.67)` по
белому даёт относительную яркость, дающую 4.79:1; расхождение в третьем
знаке с прежним черновым числом не меняет вывод «≥4.5:1», перепроверено
живым замером ниже).

Порядок «светлее/темнее» сохранён (`--ink-faint` бледнее/прозрачнее,
`--ink-muted` темнее/плотнее, оба темнее сплошного `--ink`), оба
по-прежнему ≥4.5:1 на самом частом фоне (`--background`).

**Почему смысловые имена, а не `a67`/`a72` (числовой суффикс по новой
альфе)**: числовой суффикс изначально кодировал *дизайнерское* значение
прозрачности из прототипа (40%, 45%, 50% — это были три отдельных
дизайн-решения). После подъёма под AA число в имени перестало быть тем
числом, что реально стоит в `rgba()`, и совпадение с реальной альфой
всё равно не гарантировано на будущее (если контраст ещё раз пересчитают
для другого фона — альфа снова уедет, а имя без причины снова совпадёт
или разойдётся с числом в имени, как уже было один раз с `a40`/`a45`).
Имя по смыслу (`muted`/`faint`) не даёт этого источника рассинхрона:
шкала описывает *степень* приглушения относительно друг друга, а не
конкретное число, которое читатель кода не обязан удерживать в голове,
сверяя с `globals.css`.

**Почему не оставили только один токен вместо двух**: в проекте уже
устоялось два независимых по смыслу применения — «пояснение к контенту»
(`text-caption`, обычно `--ink-muted`, чуть темнее) и «служебный
надзаголовок секции» (`text-eyebrow`, обычно `--ink-faint`, чуть
светлее и заглавными буквами — сам регистр и трекинг уже снижают
«вес» строки, поэтому цвет может быть светлее без потери читаемости).
Слияние в один токен убрало бы это различие там, где оно намеренное
(таблица «Типографическая шкала» выше и стр. `/styleguide`, секция
«Типографика», по-прежнему показывает `caption` на `--ink-muted` и
`eyebrow` на `--ink-faint` рядом — сравнение видно вживую).

### Что переименовано и куда переехали все использования

Все прежние `text-ink-a50` → `text-ink-muted`; все `text-ink-a45` и
`text-ink-a40` (включая ранее заведённый из `text-ink/38` `text-ink-a40`
в `Caption`) → `text-ink-faint`. Проверено (`grep -rn "ink-a40\|ink-a45\|
ink-a50\|ink-a60" web/src` — пусто) — старых имён в коде не осталось.
Затронуты: `shell-loading.tsx`, `InstallCarousel`, `PasswordField`,
`BodyText` (tone `ink`), `ListCard`/`ItemDescription`, `Caption`,
`Eyebrow`, `SectionLabel`, `FieldCard`, `StatusGlyph` (tone `neutral`),
`PillForm` (hint), `global-error.tsx`, витрины `catalog-section.tsx`,
`usage-matrix.tsx`, `ComponentsPage.tsx`, `StyleguidePage.tsx`. Вендорные
токены shadcn — `--muted-foreground: var(--ink-muted)` и
`--chart-5: var(--ink-muted)` (оба и раньше указывали на бывший `a50`,
значение не меняется, меняется только имя источника).

### Судьба `--ink-a55` и `--ink-a60`

Обе — не часть шкалы приглушённого *текста* (в двухступенчатую пару выше
не входят), решение по каждой принято отдельно:

- **`--ink-a55` (0.55) — оставлен как есть**, не переименован и не
  тронут по значению. Единственное применение — цвет иконок-замков
  (`LockClosedIcon`/`LockOpenIcon`) на `/styleguide`, секция «Иконки»:
  это глифы, не текст (контраст текста 4.5:1 к ним неприменим по
  определению — применим порог для *графических объектов/UI-компонентов*
  3:1, который `a55` тоже не проходит, 3.30:1/3.39:1, но это
  предсуществующее состояние демонстрационной, не реальной страницы, вне
  объёма этой задачи). Помечен в исходном комментарии `globals.css` как
  декоративный служебный токен, отдельный от `--ink-muted`/`--ink-faint`.
- **`--ink-a60` (0.60) — удалён.** В отличие от `a55`, у `a60` было **не
  только декоративное** применение: три реальных подписи-«чипа» на
  `/styleguide` (`тень`/`радиус`/`нажать`) и два текстовых поля

  `catalog-section.tsx`); токен `--ink-a60` удалён из `globals.css`
  целиком (`@theme inline` и `:root`).

## Обновление 2026-10-21: токен движения и граница правила про `cn.ts`

В `@theme inline` появилась первая запись не про цвет, размер или форму —
`--animate-value-bump` (`value-bump 140ms ease-out`, ADR 0060): короткий
перескок числа, когда оно изменилось. Это ответ на **другое** событие,
чем `.pressable`: нажатие чувствует палец, изменение числа видит глаз, —
поэтому она не часть механизма нажатия и не его переменная.

Заодно уточнена граница правила «каждый новый именованный токен — сразу в
`shared/lib/cn.ts`». Правило существует ради одной беды: неизвестный
суффикс после `text-`/`font-`/`rounded-`/`shadow-` молча попадает в чужую
группу конфликтов (так `text-list-row` вытеснял цвет). У `animate-*` этой
беды нет, и это **проверено, а не предположено**: `cn("animate-value-bump",
"animate-pulse")` даёт `animate-pulse`, обратный порядок —
`animate-value-bump`, с посторонними классами конфликта нет. Поэтому токен
в `cn.ts` не регистрируется, а в самом `cn.ts` записано, почему.

Правило читать так: регистрировать нужно токены тех групп, где валидатор
снимка Tailwind строгий (размеры, веса, радиусы, тени). Для новой группы —
сначала проверить тестом, потом решать; конфигурация, которая ничего не
меняет, это лишняя сущность для следующего читателя.
