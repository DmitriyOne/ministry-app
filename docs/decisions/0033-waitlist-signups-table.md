# ADR 0033: таблица вайтлиста — доступ только через `security definer`-функцию

## Контекст

ADR 0022 («отправка формы вайтлиста — серверное действие») и ADR 0027
(«email вайтлиста пока пишется только в серверный лог») оставили один и
тот же незакрытый шаг: `persistWaitlistSignup`
(`web/src/features/join-waitlist/api/join-waitlist-action.ts`) пишет
адрес в `console.info`, а не в базу. ADR 0027 назвал это временным и
перечислил три условия перехода. Этот ADR их закрывает.

Одновременно появилось новое продуктовое требование: после записи
человек должен увидеть свой номер в списке («вы такой-то в очереди»), а
при повторной отправке того же адреса — узнать, что он уже в списке, а
не записаться дважды.

Это **первая таблица в проекте** — `backend/supabase/migrations/` до
сих пор содержала только `.gitkeep`. Поэтому решение здесь задаёт
образец модели доступа для всего, что появится дальше, и разобрано
подробнее, чем требовала бы одна таблица с тремя колонками.

## Что именно нужно решить

Форму отправляет анонимный посетитель. В `web` используется только
**publishable**-ключ; секретный (`service_role`/`sb_secret_...`) ключ в
`web` не используется вообще (ADR 0006, правило корневого `CLAUDE.md`).
Значит запрос к базе приходит под ролью `anon` — и ей нужно дать ровно
одну возможность: «добавь этот адрес и верни номер», не дав при этом
ничего прочитать.

## Варианты модели доступа

### A. RLS-политика `insert` для `anon`, запись напрямую из действия

Политика `for insert to anon with check (true)`, вставка через
`.from("waitlist_signups").insert(...)`.

Не подходит по существу задачи: чтобы вернуть номер, нужен `.select()`
поверх вставки (PostgREST возвращает представление только при наличии
привилегии `select`), то есть роли `anon` придётся выдать право читать
таблицу. Одна `select`-политика — и любой посетитель выгружает все
чужие адреса одним запросом. Утечка всей базы ради одного числа.

Отдельно: **grants и policies — два независимых барьера**, и новая
таблица в схеме `public` получает `select/insert/update/delete` для
`anon` и `authenticated` автоматически (в `backend/supabase/config.toml`
`auto_expose_new_tables` не задан, то есть действует значение по
умолчанию `true`). Добавление политики **не отбирает** эти grants —
таблица, защищённая только политиками, всё равно оставляет `anon`
открытый путь на запись. Это касается любого из вариантов ниже и
отдельно учтено в решении.

### B. Запись секретным ключом на сервере

Технически решает всё (ключ обходит RLS), но прямо запрещено правилом
проекта (ADR 0006): секретный ключ в `web` не используется. Не
рассматривался дальше.

### C. Функция `security definer` как единственная дверь — выбрано

Таблица закрыта полностью: RLS включён, политик нет ни одной, grants
отозваны. Единственная точка доступа — функция `public.join_waitlist`,
выполняемая с правами владельца, с `execute` только для `anon`. Она
сама нормализует адрес, решает «вставить или уже есть» и возвращает
ровно два поля: признак «уже был» и номер. Чужие адреса наружу не
выходят ни при каком вызове, потому что функция их и не возвращает.

Это рекомендуемый Supabase образец для публичной записи в закрытую
таблицу (документация Supabase, «Row Level Security → Grants and
policies»; проверено через context7).

## Решение

### Таблица

```sql
create table public.waitlist_signups (
  id         bigint generated always as identity primary key,
  email      text not null,
  created_at timestamptz not null default now(),
  constraint waitlist_signups_email_key unique (email),
  constraint waitlist_signups_email_normalised check (email = lower(btrim(email))),
  constraint waitlist_signups_email_shape check (email like '%_@_%.__%' and length(email) <= 254)
);

alter table public.waitlist_signups enable row level security;
revoke all on table public.waitlist_signups from anon, authenticated;
```

- **Ни одной RLS-политики — это и есть защита, а не упущение.** RLS
  включён, политик нет → прямого доступа нет ни у кого, кроме владельца
  (и `service_role`, который RLS обходит, но в `web` не используется).
  Если позже у таблицы появится политика, это должно быть осознанным
  решением с отдельной записью, а не побочным эффектом правки миграции.
- **`revoke all` обязателен** — по причине, разобранной в варианте A:
  grants выданы при создании таблицы автоматически и политиками не
  отбираются.
- **`check`-ограничения — последняя линия обороны, не замена
  валидации.** Адрес уже проверен zod-схемой и на клиенте, и на сервере
  (`features/join-waitlist/model/schema.ts`, одна схема на обе стороны).
  Ограничения в таблице гарантируют, что ненормализованный или
  бессмысленный адрес не ляжет в базу даже в обход функции. 254 — предел
  длины адреса по RFC 5321.
- Больше никаких колонок (`utm_*`, источник, локаль) — YAGNI. ADR 0027
  упоминал их как «возможно понадобится позже»; пока не понадобилось,
  добавлять нечего.

### Функция

```sql
create or replace function public.join_waitlist(p_email text)
returns table (already_joined boolean, list_position bigint)
language plpgsql security definer set search_path = ''
as $$
declare
  v_email   text := lower(btrim(p_email));
  v_id      bigint;
  v_already boolean := false;
begin
  select s.id into v_id from public.waitlist_signups s where s.email = v_email;

  if v_id is not null then
    v_already := true;
  else
    insert into public.waitlist_signups (email) values (v_email)
    on conflict (email) do update set email = excluded.email
    returning id into v_id;
  end if;

  return query
    select v_already,
           (select count(*) from public.waitlist_signups s where s.id <= v_id);
end;
$$;

revoke all on function public.join_waitlist(text) from public;
grant execute on function public.join_waitlist(text) to anon;
```

Четыре решения внутри, каждое не очевидно:

1. **`set search_path = ''`** — обязательная гигиена для
   `security definer`: без неё вызывающая сторона может подсунуть свой
   `search_path` и подменить то, что функция считает `waitlist_signups`,
   получив исполнение под правами владельца. Отсюда полные имена
   `public.*` внутри тела.
2. **Статус возвращается в ответе, а не бросается исключением.**
   Документация Supabase предупреждает: `raise exception` с кастомным
   `errcode` легко попадает в `40001` (`serialization_failure`), и тогда
   PostgREST считает ошибку временной и **бесконечно ретраит
   транзакцию** — CPU в потолок, логи в мусоре, один HTTP-запрос
   превращается в несколько независимых транзакций. Поле
   `already_joined` в payload обходит эту ловушку целиком, и заодно
   избавляет действие от разбора SQL-кодов ошибок.
3. **`on conflict ... do update`, а не `do nothing`.** При гонке двух
   одинаковых адресов `do nothing` вернул бы `null`, и пришлось бы
   повторно искать строку; а если конкурирующая транзакция откатилась,
   поиск не нашёл бы ничего и номер стал бы `null`. `do update set email
   = excluded.email` всегда возвращает строку — пути с `null` просто не
   существует. Цена — холостая перезапись того же значения в редком
   случае гонки.
4. **`list_position`, а не `position`** — `position` в Postgres
   зарезервировано (это встроенная функция), с таким именем поле
   приходилось бы квотировать в каждом обращении.

`revoke ... from public` перед `grant` — не формальность: Postgres по
умолчанию выдаёт `execute` роли `public`, то есть всем. Без `revoke`
«выдали только `anon`» было бы иллюзией.

### Номер в списке — счётчик, а не `id`

Возвращается не `id`, а `count(*) where id <= v_id`.

`id` — последовательность, и она расходует значения на неудачных
вставках и откатах. То есть `id` растёт быстрее, чем число людей в
списке: «вы 47-й» при двенадцати записях. Счётчик на таком масштабе
бесплатен, а число не врёт. `id` остаётся ключом, `list_position` — тем,
что человек видит.

### Поведение при повторной отправке

Повторная отправка того же адреса — **успех с существующим номером**
(«You're already #12 on the list»), не ошибка под полем. Человек видит,
что он в списке, и не пробует снова; записи-дубликата при этом не
возникает.

### Серверное действие и форма

- `persistWaitlistSignup` → `joinWaitlistRecord(email)`: вызов
  `rpc("join_waitlist", { p_email })` через
  `createServerSupabaseClient` (`shared/api/supabase/server.ts`).
- `JoinWaitlistActionState` получает `position?: number` и
  `alreadyJoined?: boolean`.
- **`console.info` с адресом удаляется полностью** — третье условие ADR
  0027. Вместо него лог факта без значения, тем же способом, что уже
  принят для IP посетителя (ADR 0026: в лог идёт скоуп/факт, не
  значение).
- Словарь: вместо одного `successText` два ключа с параметром
  `{position}` — `successText` и `alreadyJoinedText`.
- `PillForm` (`shared/ui/pill-form.tsx`) получает проп `isPending`: поле
  становится `readOnly`, на `<form>` — `aria-busy`, в кнопку добавляется
  `Spinner` (`shared/ui/spinner.tsx`) рядом с уже существующей подменой
  подписи на `submitButtonPending`. **`readOnly`, а не `disabled`:**
  `disabled` выбрасывает поле из порядка табуляции и его значение
  перестаёт озвучиваться скринридером — человек в момент отправки теряет
  то, что он ввёл, из доступного дерева. `readOnly` блокирует ввод,
  сохраняя и фокус, и озвучивание.
- Блокировка ввода на время отправки — общее правило для форм проекта,
  не частный случай этой. Применяется к `PillForm`, потому что другие
  поля (`FieldRow`, `PasswordField`) пока не стоят ни в одной реальной
  форме; тот же проп заводится в них, когда такая форма появится.

### Уведомление о конфиденциальности

Email вайтлиста — отдельная цель обработки, которой нет в текущем тексте
`/privacy` (ADR 0031: там только email учётной записи и записи о
служении). В том же изменении:

- раздел 1 («What we store») — строка про адрес, оставленный до запуска;
- раздел 2 («Why we store it») — цель («сообщить, когда приложение будет
  готово») и срок («до запуска, затем удаляется»);
- основание — то же согласие Art. 6(1)(a), новой правовой конструкции не
  требуется.

Текст и база правятся одним изменением намеренно: таблица, собирающая
адреса, и уведомление, которое о них молчит, не должны существовать
одновременно даже недолго.

## Последствия

- Условие ADR 0027 закрыто: адрес больше не лежит в логах Vercel
  открытым текстом, появились структурированный доступ («кто оставил
  email») и возможность удаления по требованию.
- Образец доступа для следующих таблиц задан: RLS включён, политик нет,
  grants отозваны, наружу выходит только явно разрешённая функция. Любое
  отступление от него — отдельное решение с отдельной записью.
- `database.types.ts` перестаёт быть пустым — требуется `pnpm db:types`
  после применения миграции.
- Возвращать нечего, кроме номера: даже если функция когда-нибудь
  понадобится авторизованной роли, расширять её придётся осознанно, а не
  «заодно».

### Оговорка 1: повторная отправка остаётся признаком, по которому можно проверить адрес

Разный текст при «записали» и «уже в списке» означает, что кто угодно,
зная чей-то адрес, за одну отправку узнаёт, что этот человек в списке
ожидания приложения для учёта часов служения — то есть делает вывод о
его религиозной принадлежности. Это та самая особая категория данных
Art. 9, вокруг которой построено всё уведомление о конфиденциальности
(ADR 0031).

Выбрано осознанно: альтернатива (неотличимый ответ в обоих случаях) не
даёт человеку понять, что он уже записан, и он продолжает отправлять
форму. Смягчающее: рейт-лимит 3/час на IP и 15/мин глобально (ADR 0026)
делает перебор по словарю бессмысленным — но против проверки одного
конкретного адреса не помогает, для неё нужна ровно одна попытка.

Если список станет публично анонсированным и заметным, это стоит
пересмотреть в пользу неотличимого ответа.

### Оговорка 2: номер сдвигается после удаления

Номер считается среди существующих строк, поэтому после удаления записи
по требованию (право на забвение) номера всех, кто записался позже,
сдвинутся вниз на единицу. Это цена честного числа; альтернатива — `id`
с дырами, который врёт сразу и всегда. Номер не обещан как постоянный
идентификатор и нигде не используется как ключ — только как
человекочитаемое «вы такой-то по счёту» в момент записи.
