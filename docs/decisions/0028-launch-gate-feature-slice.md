# ADR 0028: `ShellGate` переезжает из `app/` в `features/launch-gate`

## Контекст

`ShellGate`/`ShellLoading`/`ShellNoscriptFallback` жили в
`web/src/app/layout/` рядом с `root-layout.tsx`/`providers.tsx` — там же,
где и настоящая инициализация приложения (корневая разметка, провайдеры,
глобальные стили, генерация `metadata`/`viewport`).

Пользователь указал на архитектурную проблему: слой `app` в FSD — это
инициализация (провайдеры, корневой макет, стили, всё то, что нужно один
раз при старте приложения и не несёт собственной продуктовой логики), а
`ShellGate` решает продуктовую задачу — «определить, каким способом
человек запустил приложение (со значка на домашнем экране или обычной
вкладкой браузера), и в зависимости от этого либо показать его, либо
отправить на `/install`». Это сценарий с собственным решением и
собственным побочным эффектом (`window.location.replace`), а не
инициализация — по определению FSD `app` не должен нести такую логику,
для неё есть слой `features`.

## Решение

Слайс `features/launch-gate` — три файла переехали без изменения
поведения, но с разделением по сегментам `ui`/`model` (как в остальных
слайсах `features` проекта — `install-sheet`, `install-carousel`,
`join-waitlist`: `model/` — хуки с состоянием и эффектами, `ui/` —
компоненты, которые их используют):

```
web/src/features/launch-gate/
├─ model/
│  └─ use-launch-gate.ts     — вынесенная логика из ShellGate: `phase`,
│                               эффект с определением standalone/
│                               редиректом, таймер-страховка
├─ ui/
│  ├─ launch-gate.tsx         — ShellGate → LaunchGate: рендер оверлея/
│  │                            контента по `phase` из хука
│  ├─ launch-loading.tsx      — ShellLoading → LaunchLoading
│  └─ launch-noscript-fallback.tsx — ShellNoscriptFallback →
│                                      LaunchNoscriptFallback
└─ index.ts                   — публичный API: LaunchGate, LaunchLoading,
                                 LaunchNoscriptFallback
```

### Почему `launch-gate`, не `shell-gate`

Имя `shell-gate` описывало реализацию («переключатель приложения-
оболочки»), не продукт. С точки зрения продукта этот сценарий отвечает
на один вопрос — «человек запустил приложение как установленное (со
значка) или как обычную веб-страницу?» — и маршрутизирует в зависимости
от ответа. `launch-gate` называет именно это: гейт на способе запуска
(«launch»), не техническую деталь («shell» — оверлей/контент как две
DOM-обёртки, случайность конкретной текущей реализации, ADR 0019 уже
трижды меняло саму механику переключения под этим именем). Слайс
называется по тому, что он **решает**, а не по тому, **как** сейчас
устроен внутри — второе может снова смениться (уже менялось три раза,
ADR 0019), имя слайса от этого меняться не должно.

Компоненты переименованы вслед за слайсом (`ShellGate` → `LaunchGate` и
т.д.) — оставлять компонент `ShellGate` внутри слайса `launch-gate` было
бы внутренне противоречиво (то же имя, что раньше указывало на файл
`shell-gate.tsx`, а не на назначение). DOM id/классы (`#shell-loading`,
`.shell-loading-exit`, `.shell-content-enter` в `globals.css`) **не
переименованы** — это устоявшиеся, никак не связанные с FSD-слоями CSS-
идентификаторы; переименование потребовало бы синхронной правки
`globals.css` (`@keyframes`, `transition`, кастомные свойства — тонкая
механика, задокументированная в ADR 0019, с историей найденных вживую
багов) без единой архитектурной выгоды — чистый риск ради
косметического единообразия имён.

### Что осталось в `app/` и где граница

`app/layout/root-layout.tsx` — единственное место, которое **подключает**
`LaunchGate` (импорт из `@/features/launch-gate`, разрешённое направление
— `app` может импортировать из `features`, слой строго ниже). Сам
`root-layout.tsx` никакой логики про запуск/standalone не содержит — он
решает только «показывать `LaunchGate` или пропускать детей напрямую»
по `env.DEV_MODE` (серверное значение, инициализационное по своей
природе — какую ветку разметки собрать при рендере, не что делать в
ответ на клиентское событие). Это ровно та граница, которую просил
пользователь: `app` — провода и разводка (какой компонент куда
подключен), `features` — сама логика решения.

`use-launch-gate.ts` (`model/`) вынесен из `shell-gate.tsx` отдельным
файлом-хуком — по тому же принципу, что уже применён в
`install-sheet`/`install-carousel`/`join-waitlist`: `model/` содержит
состояние и эффекты, `ui/` — компонент, который их использует и
рендерит. `launch-gate.tsx` (`ui/`) стал тоньше — вызывает
`useLaunchGate()`, дальше только `JSX` по `phase`.

## Проверка

- `pnpm lint` (ESLint + `steiger`, проверка границ FSD) — чисто, слайс
  проходит все правила `@feature-sliced/steiger-plugin` (public API
  только через `index.ts`, импорт `app → features` — разрешённое
  направление вниз, никаких кросс-импортов между слайсами `features` на
  одном уровне).
- `pnpm typecheck`, `pnpm test`, `pnpm build` — чисто, поведение
  идентично (перенос и разбиение на сегменты, без изменения логики
  `useLaunchGate`/`LaunchGate`).
- Все ссылки на старые имена/пути (`ShellGate`, `shell-gate.tsx`,
  `ShellLoading`, `ShellNoscriptFallback`) в комментариях по всему
  проекту (`globals.css`, `shared/ui/button.tsx`, `features/copy-link/
  ui/copy-link-button.tsx`, `pages/install-app/ui/InstallAppScreen.tsx`,
  `CLAUDE.md`) обновлены на новые — grep по старым именам в `web/src` и
  `web/app` не находит ничего, кроме исторических упоминаний в
  `docs/decisions/0019-*.md` (описывает решение на момент, когда файл
  ещё жил в `app/` — не переписывается задним числом, см. правило ADR
  этого репозитория: новые решения фиксируются новыми записями, старые
  не переписываются).
