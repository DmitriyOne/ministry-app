# ADR 0013: Формы и доступность

## Обновление: пер-полевые ошибки, блокировка кнопки, рамка+кольцо

Три замечания по живому примеру `validation-form-demo.tsx` на витрине
`/components` (общий список ошибок над формой вместо ошибок под полями,
активная кнопка при невалидной форме, только рамка без кольца у ошибки).
Все три — про один и тот же узел (`FieldRow`/`PasswordField`), правки
внесены туда, а не точечно в демо.

### 1. Ошибки — под полем, не общим списком

Раньше `FieldRow`/`PasswordField` принимали `invalid`/`errorId` и
рассчитывали на один `FieldError` на всю форму (витрина сама решала,
куда его поставить — оказалось, что над формой, что и было замечанием).
Теперь оба компонента принимают `errors?: FieldErrorItem[]`
(`FieldErrorItem` — тип из `field.tsx`, теперь экспортирован) и сами
рендерят свой `FieldError` сразу под контролом, с собственным `id`
(`useId`), на который ссылается `aria-describedby` того же поля.
`invalid` (`Boolean(errors?.length)`) считается внутри компонента, наружу
как проп не выходит — единственный источник правды об ошибке поля теперь
`errors`, не два синхронизируемых пропа. Вызывающая сторона
(`validation-form-demo.tsx`) передаёt `fieldState.error ? [fieldState.error]
: undefined` из `Controller` — `fieldState.error` уже нужной формы
(`{message?: string}`).

`FieldCard` не тронут: `FieldError` — третий child внутри уже
существующего `Field` (`gap-1.25` между лейблом/контролом/ошибкой),
раскладка строк и разделителей между `FieldRow` в `FieldCard`
(`Children.toArray` + `Separator`) не меняется — ошибка увеличивает
высоту своей строки, не затрагивает соседние.

### 2. Кнопка отправки блокируется, пока есть ошибки

`ValidationFormDemo`: `isDisabled={Object.keys(formState.errors).length >
0}` на `<Button type="submit">` (react-aria `isDisabled`, не `disabled` —
`Button` уже принимает `ButtonPrimitiveProps` от `react-aria-components`,
проп был доступен и раньше через `...props`, просто не использовался).

Режим валидации не менялся: `mode: "onSubmit"`, `reValidateMode:
"onChange"` (тот же выбор, что описан ниже в исходном тексте ADR, и
проверен заново). Следствие важно для формулировки задачи «не блокировать
пустую форму без нужды»: react-hook-form не валидирует нетронутую форму
сама по себе — до первого submit `formState.errors` пуст независимо от
того, что поля пустые, поэтому кнопка остаётся активной на пустой форме.
После первого submit ошибки появляются и дальше пересчитываются на
каждое изменение поля (`reValidateMode: "onChange"`), поэтому кнопка
блокируется сразу и разблокируется в момент, когда `errors` становится
пустым — без отдельного `isSubmitted`-флага, который раньше нужен был
только для решения «показывать общий список ошибок или нет».

Проверено вживую (Playwright, `/components`): submit пустой формы →
кнопка получает `disabled` (настоящий HTML-атрибут, не только
визуально приглушённый вид); ввод корректной почты → ошибка email
пропадает, ошибка пароля остаётся, кнопка всё ещё `disabled`; ввод
корректного пароля → обе ошибки пропадают, `btn.disabled === false`.

### 3. Состояние ошибки — рамка и кольцо, в одном месте

Раньше `invalid &&` добавлял только `border border-negative` на
обёртку строки условно (без кольца); `Input` (`shared/ui/input.tsx`,
вендорный shadcn) параллельно нёс свои классы
`aria-invalid:border-destructive aria-invalid:ring-3
aria-invalid:ring-destructive/20`, которые FieldRow/PasswordField
частично перебивали (`border-0`), а частично — нет (`ring-*` не был
перебит ничем, мог непредсказуемо накладываться на кольцо обёртки).
Два источника одного и того же состояния в двух разных компонентах —
и есть претензия «стили ошибки дублируются».

Решение — один источник: `data-invalid` (boolean, тот же паттерн,
что уже использует `fieldVariants` в `field.tsx`) на обёртке-`div`
вокруг `Input`/кнопки-глаза, и вся визуальная реакция — классами
`data-[invalid=true]:` на этой обёртке:

```
border border-transparent -mx-2 -my-1 px-2 py-1 transition-colors
focus-within:border-ring focus-within:ring-3 focus-within:ring-ring/50
data-[invalid=true]:border-negative data-[invalid=true]:ring-3
data-[invalid=true]:ring-negative/20
```

`border-transparent` (не отсутствие рамки) держится всегда, не только
при ошибке — так переключение invalid/valid не двигает соседние
элементы (рамка уже учтена в размере). `Input` внутри получает
`ring-0 focus-visible:ring-0 focus-visible:border-0 aria-invalid:border-0
aria-invalid:ring-0` — гасит свои собственные classes подряд, чтобы
рамка/кольцо рисовались только на обёртке. `aria-invalid` на самом
`<input>` остаётся — это семантика для скринридеров, не стилизация (её
несёт `data-invalid` на обёртке).

Фокус и ошибка не конфликтуют по построению: `focus-within:` идёт в
классах раньше `data-[invalid=true]:` — при одновременном фокусе и
ошибке побеждает последний в источнике (`data-[invalid=true]`), как и
в исходном шаблоне shadcn (`focus-visible:` перед `aria-invalid:` в
`input.tsx`). Проверено вживую: клик в невалидное поле после submit —
рамка и кольцо остаются терракотовыми (`--negative`), не переключаются
на `--ring` (приглушённый зелёный) фокуса.

Цвета — токены, не хардкод: `border-negative`/`ring-negative/20` (см.
ADR 0011, `--negative` = `--palette-terracotta`, тот же цвет, что и
`--destructive`), `border-ring`/`ring-ring/50` для обычного фокуса.

Скриншоты (`.playwright-mcp/` корня репозитория):
`validation-form-errors-per-field.png` (submit пустой формы — ошибки под
полями, рамка+кольцо, кнопка `disabled`), `validation-form-focus-and-error.png`
(фокус на невалидном поле — кольцо остаётся красным), `validation-form-all-valid.png`
(оба поля исправлены — ошибок нет, кнопка снова активна).

## Обновление: переход на React Aria (`aria-nova`)

После первой версии этого ADR стек переехал с `@base-ui/react` на
`react-aria-components` (`web/components.json` → `"style": "aria-nova"`).
Причина: `aria-nova` — вариант shadcn-реестра с более полным покрытием
интерактивных примитивов (в первую очередь — полей форм и их состояний
валидации) поверх React Aria, которым и написана эта библиотека
компонентов. Следствия:

- **API событий другое.** `react-aria-components` даёт `onPress` вместо
  `onClick`, `isDisabled` вместо `disabled` и т.п. на своих примитивах
  (`Button`, `Link`, `Input` — везде, где написано `import {...} from
  "react-aria-components"`). Обычный `<button>`/`<input>` (например,
  toggle-кнопка глаза в `PasswordField`) — не react-aria-примитив, там
  остаётся нативный `onClick`. Смешивать `onClick` и `onPress` на одном
  и том же react-aria-компоненте — ошибка; проверено `grep -rn "onClick"
  src` — единственное совпадение вне вендорных файлов на нативном
  `<button>`.
- **Клиентская граница.** Любой файл, импортирующий
  `react-aria-components` (`button.tsx`, `input.tsx`, `label.tsx`,
  `separator.tsx`, `item.tsx`, `field.tsx` — использует `Label`/
  `Separator` — и `screen-header.tsx` — использует клиентский `Button`,
  но сам хуков не вызывает) — либо сам помечен `"use client"`, либо
  собирается в клиентский бандл через импорт из уже клиентского файла.
  Помечены `"use client"`: `button.tsx`, `input.tsx`, `label.tsx`,
  `separator.tsx`, `item.tsx`, `field.tsx`, `password-field.tsx`,
  `pill-form.tsx` и демо на витрине, использующие `useState`/
  `useForm`/`Controller`. **Не** помечены (остаются серверными
  композициями поверх клиентских примитивов, сами без хуков):
  `screen-header.tsx`, `scroll-state.tsx`, каркасы состояний, текстовые
  роли, `field-card.tsx`, `list-card.tsx`, `hero-card.tsx`, `app-mark.tsx`
  и т.д.
- **`ErrorList` удалён.** Использовался `Alert`/`AlertDescription` +
  свой `<ul>`/`<li>`; заменён на штатный shadcn `FieldError` из
  `field.tsx` — он сам сворачивает массив ошибок в `<ul
  className="list-disc">/<li>`, когда их больше одной, и просто текст,
  когда она одна. `FieldRow`/`PasswordField` не изменились: те же
  `invalid`/`errorId`, только текст ошибок теперь рендерит `FieldError`,
  не свой компонент. Раздел «Как выглядят ошибки» ниже обновлён.
- **`ScreenHeader` и `onBack` через границу RSC.** `ScreenHeader` не
  использует хуков и намеренно остался серверным — `onBack` он
  прокидывает в клиентский `Button` как проп. Это безопасно, пока
  `ScreenHeader` вызывается из клиентского дерева (там, где вызывающий
  компонент/страница уже `"use client"`, — импорт серверного файла из
  клиентского делает его частью клиентского бандла, обычная композиция).
  Ограничение: настоящий Server Component (страница без `"use client"`)
  **не может** передать в `onBack` функцию-замыкание — React не умеет
  сериализовать функции через границу RSC в обычный (не Server Action)
  проп клиентского компонента. На практике это не проблема: работающий
  «назад» всегда требует клиентской навигации (`router.back()` и т.п.),
  то есть вызывающая страница и так обязана быть `"use client"`, прежде
  чем у неё появится осмысленный `onBack`. Если это когда-нибудь
  перестанет быть верным — решение: пометить `ScreenHeader`
  `"use client"` явно, а не оставлять неявную гарантию.

## Контекст

Ревью ADR 0012 нашло шесть проблем: заголовки без осмысленных уровней,
доступность только в трёх компонентах из ~20, текстовый символ `‹` вместо
иконки, отсутствие единого подхода к валидации форм, вручную
продублированные `Button`/поле в `PillForm`, неясная граница между
`shared/ui` и будущими `features`. Этот ADR фиксирует решения по всем
шести пунктам, чтобы при сборке реальных экранов (следующий этап) не
плодить разночтений.

## Валидация форм: react-hook-form + zod

Решение пользователя. Установлены `react-hook-form` и
`@hookform/resolvers` (резолвер `zodResolver`, `zod` уже был в
зависимостях).

**shadcn `form` не установлен.** Актуальный shadcn-реестр (стиль
`aria-nova`, тот же, что у проекта) для React Hook Form не даёт отдельный
компонент `form.tsx` с контекстом (`FormField`/`FormItem`/`useFormField` —
это устаревший radix-паттерн из старых версий shadcn); текущий подход
shadcn — использовать `Controller` из react-hook-form напрямую с
компонентами `Field`/`FieldLabel`/`FieldError` из `field.tsx` (уже
установлен, см. ADR 0012) и «полной свободой над разметкой» (цитата из
их документации). Мы используем ровно этот подход: `Controller` +
`zodResolver`, но с *нашими* `FieldRow`/`PasswordField` вместо
generic `Field`+`Input` конструкции по месту — они и так уже дают
лейбл, `aria-invalid`, `aria-describedby`.

### Как выглядят ошибки

**Устарело, см. «Обновление: пер-полевые ошибки…» в начале файла** —
раздел ниже описывает промежуточный вариант с одним общим `FieldError`
на форму; актуальный вариант — свой `FieldError` под каждым полем.

Три части:
- **`FieldError`** (`shared/ui/field.tsx`, штатный shadcn-компонент —
  см. «Обновление» выше) — принимает `errors: {message?}[]`, сам
  сворачивает их в текст (одна ошибка) или `<ul
  className="list-disc">/<li>` (несколько), `role="alert"`,
  деструктивная окраска (уже равна `--negative`). Каждый `FieldRow`/
  `PasswordField` рендерит свой `FieldError` под контролом с id (`useId`)
  внутри себя — не форма собирает один общий блок на все поля.
- **`FieldRow`/`PasswordField`** принимают проп `errors?:
  FieldErrorItem[]`. `invalid` (красит рамку+кольцо в `--negative`,
  ставит `aria-invalid="true"` на `<input>`) считается из `errors`
  внутри компонента, наружу отдельным пропом не выходит; `aria-describedby`
  тоже собирается внутри и указывает на собственный `id` `FieldError`
  этого поля.
- **`InlineError`** (уже был) — не переиспользован для списка: это
  одиночное сообщение на `--hero`, другая роль, другой контекст (см.
  ADR 0012).

### Где живёт схема и `useForm`

**Не в `shared/ui`.** Схема `zod`, `useForm`, тексты ошибок конкретной
формы — в слайсе, которому принадлежит экран. Для живого примера на
витрине это `web/src/pages/components/ui/validation-form-demo.tsx` —
слайс витрины, не `shared/ui`. На реальных экранах (следующий этап) то
же самое место займёт `features` (например, `features/join-whitelist` для
`PillForm`, `features/sign-in` для формы входа) — см. границу `shared/ui`
ниже.

### `reValidateMode: "onChange"` — проверено вживую

`useForm({ resolver: zodResolver(schema), mode: "onSubmit", reValidateMode:
"onChange" })`. Это и есть значение по умолчанию react-hook-form
(`reValidateMode` по умолчанию `"onChange"`) — указано явно для
читаемости, не как обход бага.

Проверено в браузере (Playwright), не только по документации, повторно
после перехода на React Aria (см. «Обновление» выше):
1. Пустая форма → submit → `FieldError` показывает список ошибок
   (`<ul>/<li>` при двух и более), оба поля красные, `aria-invalid="true"`,
   `aria-describedby` совпадает с `id` `FieldError`.
2. Ввод в поле «Эл. почта» (`fill` с валидным значением) → без повторного
   submit ошибка этого поля пропала из списка и рамка вернулась к
   обычной; ошибка пароля осталась (поле ещё не тронуто). Скриншоты в
   `.playwright-mcp/validation-errors.png` (оба поля invalid) и
   `.playwright-mcp/validation-fixed-and-eye-toggle.png` (email исправлен,
   пароль всё ещё invalid).

## Заголовки: правило уровней

- `Title` — как и раньше, `as` по умолчанию `h1` (это главный заголовок
  state-экрана: 404/500/Coming soon/Вход).
- `TextBlock` — проп `titleAs`, пробрасывается в `Title`. Без него
  экран, где `TextBlock` — единственный смысловой заголовок, получает
  `h1` (как раньше); при вложении в чужой контекст вызывающая сторона
  обязана передать `titleAs`.
- `HeroCard` — `titleAs`, по умолчанию `h2` (открывает контентный экран,
  h1 которого — уже не `TextBlock`, а заголовок самого экрана выше).
- `ListRow` — `titleAs`, по умолчанию `h3` (строка списка внутри
  контентного экрана, на уровень ниже `HeroCard`).
- `SectionLabel` — стал заголовком (`as`, по умолчанию `h2`), а не
  `<p>`: подписывает раздел контента, это семантически заголовок.

На витрине (`/components`) эти умолчания почти везде переопределены
(`titleAs="h4"`/`"h5"`), потому что живые примеры вложены глубоко внутрь
собственной структуры страницы (`h1` страницы → `h2` раздела каталога →
`h3` имя компонента → `h4`/`h5` заголовок внутри примера) — умолчания
компонентов рассчитаны на реальный экран, не на витрину.

**Проверено `document.querySelectorAll('h1,h2,h3,h4,h5,h6')`** на
`/components`: один `h1`, дальше `h2` (разделы) → `h3` (имена
компонентов) → `h4`/`h5` (заголовки внутри примеров, включая вложенный
`HeroCard`→`ListRow` в примере `ScrollState`, который поэтому идёт на
`h4`→`h5`). Полная последовательность — 44 заголовка, ни одного скачка
через уровень при движении вниз, ни одного второго `h1`.

## Лендмарки

- `CenteredState`, `TopAndBottomState` — уже были `<main>`.
- `ScrollState` — прокручиваемая область стала `<main>` (была `<div>`),
  `ScreenHeader` — `<header>` (уже был). На экране, собранном из одного
  каркаса, `<main>` ровно один.
- `ScreenHeader` использует `<header>` и настоящую кнопку `<button>`
  (через `Button`) — было и осталось.

## Декоративные иконки и знаки

- `AppMark` — `aria-hidden="true"` по умолчанию (почти всегда стоит
  рядом с видимым текстовым заголовком). Проп `label?: string` снимает
  `aria-hidden` и добавляет `role="img" aria-label={label}` — для
  случая, когда знак — единственный логотип без соседнего текста.
- `ListRow` — иконка-плитка (`icon`) получила `aria-hidden="true"`:
  смысл несёт заголовок строки, иконка декоративна.
- `ChevronLeftIcon` (`shared/ui/icons/chevron-left-icon.tsx`) заменил
  текстовый символ `‹` в `ScreenHeader` — геометрия как у остальных
  иконок (`viewBox 24`, штрих `1.7`, круглые окончания, как в
  `eye-icon.tsx`). `aria-label="Назад"` (переопределяемый пропом
  `backLabel`) остался на кнопке, иконка внутри декоративна по факту
  (не помечена явно `aria-hidden`, так как `<svg>` без `role` и так не
  участвует в accessible name кнопки при наличии `aria-label` на самой
  кнопке).
- `StatusGlyph` — код (`"404"`/`"500"`) остаётся обычным видимым текстом,
  не скрыт. Потенциальное дублирование с заголовком экрана: в каталоге
  404/500-экраны показывают и `StatusGlyph` (код), и `Title` («Страница
  не найдена» / текст ошибки) — это разные по смыслу тексты (код vs.
  описание), не дублирование. Риск дублирования появится, если на
  реальном экране рядом добавят ещё и `Caption` вида «Код ошибки:
  SRV-500» (как в каталоге для 500) — тогда код будет назван дважды.
  Рекомендация на следующий этап: либо `Caption` для 500 несёт
  технический ID инцидента (`SRV-500`, не сам HTTP-код), либо
  `StatusGlyph` получает `aria-hidden` с пояснением кода только в
  `Title`/`Caption`. Решение отложено до сборки самого экрана 500.

## Дублирование: `PillForm`, `font-500`

- `PillForm` больше не рисует свою кнопку и своё поле: кнопка — общий
  `Button` (`variant="deep" size="role"`, радиус/высота переопределены
  через `className` на капсулу), поле — общий `Input` (shadcn). Стили
  кнопки теперь живут в одном месте (`button.tsx`).
- Все веса в `shared/ui`, где раньше стоял Tailwind `font-medium`
  (500 — совпадает численно, но был подключён как именованная утилита,
  а не токен), переведены на `font-500` — новый токен
  `--font-weight-500` (см. ADR 0012). Правило: в `shared/ui` веса — всегда
  через `font-500…font-640`, никогда не смешивать с `font-medium`/
  `font-semibold`/`font-bold` даже при совпадении числа.

## Граница `shared/ui`: что можно, что нельзя

Зафиксировано по итогам ревью — явный список на будущее.

**Можно в `shared/ui`:**
- локальное состояние самого элемента интерфейса: открыт/закрыт,
  показан/скрыт пароль (`PasswordField`), фокус — то же самое, что
  делают сами компоненты shadcn/ui (`Dialog`, `Accordion` и т.д.),
  которые живут в этом слое;
- `useId` и подобные хуки идентичности/доступности;
- обработчики, которые просто пробрасываются наружу (`onClick`,
  `onSubmit`, `onValueChange`) — компонент их вызывает, но не решает,
  что в них происходит;
- необязательный неуправляемый режим (`defaultValue` + внутренний
  `useState`) поверх управляемого — как у `PillForm`/`PasswordField`.

**Нельзя в `shared/ui`:**
- бизнес-сценарии (запись в вайтлист, вход, любой запрос к Supabase);
- знание о доменных сущностях;
- схемы валидации конкретных форм приложения (`zod`-схемы, правила
  вида «пароль ≥ 6 символов» — это принадлежит форме, не полю);
- захардкоженные доменные тексты (`PillForm` больше не хранит «Спасибо!
  Мы напишем вам…» — это `successText`, проп).

**Практическое следствие:** когда у компонента `shared/ui` появляется
сценарий с данными (например, `PillForm` на реальном Coming soon начнёт
писать email в Supabase), сам сценарий — `useState`/`useForm` с
конкретной схемой, вызов API, обработка ответа — переезжает в
соответствующий слайс `features` (например, `features/join-whitelist`),
а `shared/ui` продолжает поставлять только «глупую» вёрстку
(`PillForm`, `FieldCard`/`FieldRow`, `FieldError`, `Button`), ничего в
`shared/ui` при этом не меняется.

## Стрелочные функции — включая вендорные файлы

Все функции и компоненты проекта — стрелочные (`export const X = (...)
=> ...`), **без исключения для файлов `shadcn add`**. Это решение
поменялось относительно первой версии этого ADR (там вендорные файлы
были оставлены как сгенерировал CLI, `function X(...)`) — пересмотрено
в пользу единообразия всей кодовой базы; расхождение с апстримом теперь
ограничено этим одним стилевым правилом (плюс именованные `type` вместо

нужно будет повторить вручную — компонент проверяется тем же способом,
что и остальной код (`pnpm lint`, `pnpm typecheck`), не построчным
diff'ом с апстримом.

## Обновление (2026-10-06): внутри карточки поля не обводятся

Решение владельца, принятое по живому экрану входа — первому месту, где
эти правила стало видно.

### Ни фокус, ни ошибка не рисуют рамку и кольцо

Выше в этом ADR зафиксирована обводка на обёртке контрола: `border` и
`ring` при `focus-within`, терракотовые при `data-[invalid=true]`. Внутри
`FieldCard` это не работает визуально: карточка уже отделяет поля друг от
друга тонкими линиями, и контур вокруг одной строки читается как вторая
карточка внутри первой.

Теперь ни фокус, ни ошибка обводки не дают. **Ошибка показывается цветом
текста самого поля** (`aria-invalid:text-negative`) плюс сообщением под
ним — сообщение и раньше было, менялась только обводка.

Приятное следствие: отрицательные отступы `-mx-2 -my-1` с
компенсирующим `px-2 py-1` существовали только затем, чтобы рамке было
где поместиться. Вместе с рамкой они ушли, и кнопка-глазок встала вплотную
к концу строки — отдельная претензия владельца к макету, которая
закрылась сама.

**Что при этом НЕ изменилось:** `aria-invalid` на самом контроле и
`aria-describedby` на сообщение. Невидящий человек узнаёт об ошибке так
же, как раньше; поменялось только то, как она выглядит.

**Чего это стоит, честно:** видимого индикатора фокуса у поля внутри
карточки больше нет — ориентироваться с клавиатуры придётся по курсору.
Для экрана из двух полей это приемлемо, но правило не стоит переносить на
формы посложнее не подумав.

### `InlineError` берёт токен, который для него и завели

Компонент был написан с `--negative` — терракотой, рассчитанной на
светлый фон. На `--hero` она даёт **1.73:1** и читается как грязно-коричневый
(видно на скриншоте владельца). При этом в `globals.css` у токена
`--negative-hero` стоит комментарий: «ONLY on top of --hero, **for
InlineError on a dark background**» — то есть он был заведён ровно для
этого компонента, а компонент его не использовал. Исправлено: текст и
рамка берут `--negative-hero`, это **5.44:1**.

Отдельно про предложенный вариант «светло-красная подложка с тёмно-красным
текстом»: измерено — тёмная терракота `#9a5238` на тинте `#e9b49c` даёт
**3.15:1**, то есть ниже порога 4.5:1 для обычного текста, и как есть он
не годится. Тот же тинт с цветом чернил `--ink` даёт **7.51:1** и подошёл
бы; это остаётся открытым вариантом, если захочется именно плашку.

### Кольца убраны в самих компонентах, а не отменены у вызывающих

Первая попытка выполнить решение выше гасила кольца классами
`ring-0`/`aria-invalid:ring-0` там, где поля используются. Это не
работает, и причина общая, а не наша: **Tailwind генерирует правило для
каждого класса, встреченного в исходниках**, независимо от того,
перебивает ли его что-то. Класс остаётся на элементе, правило — в
таблице стилей, и в инструментах разработчика всё выглядит так, будто
ничего не убрали. Обсуждения в репозитории shadcn приходят к тому же:
править надо сам компонент, а не наслаивать на него переопределения.

Поэтому кольца удалены там, где объявлены: в `shared/ui/input.tsx`
(фокус и ошибка) и в базовом классе `InputGroup`
(`shared/ui/input-group.tsx`). Переопределения у вызывающих после этого
стали мёртвыми и убраны — иначе они возвращали бы классы обратно.

**Что сохранено намеренно:** `aria-invalid:border-negative` у базового
`Input`. На ней держится единственный признак ошибки у `PillForm` (поле
вайтлиста), и это рамка, а не кольцо. Фокус у `PillForm` свой —
`focus-visible:border-hero`, то есть видимый индикатор фокуса там
остаётся. Внутри `FieldCard` рамка гасится `aria-invalid:border-0`.

**Где кольцо фокуса осталось и должно остаться:** кнопки
(`shared/ui/button.tsx`), тихие ссылки (`text-link.tsx`) и чип-якоря
(`section-index.tsx`). Это не поля ввода, и у них кольцо — единственный
видимый признак фокуса с клавиатуры; убрать его значило бы сделать
навигацию с клавиатуры невидимой.

## Обновление (2026-10-07): автозаполненные поля не красятся браузером

Safari и Chrome рисуют автозаполненное поле своим фоном и своим цветом
текста — у Safari это характерная желтоватая подложка. На зелёном экране
входа и на белой карточке полей это выглядит чужеродно, а поле ещё и
перестаёт читаться как часть карточки.

Переопределить это нельзя: оба браузера объявляют `background-color` и
`color` для `:-webkit-autofill` с `!important` **в UA-таблице**, а
важное объявление браузерного происхождения стоит в каскаде выше любого
авторского, включая авторское `!important`. Поэтому общепринятое решение
— не переопределять, а закрыть: огромная внутренняя тень (`box-shadow:
inset 0 0 0 1000px`, свойство, которого в UA-правиле нет) плюс
`-webkit-text-fill-color`, который имеет приоритет над `color`. Тень
подчиняется `border-radius` элемента, поэтому скруглённые поля не
портятся. Заодно задан `caret-color` — курсор наследовал тот же
браузерный цвет.

Правило одно, в `globals.css`, и **намеренно вне `@layer`** — ровно та
же ловушка каскадных слоёв, что в ADR 0019 и ADR 0046: у наших полей
стоит утилита `shadow-none` (`CARD_FIELD_CONTROL_CLASS`), а утилита
бьёт `@layer base` при любой специфичности, так что внутри `base` это
правило выключал бы тот самый класс, который ему надо пережить.
Незалоёренное объявление стоит выше слоя утилит, поэтому `!important`
не понадобился.

Селектор — `input:is(:autofill, :-webkit-autofill)`: список селекторов
целиком отбрасывается, если браузер не знает хотя бы один из них, а
`:is()` — прощающий. `:autofill` — стандартный псевдокласс,
`:-webkit-autofill` — то, что понимают старые WebKit.

Заплатка обязана быть непрозрачной (прозрачная не закрывает ничего,
браузерный цвет остаётся виден), поэтому правило должно знать цвет
поверхности под полем. Знает не оно: **цвет объявляет тот, кто эту
поверхность рисует**, строкой рядом со своим `bg-*`, а переменная
наследуется вниз, на все поля внутри. `FieldCard` ставит
`[--autofill-surface:var(--background)]` рядом с `bg-background`, инпут
`PillForm` — `[--autofill-surface:var(--card)]` и
`[--autofill-ink:var(--hero)]` рядом со своими `bg-card`/`text-hero`.
Форме при этом не нужно знать ничего: она не красит фон.

Первая версия правила подставляла по умолчанию `var(--card)` — чистый
белый. Это была ошибка: карточка полей на экране входа — `bg-background`
(тёплый серый), и автозаполненное поле выпадало из неё белым пятном.
Запасные значения теперь `--background` и `--ink` — то, что верно для
поля, лежащего прямо на экране. Поле на любой другой поверхности, которое
забудет объявить переменные, молча получит неверный цвет, и именно
поэтому объявление живёт рядом с фоном, а не в форме: иначе о нём некому
вспомнить.

Проверено по собранному CSS: правило лежит на верхнем уровне, не внутри
слоя. Вживую на iPhone ещё не смотрели — как и остальной экран входа.

Источники: обсуждение tailwindlabs/tailwindcss#14031 (тот же приём для
полей shadcn), «How to Remove WebKit's Banana-Yellow Autofill
Background» (M. Schulz), MDN `:autofill` / `:-webkit-autofill`.

## Обновление 2026-10-12: механика формы — один хук, строка — один компонент

Ревью v2 (`docs/superpowers/plans/2026-10-12-v2-review.md`) нашло в
формах два повтора и одну ошибку, которую повтор и прятал.

**Ошибка.** `PillForm` с самого начала отказывался от второго сабмита,
пока первый в полёте (`if (isPending) return`). Три формы v2 этого не
делали: кнопка блокируется, но Enter в поле отправляет форму мимо
кнопки. На входе оба запроса списывались с одного бюджета в три попытки
— одно нажатие стоило двух.

**`useActionForm` (`shared/lib/forms`)** собрал механику, которую
повторяли все четыре формы: валидация той же схемой, что на сервере,
перенос серверных ошибок полей в `react-hook-form`, отказ от повторного
сабмита и тост на недоступный бэкенд (ADR 0046). Реакцию на успех он
намеренно не берёт: вход пишет приветствие и уходит на `/day`, админская
форма показывает тост и очищается, сброс пароля не делает ничего — это
три разные вещи, и хук возвращает `state`, чтобы фича решала сама.

`useActionState` остался на стороне вызова. Если отдать хуку действие и
начальное состояние, он становится обобщённым по типу состояния в
единственном месте, где TypeScript его не сворачивает (`Awaited<TState>`),
и пройти можно только приведением типа — в общем куске, скрывающим ровно
то несоответствие, ради которого он написан. Одна строка на вызов дешевле.

`use-join-waitlist` оставлен как был: его `onSubmit` принимает значение
ловушки отдельным аргументом и отправляет не ту форму значений, что
держит `useForm`. Приведение его к общему виду потребовало бы параметра
-преобразователя, существующего для одного вызова.

**`CardTextField` (`shared/ui`)** — текстовая строка карточки полей, с
тем же API, что у `PasswordField`, намеренно: в одной форме обе строки
теперь читаются одинаково, а не шесть строк против восемнадцати. Внутри
— то, что формой не решается: рендер-проп `CardField`, три
`aria`-атрибута, `CARD_FIELD_CONTROL_CLASS`. Потерять один из атрибутов
(скажем, `aria-describedby`) — это тихо сломать сообщение об ошибке, и
только для скринридера.

## Обновление 2026-10-14: разметку формы тоже вынесли, и ошибки полей больше не перечисляются руками

`useActionForm` вынес механику, но разметка осталась копиями в трёх
виджетах. По итогам ревью релиза v2 вынесена и она — `ActionForm` и
`SubmitButton` (ADR 0012, обновление). Правило «кнопка заблокирована,
пока в форме есть ошибка» и размер крутилки теперь существуют в одном
месте, а не в трёх.

Отдельно — серверная сторона ошибок полей. Каждое действие после
`safeParse` вручную раскладывало `z.flattenError(...).fieldErrors` по
именам: `email?.[0]`, `password?.[0]` и так далее. Добавить поле в схему
и забыть дописать его сюда означало **молча потерять** серверную ошибку
этого поля: человек видит форму без единого сообщения и не понимает, что
не так. Клиентская сторона от этой же ошибки была защищена с самого
начала (`useActionForm` берёт ключи из `defaultValues`), серверная — нет.

Теперь это `firstFieldErrors` (`shared/lib/forms`): перебирает то, что
вернул разбор, и отдаёт по одному сообщению на поле. Поле, которое никто
не перечислил, доезжает само — на это есть тест.

Почему функция лежит рядом с `useActionForm`, хотя зовут её только с
сервера: баррель отдаёт Server Action'у модуль, который экспортирует и
клиентский хук, — в эту сторону безвредно (хук становится клиентской
ссылкой и на сервере не исполняется), в отличие от обратного случая из
ADR 0046, где клиентский бандл потянул бы `server-only` и сборка бы
упала. Альтернативой был семнадцатый сегмент в `shared/lib`, а steiger уже
на шестнадцатом говорит, что их слишком много.


## Обновление 2026-10-22: `useActionForm` отдаёт `validate`

Форма, которая **спрашивает подтверждение перед отправкой** (выбор
статуса служения, ADR 0061), должна знать, что значения верны, **до**
вопроса. Иначе порядок получается обратный: «вы уверены?» → «да» →
«нет, это число неверное», и сообщение об ошибке рисуется под полем,
то есть **за** диалогом, который задаёт вопрос.

`useActionForm` теперь возвращает `validate` — это `trigger` из
react-hook-form под именем, которое говорит, зачем он нужен. Вызывающая
сторона делает `if (await form.validate()) …` и только тогда открывает
диалог.

Добавлено в общий хук, а не написано рядом с одной формой, по тому же
правилу, по которому хук вообще появился: вторая форма с
подтверждением не должна изобретать это заново.
