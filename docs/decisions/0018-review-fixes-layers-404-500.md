# ADR 0018: ревью — слои features/widgets, 404/500, мелкие фиксы UI

## Контекст

Ревью пользователя по ADR 0017 (десять пунктов): часть UI-компонентов
собранных вперемешку в `pages/*` нужно было разложить по слоям FSD
(`features`/`widgets`), несколько экранов имели баги
(кнопка-«призрак» до гидратации, отсутствие валидации формы, нечитаемое
состояние успеха), не хватало реальных экранов 404/500. Ниже — что и
почему изменилось.

## 1. Кнопка «Скопировать ссылку» — рендер сразу, ошибка через try/catch

`web/src/pages/ios-browser-required/ui/copy-link-button.tsx`. Раньше
кнопка стартовала скрытой (`useState(false)` + эффект, проверяющий
`navigator.clipboard` после маунта) — в первом ответе сервера кнопки не
было вовсе, она появлялась только после гидратации и эффекта. Теперь
кнопка в разметке всегда, состояние — `"idle" | "copied" | "error"`;
доступность Clipboard API не проверяется заранее — сам вызов
`navigator.clipboard.writeText` обёрнут в `try/catch` внутри обработчика
клика, ошибка (WebView без разрешения, отсутствие API целиком — оба
случая бросают исключение при обращении к `navigator.clipboard`) ловится
одинаково, логируется (`console.error`) и показывает `InlineError` с
текстом из словаря (`copyLinkError`). Гидратация не расходится: серверная
и первая клиентская разметка идентичны (никакого `useEffect`, меняющего
видимость).

## 2–3. Install sheet: кнопка «Ок» и единый стиль кнопки-триггера

`InstallSheet` (теперь `web/src/widgets/install-sheet/ui/InstallSheet.tsx`,
см. раздел про слои ниже) получил `SheetFooter` с `SheetClose`
(`shared/ui/sheet.tsx`, `slot="close"` — закрывает панель через
react-aria без ручного `onPress`) — тот же `variant="deep" size="role"`,
что и у остальных CTA-кнопок на экранах-состояниях.

Кнопка-триггер «Как установить» до этого была `size="role-lg"` (54px) —
единственное место в проекте, где этот размер ещё использовался. Из
комментария в `shared/ui/button.tsx` про роли каталога: `role-lg`
заведён специально под экран входа (54px), а экран входа удалён ещё в
ADR 0016. Из-за этого кнопка была на 4px выше и с чуть другой
типографикой, чем `CopyLinkButton`/кнопка отправки `WaitlistForm` — все
остальные CTA на экранах-состояниях используют `role` (50px). Осознанных
переопределений цвета не было (`variant="deep"` и там, и там даёт
`bg-hero text-hero-foreground`) — расхождение было только в размере.
Исправлено: `size="role"` везде. Живая проверка (см. ниже) сравнила
вычисленные стили обеих кнопок.

## 4–6. `InstallSheet`/`InstallCarousel` — по слоям FSD

Было: `web/src/pages/install-app/ui/{install-sheet,install-carousel}.tsx`
— вся логика (открыт ли sheet, драг-жест закрытия, шаг карусели,
константы шагов) жила прямо в файлах экрана.

Стало:

- **`web/src/features/install-sheet/model/use-install-sheet.ts`** —
  хук `useInstallSheet()`: состояние `isOpen`, свайп-жест закрытия
  (`dragY`, `CLOSE_DRAG_THRESHOLD = 90`, обработчики `onPointerDown/Move/
  Up/Cancel`). Публичный API слайса — только хук (`index.ts`).
- **`web/src/features/install-carousel/`** — шаги инструкции:
  - `model/steps.ts` — `STEP_KEYS`/`STEP_IMAGES` (сегмент `model`, не
    `ui`/файл компонента — см. ниже, почему).
  - `ui/InstallCarousel.tsx` — сама карусель (стрелки, точки-индикаторы,
    картинка шага), использует константы из `../model/steps`.
- **`web/src/widgets/install-sheet/ui/InstallSheet.tsx`** — виджет:
  раскладка панели (кнопка-триггер, drag-handle, `Sheet` из `shared/ui`,
  `InstallCarousel` из features, футер с кнопкой «Ок»), сам без
  бизнес-логики — только подключает `useInstallSheet()` и рендерит.
- `web/src/pages/install-app/ui/InstallAppScreen.tsx` теперь только
  вызывает `<InstallSheet />` из `@/widgets/install-sheet`.

Аналогично для формы вайтлиста (пункты 7–8, ниже):

- **`web/src/features/join-waitlist/model/use-join-waitlist.ts`** —
  хук `useJoinWaitlist()`: схема zod, `useForm`/`handleSubmit`, локальное
  состояние `submitted` (без бэкенда — как и раньше, ADR 0012/0013).
- **`web/src/widgets/waitlist-form/ui/WaitlistForm.tsx`** — виджет:
  `Controller` вокруг `PillForm` (`shared/ui`), передаёт `errors`/
  `isSubmitDisabled`/`onSubmit` из хука.
- `web/src/pages/coming-soon/ui/ComingSoonScreen.tsx` вызывает
  `<WaitlistForm />` из `@/widgets/waitlist-form`.

### Где константы шагов карусели — сегмент `model`, не файл компонента

Сверено с документацией Feature-Sliced Design (context7,
`feature-sliced/documentation`): сегмент `model` — «the data model:
schemas, interfaces, stores, and business logic», `config` — «configuration
files and feature flags». `STEP_KEYS`/`STEP_IMAGES` — не конфигурация
приложения (это не переключатель поведения), а статичные данные шага
карусели (какие ключи словаря и какие картинки к ним привязаны) — то есть
ближе к «data model» слайса, чем к `config`. Заведены в
`features/install-carousel/model/steps.ts`, `STEP_IMAGES` — `Record<StepKey,
string>` (не массив по индексу, чтобы связь ключ↔картинка была явной, а
не подразумевалась порядком).

### `steiger` и "insignificant-slice"

`fsd/insignificant-slice` (правило из `@feature-sliced/steiger-plugin`,
часть FSD v2.1 "pages first") предлагает сливать `features`/`widgets`
обратно в `pages`, пока у слайса ровно один потребитель — формально верно
для всех пяти новых слайсов выше (`install-sheet` и `install-carousel`
использует только `install-app`, `join-waitlist` и `waitlist-form` —
только `coming-soon`). Это прямое противоречие с явным запросом ревью
(пункты 4/5/7) — разложить именно так. Правило выключено в
`web/steiger.config.ts` (`"fsd/insignificant-slice": "off"`, с
комментарием на месте) — осознанное отступление от эвристики "pages
first" для конкретных слайсов, а не общий отказ от неё. Риск (слайсы
могут расплодиться без нужды) остаётся на код-ревью, раз линтер эту
проверку больше не делает.

## 7–8. Валидация вайтлиста

`PillForm` (`shared/ui/pill-form.tsx`) расширен по границе ADR 0013 —
так же, как `FieldRow`: новые пропсы `name`/`onBlur`/`errors`/
`isSubmitDisabled`, сам компонент по-прежнему не знает правил валидации
(схема — в `features/join-waitlist`). `Input` уже имел вариант
`aria-invalid:border-destructive aria-invalid:ring-3
aria-invalid:ring-destructive/20` в базовых классах (`shared/ui/input.tsx`)
— передача `aria-invalid={invalid || undefined}` включает подсветку без
дублирования стилей. Ошибка — `FieldError` под полем (`aria-describedby`),
кнопка отправки — `isDisabled={isSubmitDisabled}` (не блокирует до
первого submit, блокирует после — как в `showcase/validation-form-demo`,
`mode: "onSubmit"` + `reValidateMode: "onChange"`).

Схема — `z.object({ email: z.string().min(1, t("emailRequired")).email(t
("emailInvalid")) })`, тексты — `screens.comingSoon.emailRequired`/
`emailInvalid` в словаре.

## 9. Плашка успеха

Было: `<p role="status" className="text-list-row font-500 text-primary">`
— обычный текст без заливки, терялся на фоне формы. Стало:
`<div role="status" className="rounded-2xl bg-card px-5 py-4 text-list-row
font-500 text-hero shadow-card">` — карточка на токенах (`--card` = белый,
`--hero` = `#1e4a40`, `rounded-2xl` = 26px из шкалы радиусов, `shadow-card`
— штатная тень). Контраст текста `--hero` (#1e4a40) на `--card` (#ffffff)
— посчитан по WCAG (относительная светлота): ratio ≈ **11.9:1**, с большим
запасом выше порога 4.5:1 для обычного текста. Живая проверка (Playwright)
подтвердила вычисленные `background-color`/`color` совпадают с этими
токенами (см. раздел «Живая проверка»).

## 10. 404 и 500 — настоящие Next.js-конвенции

`app/not-found.tsx` и `app/error.tsx` (+ `app/global-error.tsx`) вместо
страниц по произвольному адресу — Next.js вызывает их автоматически
(`notFound()`/несовпавший маршрут → `not-found.tsx`; необработанное
исключение при рендере сегмента → ближайший `error.tsx`; исключение в
самом корневом `layout.tsx` → `global-error.tsx`, единственный файл,
который обязан сам объявлять `html`/`body`, так как заменяет корневой
layout целиком).

- **`web/src/pages/not-found/ui/NotFoundScreen.tsx`** — серверный
  компонент (`getTranslations`, как остальные `pages/*`): `StatusGlyph
  tone="neutral" code="404"`, заголовок/текст, одна кнопка «На главный
  экран» (`LinkButton href="/day" variant="deep" size="role"`).
- **`web/src/pages/server-error/ui/ServerErrorScreen.tsx`** — обязан
  быть клиентским (контракт `app/error.tsx` требует Client Component,
  получает `{ error, reset }` от Next.js) — `useTranslations`, не
  `getTranslations`. `StatusGlyph tone="alert" code="500"` (терракота —
  `--negative`, ровно цвет из макета пользователя, `rgb(154,82,56)`).
  Две кнопки: «Повторить попытку» (`variant="alert"` — терракотовая
  заливка, как в макете, `onPress={reset}` — штатный сброс границы
  ошибки Next.js, ререндерит сегмент заново) и «На главный экран»
  (`variant="plain"`, `LinkButton href="/day"`). Подпись `Caption`:
  «Код ошибки: {code} · {date}» — `code` берёт `error.digest`, если Next
  его выставил (в проде — почти всегда, в dev — часто нет), иначе
  запасной текст `t("code")` ("500"); `date` — `Intl.DateTimeFormat
  ("ru-RU").format(new Date())`, формат `ДД.ММ.ГГГГ`, как в образце
  каталога компонентов. `useEffect` логирует ошибку (`console.error`) —
  наблюдаемость, тот же паттерн, что и в `CopyLinkButton`.
- **`app/global-error.tsx`** — единственный файл в проекте с текстом не
  из словаря (осознанное, задокументированное здесь исключение из
  правила «ни одной строки в разметке», ADR 0014): вызывается, только
  когда падает сам корневой `layout.tsx`, то есть до того, как
  `NextIntlClientProvider` успел смонтироваться — `useTranslations` в
  этом файле физически не может сработать надёжно, ведь сам провайдер
  словаря мог быть причиной падения. Файл живёт в `web/app/`, не в
  `web/src/pages/` — `eslint-plugin-i18next` (`i18next/no-literal-string`)
  ограничен `files: ["src/**/*.tsx"]` (`web/eslint.config.mjs`), поэтому
  `pnpm lint` не спотыкается об это исключение, а само исключение
  физически не может просочиться в `src/`.

### Не выдумано: кнопки и текст 500 сокращены относительно макета

Макет пользователя (`404-500.html` в основном репозитории) для 404 второй
кнопкой предлагал «Открыть профиль», для 500 — «Работать оффлайн» и текст
про автосохранение отчёта и повторную отправку при восстановлении связи.
Ни профиля, ни офлайн-очереди отчётов в проекте нет (`/day` — по-прежнему
заглушка со статусом Supabase, ADR-0016/17), поэтому:

- 404 — только одна кнопка, «На главный экран» (вместо пары
  primary/secondary из макета).
- 500 — вторая кнопка заменена на «На главный экран» (нейтральное,
  реально работающее действие) вместо «Работать оффлайн».
- Текст 500 переписан без утверждения об автосохранении/автоотправке
  («Отчёт сохранён на устройстве...») — на нейтральное «Не удалось
  загрузить данные. Проверьте соединение и попробуйте ещё раз.» — точнее
  отражает то, что происходит сейчас (ошибка рендера/загрузки, не
  потеря сети конкретно у отчёта, которого ещё не существует).

Отложено (не реализовано, зафиксировано здесь как техдолг): переход в
профиль (профиля пока нет вообще) и офлайн-режим с локальным сохранением
и автоотправкой отчёта (потребует Service Worker background sync или
аналог — сейчас `sw.ts` его не делает, только precache). Когда появится
профиль/офлайн-очередь — вернуть вторые кнопки и уточнить текст 500 по
месту.

### 404/500 и щит доступа: кто что видит

Заблокированные устройства **не видят** ни 404, ни 500 почти никогда — не
из-за специальной проверки внутри этих страниц, а как побочный эффект
устройства самого `web/proxy.ts`: для всех классов, кроме `ios-safari`,
proxy переписывает **любой** путь (не только известные) на
`/access/desktop`/`/access/android`/`/access/ios-browser` — см. `if
(access !== "ios-safari") { ...rewrite... }` до какой-либо проверки
`pathname` в `proxy.ts`. Значит запрос на несуществующий путь с десктопа
или Android никогда не доходит до резолвинга маршрутов Next.js — он
подменяется на заглушку устройства раньше. Проверено живьём: `curl`
без `User-Agent` (классифицируется как `desktop`) на `/does-not-exist`
вернул страницу `/access/desktop` (200, не 404); тот же путь с iPhone
Safari UA вернул настоящий `/not-found` (404). Путь к 404/500 для
заблокированного устройства остаётся только при `DEV_MODE=true` (proxy
выключен целиком) — там оба экрана ведут себя как в обычном Next.js
проекте, что и ожидается для локальной отладки.

`app/error.tsx` перехватывает исключения рендера уже ПОСЛЕ того, как
запрос прошёл через `proxy.ts` и достиг конкретной страницы — то есть
заблокированное устройство физически не может увидеть 500-экран этого
проекта: оно не доходит до рендера `/day` (единственного маршрута, где
вообще есть код, способный бросить исключение, — остальные страницы
статичны). `global-error.tsx` — тот же случай, но для падения самого
`RootLayout`, который рендерится для всех маршрутов без исключения
(включая `/access/*`); это единственный сценарий, где теоретически
заблокированное устройство могло бы увидеть аварийный экран — но текст
намеренно нейтральный (не раскрывает структуру `/day`/`/access/*`,
просто «Сервер не отвечает» + кнопка «Повторить попытку»), так что
ничего не «протекает» через эту границу.

## Живая проверка

`pnpm lint` (ESLint + `steiger`), `pnpm typecheck`, `pnpm test` (23/23),
`pnpm build` — чисто.

`curl`, `DEV_MODE=false`, `next dev`:

- `/access/ios-browser` (UA — Instagram-webview) — кнопка «Скопировать
  ссылку» присутствует в самом первом HTML-ответе сервера (без выполнения
  JS) — пункт 1 подтверждён на уровне разметки.
- `/does-not-exist` без `User-Agent` → 200, содержимое
  `/access/desktop` — подтверждает, что щит перехватывает произвольные
  пути раньше резолвинга маршрутов.
- `/does-not-exist` с iPhone Safari UA → настоящий 404, заголовок
  «Страница не найдена», текст совпадает со словарём.
- `/day` с `DEV_MODE=true` при принудительно брошенном исключении внутри
  `DayPage` (временная правка, убрана сразу после проверки — `git diff`
  на `web/src/pages/day/ui/DayPage.tsx` после проверки чист) → HTTP 500,
  в теле — «Сервер не отвечает», «Повторить попытку», «На главный
  экран», «Код ошибки».
- `/day?pwa=1` с iPhone Safari UA → форма вайтлиста в исходном HTML
  (`type="email"`, «Ваш email», «Записаться») — подтверждает, что форма
  по-прежнему рендерится на сервере, валидация не сломала SSR.

Playwright (реальный браузер, порт 3110, `DEV_MODE=false`): проверены
живьём — открытие/закрытие install sheet кнопкой «Ок», совпадение
вычисленных стилей кнопки-триггера и кнопки «Ок» (высота 50px, заливка
`--hero`), сценарий валидации формы вайтлиста (пустая отправка → ошибка +
заблокированная кнопка, невалидный email → ошибка, валидный → ошибка
исчезает, кнопка разблокируется, успешная отправка → плашка), путь
ошибки копирования ссылки с намеренно сломанным `navigator.clipboard`.
Подробные результаты и скриншоты (`​.playwright-mcp/v3-*.png` в основном
репозитории) — см. отчёт задачи в истории агента; при обнаружении
расхождений между этим описанием и фактическим поведением живой проверки
считать приоритетным фактическое поведение и завести отдельный ADR/фикс.
