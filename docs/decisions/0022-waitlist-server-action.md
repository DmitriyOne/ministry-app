# ADR 0022: отправка формы вайтлиста — серверное действие Next.js

> **Обновление: раздел «Куда сохраняются данные» устарел.** Адрес больше
> не пишется в серверный лог: `persistWaitlistSignup` вызывает функцию
> `join_waitlist` в Supabase (ADR 0033, доступ — ADR 0037). Остальное в
> этом ADR (серверное действие, схема zod, причины, по которым у `<form>`
> нет `action`) по-прежнему верно.

## Контекст

Форма вайтлиста (`widgets/waitlist-form` + `features/join-waitlist`,
ADR 0013/0018) валидировала email через react-hook-form + zod, но сама
"отправка" была чисто клиентской: `onSubmit` просто переключал локальный
`useState` в состояние "успех", реального запроса никуда не было.
Пользователь захотел настоящую отправку — серверным действием Next.js
(`"use server"`), а не клиентским обработчиком, раз таблицы для хранения
пока нет и отправлять было объективно некуда.

Отдельно: `ZodString.email()` помечен `@deprecated` в zod 4 (используемая
версия — `4.6.5`) в пользу самостоятельного `z.email()`.

## Варианты (отправка формы)

1. **Route Handler (`app/api/.../route.ts`) + `fetch` с клиента.**
   Работает, но требует вручную писать fetch-обёртку, сериализацию
   ошибок и ручной AbortController/loading-стейт — то, что Server
   Actions + `useActionState` уже решают на уровне React/Next.js.
2. **Server Action, вызванный через нативный `<form action={formAction}>`**
   (без JS — прогрессивное улучшение), валидация только на сервере через
   `FormData`. Простое и максимально совместимое (работает без JS), но
   для этого экрана теряет то, что уже есть: react-hook-form с
   `zodResolver` для мгновенной валидации по `onBlur`/`onChange` без
   похода на сервер — пришлось бы либо дублировать схему под `FormData`,
   либо выбросить клиентскую валидацию совсем.
3. **Server Action, вызванный вручную из `handleSubmit` react-hook-form
   (`useActionState` + `startTransition`), с общей zod-схемой на клиенте
   и сервере.** Официально задокументированный паттерн интеграции
   react-hook-form с Server Actions (react-hook-form,
   `advanced-usage.mdx`, раздел "Server Actions / useActionState") и
   пример из документации Next.js (`docs/01-app/02-guides/forms.mdx`,
   раздел "Validation errors").

**Выбран вариант 3.**

### Как это устроено

- **Схема — одна**, `features/join-waitlist/model/schema.ts` (без
  `"use client"`/`"use server"`, чистый модуль): `createJoinWaitlistSchema(t)`
  — фабрика, принимающая переводчик (`useTranslations` на клиенте,
  `getTranslations` на сервере — оба вызываются с одним и тем же
  namespace `screens.comingSoon`, поэтому сообщения об ошибках всегда
  из словаря, ADR 0014). Дублирования схемы нет — оба места импортируют
  одну и ту же фабрику.
- **Действие** — `features/join-waitlist/api/join-waitlist-action.ts`
  (`"use server"`), экспортирует только асинхронную функцию `joinWaitlist`
  (единственное, что разрешено экспортировать из `"use server"`-файла) —
  все типы (`JoinWaitlistActionState`, `JoinWaitlistFormValues`) и
  константа начального состояния (`joinWaitlistInitialState`) вынесены в
  `schema.ts` именно поэтому.
- **Связка с react-hook-form** — `features/join-waitlist/model/use-join-waitlist.ts`:
  `useForm` с `zodResolver(schema)` для клиентской валидации до отправки
  (кнопка блокируется по `hasErrors`, как и раньше, ADR 0013), плюс
  `useActionState(joinWaitlist, joinWaitlistInitialState)` — `onSubmit`
  собран как `handleSubmit((values) => startTransition(() => submitAction(values)))`:
  `handleSubmit` сначала гоняет ту же zod-схему на клиенте и не даёт
  дойти до сервера с уже отвергнутыми значениями, а если валидация
  прошла — передаёт **уже типизированный объект**, а не `FormData`,
  напрямую в диспетчер `useActionState` (то же самое, что делает
  официальный пример из документации react-hook-form). `startTransition`
  обязателен: вызов диспетчера `useActionState` вне `form action=.../
  formAction=...` требует явной транзакции — без неё React 19 кидает
  предупреждение в рантайме и `isPending` не обновляется (обнаружено
  вживую, Playwright, `pnpm dev`, консоль браузера).
- **Ошибки с сервера** синхронизируются в react-hook-form через
  `setError("email", {type: "server", message})` в `useEffect`,
  подписанном на `state` — легитимный случай `useEffect` (синхронизация
  внешнего состояния, не обход отсутствующего рендер-стейта), тот же
  паттерн, что показан в документации react-hook-form для этого сценария.
  Сервер валидирует по той же схеме заново (`schema.safeParse`) — клиентскую
  валидацию можно обойти прямым POST на действие, поэтому серверная
  проверка обязательна независимо от клиентской.
- **Состояние ожидания** — `isPending` от `useActionState` блокирует
  кнопку (`isSubmitDisabled={hasErrors || isPending}`) и меняет текст
  кнопки на `t("submitButtonPending")` — без изменений в `shared/ui/
  pill-form.tsx` (форма — "глупая", кнопка просто принимает готовый текст
  и флаг `isSubmitDisabled`, ADR 0013).

### Без JavaScript

Действие вызывается вручную из `handleSubmit` (вариант 3), не через
`<form action={formAction}>` — значит без JS форма не отправится вообще
(submit ничем не перехватывается, а нативного `action` на `<form>` нет).
Это осознанный компромисс, не единственный на этом экране: сама разметка
(`ShellLoading`/`ShellReadyScript`, ADR 0019) уже требует JS, чтобы
приложение вообще стало видимым — экран `/soon` без JavaScript не
показывает пользователю ничего, кроме индикатора загрузки. Требовать JS
и для отправки формы этого же экрана — не новое ограничение, а
продолжение уже принятого.

## Куда сохраняются данные

Таблицы для вайтлиста в Supabase нет, миграции — файлами в
`backend/supabase/migrations/` (отдельная задача, вне этого ADR и вне
разрешённой области этой работы). Точка сохранения — одна функция,
`persistWaitlistSignup` (локальная, не экспортируемая, внутри
`join-waitlist-action.ts`): сейчас она пишет структурированную запись в
серверный лог (`console.info("[join-waitlist] новая заявка", { email })`,
виден в `pnpm dev` и в логах Vercel). Это не имитация записи с
искусственной задержкой и не `TODO`-заглушка "здесь будет запрос" —
реальный, сразу выполняющийся побочный эффект: адрес не теряется молча,
его видно в логах, и функция меняется на один `insert` в Supabase одним
изменением в одном месте, когда появится таблица и миграция под неё.
**Честно: сейчас email никуда, кроме серверного лога, не сохраняется.**

## Устаревший метод zod: `z.string().email()` → `z.email()`

`ZodString.email()` в zod 4 помечен `@deprecated` в пользу
самостоятельного `z.email()` (обе — top-level функции-валидаторы формата,
как и `z.url()`/`z.uuid()`). Раньше оба разных сообщения об ошибке
(пустое поле / неверный формат) обеспечивались двумя аргументами одного
чейна: `z.string().min(1, emailRequired).email(emailInvalid)`. `z.email()`
сам по себе не отличает "пусто" от "не email" (пустая строка у него тоже
"неверный формат"), поэтому пришлось сохранить эти два сообщения через
`.pipe()`: `z.string().min(1, t("emailRequired")).pipe(z.email(t("emailInvalid")))`
— сначала проверяется непустота (свой текст ошибки), затем непустая
строка валидируется как email отдельной схемой (свой текст ошибки).
Проверено на реальных данных (`node -e`, локальный zod `4.6.5`): пустая
строка → `"Укажите email"`, `"abc@"` → `"Неверный формат email"`,
`"a@b.com"` → успех.

По кодовой базе пройдено `grep` на другие вызовы `.email()`/`.url()`/
`.uuid()` — устаревших вызовов, кроме исправленного, не нашлось (второе
совпадение `.email()` — `pages/components/validation-form-demo.tsx` — вне
разрешённой области этой задачи, там работает параллельный агент).

## Последствия

- Плюсы: одна схема на клиент и сервер (ADR 0014-совместимо — все
  сообщения из словаря), настоящая серверная валидация (нельзя обойти
  клиентом), пер-полевые ошибки не изменили поведение для пользователя
  (тот же `FieldError` под тем же полем), официально задокументированный
  паттерн — не самодельная интеграция.
- Минусы: форма не работает без JavaScript (см. раздел выше — уже
  принятый для этого экрана компромисс, не новый). Данные пока реально
  нигде не хранятся, кроме серверного лога — при перезапуске/деплое
  лог не персистентен; это осознанно временно до появления миграции
  Supabase.
- Следующий шаг (не в этом ADR): миграция `backend/supabase/migrations/`
  под таблицу вайтлиста + замена тела `persistWaitlistSignup` на
  `insert` через `@/shared/api/supabase/server`.

## Обновление 2026-09-25: почему у `<form>` нет `action`, хотя это React 19/Next.js

Пользователь спросил, почему форма не отправляется через нативный проп
`<form action={...}>`, раз это штатный механизм React 19/Next.js App
Router. Разобрано через актуальную документацию (context7:
`react-hook-form/documentation`, включая `advanced-usage.mdx` и
`ts.mdx`/`get-started.mdx` про их собственный компонент `<Form>`) и
поиск (exa) по практике 2025–2026 года, плюс — проверено вживую
(`pnpm dev`-аналог на порту 3119, `DEV_MODE=true`, Playwright), а не
только в теории.

### Ключевой факт: `action` и `handleSubmit` не совместимы напрямую

`react-hook-form`'s `handleSubmit(onValid, onInvalid)` **всегда** вызывает
`event.preventDefault()` — это описано в его исходниках и подтверждено
обсуждением самой команды React в GitHub issue
[facebook/react#29034](https://github.com/facebook/react/issues/29034)
про `<form>` actions: если `onSubmit` уже вызвал `preventDefault()` до
того, как React обработал форму, — React **не запускает** функцию из
`action`. Это официально задокументированное, осознанное поведение (в
том же issue его использует сам Lee Robinson (Vercel) как способ
«опт-аута» из автоматического поведения `action` при сохранении ручного
вызова через `startTransition`).

Проверено вживую: `<form action={submitAction} onSubmit={handleSubmit(...)}>`
(временный эксперимент, не попал в итоговый код) —
1. Пустая отправка → клиентская ошибка "Укажите email", `grep
   "join-waitlist" dev.log` — **ноль** записей (сервер не тронут, как и
   раньше).
2. Валидная отправка → в логе сервера **одна** запись `[join-waitlist]
   новая заявка` и **один** трейс `└─ ƒ joinWaitlist(...)`, `POST /soon`
   тоже один. То есть `action={submitAction}`, поставленный рядом с уже
   существующим `onSubmit={handleSubmit(...)}`, **не делает ничего** —
   ни разу не сработал ни на невалидной, ни на валидной отправке,
   потому что `handleSubmit` каждый раз успевает вызвать
   `preventDefault()` первым. Значит, добавить `action` к текущей форме
   можно только как мёртвый, никогда не срабатывающий проп — хуже, чем
   его отсутствие: читающий код решит, что это работающий путь
   отправки (например, автономно, без JS), а это не так.

### Чтобы `action` реально заработал — пришлось бы отказаться от того, что просил сохранить ADR 0013/этот ADR

Единственный способ заставить React реально вызвать `action` — **не
вызывать `preventDefault()` в `onSubmit`** (или не использовать
`onSubmit` вообще) и положиться на нативную отправку. Но тогда:
- клиентская валидация до обращения к серверу (обязательное требование
  этой задачи и ADR 0013 — кнопка блокируется, ошибки под полем **до**
  похода на сервер) перестаёт быть гейтом: невалидные данные всё равно
  уйдут на сервер (сервер их отклонит — но текущее «не долетает совсем»
  поведение исчезнет, каждая пустая отправка станет реальным запросом).
- Действие пришлось бы переписать под сигнатуру `(prevState, formData:
  FormData)`, потеряв текущую типизированную `JoinWaitlistFormValues`,
  которую сейчас разделяют клиент и сервер через одну и ту же
  `createJoinWaitlistSchema` — пришлось бы либо парсить `FormData`
  вручную (`formData.get("email")`), либо тащить отдельный адаптер.
- Официальный пример интеграции из документации `react-hook-form`
  (`advanced-usage.mdx`, раздел "Server Actions / useActionState") —
  **именно** `<form onSubmit={handleSubmit((data) => submitAction(data))}>`,
  без `action` на `<form>` вообще. Это ровно то, что уже реализовано в
  этом ADR (вариант 3) — не самодельный обход, а буквально
  задокументированный паттерн самой библиотеки.

Отдельно у `react-hook-form` есть свой компонент `<Form action="/api/...">`
(`get-started.mdx`/`ts.mdx`) — но его `action` это **URL строки для
fetch**, а не функция под React 19 Actions/`useActionState`: он не
интегрируется с уже построенным `useActionState`-состоянием
(`isPending`/типизированный `state`) и переписывать под него означало бы
терять то, что уже работает, ради формального "здесь есть проп action".

### Про прогрессивное улучшение — не аргумент здесь

Обычный довод в пользу `action` — работа без JavaScript. Он не
применим к этому экрану: сама разметка `/soon` не показывает ничего,
кроме индикатора загрузки, пока не выполнится `ShellReadyScript`
(ADR 0019) — без JS пользователь не увидит форму вообще, не то что
сможет её отправить. Требовать нативный `action` ради поддержки
no-JS-сценария, которого и так нет ни на одном другом уровне этого
экрана, — противоречиво.

### Решение

**Реализация не меняется** — `<form onSubmit={handleSubmit(...)}>` +
`startTransition` + `useActionState`, без `action` на `<form>`,
остаётся. Это не «оставили как было, потому что лень» — это
подтверждённый вживую и документацией вывод: добавление `action` здесь
либо ничего не делает (мёртвый код, если `onSubmit` остаётся), либо
ломает уже согласованные требования (клиентский гейт до сервера,
общая типизированная схема). Если/когда на этом экране появится
осознанная причина для no-JS доступности (например, отдельный указ
пересмотреть ADR 0019), это отдельное решение с пересмотром обоих ADR
разом, не точечная правка одной формы.
