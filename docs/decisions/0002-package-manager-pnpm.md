# ADR 0002: Пакетный менеджер — pnpm workspaces, а не npm

## Контекст

Монорепо из двух пакетов (`web`, `backend`) нуждается в workspace-механизме:
общая установка зависимостей, `--filter` для запуска скриптов в конкретном
пакете, единый lock-файл.

## Варианты

1. **npm workspaces** — встроен в npm ≥7, не требует доп. инструментов.
2. **pnpm workspaces** — отдельный пакетный менеджер с собственным
   `pnpm-workspace.yaml`.
3. **yarn workspaces / Turborepo / Nx** — альтернативные экосистемы,
   избыточны для текущего масштаба (2 пакета, нет сложного task-graph).

## Решение

Выбран **pnpm** с `pnpm-workspace.yaml` (`web`, `backend`).

Причины:
- Строгая изоляция зависимостей (non-flat `node_modules` через
  content-addressable store) снижает риск фантомных зависимостей — что
  особенно важно на старте проекта, пока границы пакетов ещё не устоялись.
- Быстрее и экономнее по месту на диске, чем npm/yarn, за счёт единого
  глобального стора и жёстких ссылок.
- `pnpm --filter <pkg> run <script>` — удобный, лаконичный способ запускать
  скрипты в конкретном пакете из корневых скриптов (`dev`, `db:*`, `lint`
  и т.д.), без дополнительных инструментов вроде Turborepo.
- Официально поддерживается Vercel (прод-деплой фронтенда) "из коробки".

## Последствия

- Все участники и CI обязаны использовать pnpm (зафиксировано через
  `packageManager` в корневом `package.json` и `engines`).
- `npm install` / `yarn install` в этом репозитории не поддерживаются и не
  тестировались.
- Если появится необходимость в сложном task-graph с кэшированием между
  пакетами — можно добавить Turborepo поверх существующей pnpm-структуры
  без её изменения.
