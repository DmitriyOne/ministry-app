# ADR 0042: CI на GitHub Actions — пять workflow, прод-деплой только руками

## Контекст

До этого решения ни одна проверка не выполнялась автоматически. Vercel
собирает проект на каждый push, поэтому ошибка типов видна на деплое, но
`lint` (включая `steiger`, сторожащий границы FSD), `test` и pgTAP
прогонялись только на машине разработчика — то есть не прогонялись вообще,
если про них забыли. При этом pgTAP — единственное, что проверяет модель
доступа к данным (RLS без политик, отозванные гранты, `execute` только у
`service_role`), и однажды он уже поймал ошибку до попадания в базу (ADR
0037, 0039).

Отдельно — три задачи, которые делались руками или не делались вовсе:

1. Бесплатный проект Supabase встаёт на паузу после 7 дней неактивности.
2. Автоматических бэкапов на бесплатном тарифе нет, а в базе уже лежат
   персональные данные — адреса вайтлиста и push-подписки.
3. `CLAUDE.md` прямым текстом называет временным состоянием то, что
   `db:push` и `functions:deploy` выполняются вручную с ноутбука, и
   требует перенести их в CI, когда тот появится.

Подробный разбор каждого workflow, со шагами и обоснованиями из документации
GitHub, — в `docs/plans/2026-10-03-github-ci.md`. Здесь зафиксированы только
решения и их последствия.

## Варианты

### A. Пять отдельных workflow на GitHub Actions — выбрано

Проверки, pgTAP, keep-alive, бэкап и прод-деплой живут в своих файлах с
разными триггерами. Код уже на GitHub, платить не надо (приватный репозиторий
на бесплатном тарифе даёт 2000 минут в месяц, мы расходуем десятки).

### B. Один workflow со всеми job

Меньше файлов, но триггеры у этих задач несовместимы: проверкам нужен
`pull_request`, pgTAP — фильтр по `backend/**`, keep-alive и бэкапу —
`schedule`, деплою — `workflow_dispatch` и только он. Свести их в один файл
означает либо запускать всё на всё, либо писать условия `if:` внутри job —
то есть переносить маршрутизацию из декларативных триггеров в императивные
проверки, где она хуже видна и не отражается в списке прогонов.

### C. Только проверки Vercel

Vercel уже собирает проект и ловит ошибки типов. Но он не запускает ни
`steiger`, ни vitest, ни pgTAP — а pgTAP требует Docker, которого в сборке
Vercel нет. Класс ошибок, который важнее всего (модель доступа к данным),
остался бы непокрытым.

### D. Git-хуки вместо CI

Дешево и быстро, но хук выполняется на той же машине, где уже всё работает,
обходится флагом `--no-verify` и ничего не знает ни о расписаниях, ни о
бэкапах. Как дополнение годится, как замена — нет.

## Решение

### Пять workflow

| Файл | Триггер | Секреты |
|---|---|---|
| `ci.yml` | `pull_request`, push в `develop`/`master` | нет |
| `db-test.yml` | то же + фильтр `backend/**` | нет |
| `health-ping.yml` | `schedule` раз в 3 дня, `workflow_dispatch` | 1 |
| `supabase-backup.yml` | `schedule` раз в сутки, `workflow_dispatch` | 1 |
| `supabase-deploy.yml` | **только** `workflow_dispatch` | 1 в окружении + 1 общий |

### Сторонние actions — по полному SHA коммита, не по тегу

Тег можно переместить на другой код. Компрометация одного action даёт доступ
ко **всем** секретам репозитория, поэтому рядом с SHA в комментарии пишется
человекочитаемая версия, а сам SHA сверяется с репозиторием самого action, не
с форком. Права токена задаются явно (`contents: read`, а у `health-ping` —
`permissions: {}`, потому что он вообще не читает репозиторий).

### Сборки в CI нет — осознанный пропуск

`pnpm build` — это `dotenv -e envs/web.local.env -- ...`, а этот файл в
`.gitignore` и на раннере его не существует; `env.ts` к тому же падает
fail-fast без обязательных переменных. Vercel собирает проект на каждый push
и ловит тот же класс ошибок. Варианты на будущее (генерировать env-файл из
секретов; сделать отсутствие файла нефатальным) рассмотрены и отложены.

### Свежесть `database.types.ts` проверяется в `db-test.yml`

`pnpm typecheck` эту ошибку поймать не может: он сверяет код **с файлом**
типов, а не с базой. Поэтому забытый `pnpm db:types` после миграции оставляет
фронтенд типизированным по схеме, которой больше нет, и все проверки при этом
проходят. Job перегенерирует файл на уже поднятом стеке и падает на
`git diff --exit-code`. Стоит это почти ничего — стек там всё равно запущен
для pgTAP.

### Keep-alive не переносится из `sole-trader-discovery` один-в-один

Ни `/api/v1/health` (отвечает 204 и намеренно не трогает ни Supabase, ни
auth — им проверяется достижимость собственного origin), ни Edge Function
`health` (статический JSON) до базы не доходят, поэтому пинг любого из них
таймер неактивности **не сбрасывает**. Запрос идёт прямо в PostgREST,
методом `HEAD` (запрос выполняется, тело не возвращается — ни один адрес из
вайтлиста не может попасть в лог CI) и секретным ключом: таблицы закрыты для
`anon` полностью, и publishable-ключ не сделает по ним ни одного успешного
запроса. Проверено локально: без ключа — `42501`, publishable — `401`,
секретный — `200`.

### Бэкап — артефакт workflow, и репозиторий обязан быть приватным

`pg_dump` схемы `public` в custom-формате плюс по одному CSV на таблицу
(таблицы ищутся через `pg_tables`, так что новая таблица попадёт в бэкап без
правки workflow). Пустой дамп опаснее отсутствующего, поэтому job отказывается
принимать файл меньше 512 байт или CSV без строки заголовка. Артефакты
читаемы всем, кто может читать репозиторий, а в дампе персональные данные —
**если репозиторий когда-нибудь станет публичным, workflow надо сначала
отключить**.

### Прод-деплой: `workflow_dispatch`, граф `guard → db-test → deploy`

Запись в прод остаётся осознанным действием человека, но выполняется
воспроизводимо из чистого окружения, а не с ноутбука. Подтверждение стоит
**первым**: внутри job `deploy` оно сначала дождалось бы шлюза pgTAP и
запроса одобрения, чтобы потом сообщить, что галочку не поставили.
Неподтверждённый запуск **падает**, а не завершается зелёным: зелёная галочка
читалась бы как «деплой ушёл». Секреты лежат в окружении `production`,
поэтому до них дотягивается только последний job и только после pgTAP.
`cancel-in-progress: false` — прерванный `db push` хуже доведённого до конца.

`supabase db reset` не встречается в этом файле ни в каком виде, и шапка
говорит об этом прямо: на привязанном проекте он уничтожает данные в облаке.

### `supabase link` не используется — токен получает одно разрешение

Документация Supabase по scoped personal access tokens перечисляет, что
`supabase link` требует **Project Settings**, **API Keys** и **API Key
Secrets**, все с правом Read. Последнее — это право читать секретный ключ
проекта (`sb_secret_…`), то есть токен в CI оказался бы не слабее самого
ключа, обходящего RLS. Платить этим за одну команду незачем: и `db push`, и
`functions deploy` умеют принимать цель напрямую.

```
supabase db push --db-url "$SUPABASE_DB_URL"
supabase functions deploy --project-ref "$SUPABASE_PROJECT_REF" --use-api
```

Токену остаётся **Edge Functions: read & write** и ничего больше. Миграции от
токена не зависят вовсе: та же документация прямо говорит, что команды,
аутентифицированные паролем базы, правами токена не ограничены. `--use-api`
собирает функции на стороне Supabase, поэтому Docker на раннере не нужен.

Строка подключения должна быть percent-encoded — если в пароле есть `@`, `:`,
`/` или `?`, кодировать надо в самом значении секрета, иначе URL разберётся не
на те части.

Честная оговорка: `SUPABASE_DB_URL` — секрет уровня репозитория, общий с
бэкапом, а не секрет окружения `production`. Запереть его в окружении ради
деплоя смысла нет: тот же бэкап уже ходит с ним в базу через `psql` и может
выполнить там что угодно. Настоящая граница здесь другая — кто может добавить
workflow, тот уже может всё.

## Последствия

- Проверки начинают работать сразу после мержа, без единого секрета.
- **Расписания запускаются только с ветки по умолчанию** (`master`). Пока
  файлы лежат в `develop`, `health-ping` и `supabase-backup` не сработают ни
  по cron, ни кнопкой — у `workflow_dispatch` даже не появится кнопки «Run
  workflow». Одного мержа в `develop` недостаточно.
- GitHub задерживает `schedule` на 15+ минут при нагрузке и **отключает
  расписания после 60 дней без активности в репозитории**. Для keep-alive это
  значит: репозиторий, заброшенный на два месяца, перестаёт защищать базу от
  паузы.
- Артефакты живут максимум 90 дней и не являются внешним хранилищем. На
  предзапусковом масштабе этого достаточно; с ростом данных понадобится
  настоящий бэкап.
- `db-test.yml` не запускается на чисто фронтовых изменениях. Это и есть
  цель фильтра, но значит, что ошибка в миграции, внесённая правкой вне
  `backend/**`, проверку минует.
- Шаги pgTAP продублированы в `db-test.yml` и `supabase-deploy.yml`. Пока их
  четыре — терпимо; если вырастут, выносить в переиспользуемый workflow
  (`on: workflow_call`).

## Что нужно добавить в GitHub

`Settings → Secrets and variables → Actions`, вкладка **Variables**:

| Имя | Значение |
|---|---|
| `SUPABASE_URL` | `https://<ref>.supabase.co` |
| `SUPABASE_PROJECT_REF` | `<ref>` |

Обе — переменные, не секреты: и адрес, и ref проекта публичны.

Вкладка **Secrets** (уровень репозитория):

| Имя | Для чего |
|---|---|
| `SUPABASE_SECRET_KEY` | keep-alive |
| `SUPABASE_DB_URL` | бэкап и `db push` |

Для `SUPABASE_DB_URL` брать строку **Session pooler**: прямое подключение к
Supabase с раннеров GitHub по IPv4 не всегда доступно, у них только IPv6.

`Settings → Environments → production`, секрет окружения:

| Имя | Разрешения токена |
|---|---|
| `SUPABASE_ACCESS_TOKEN` | только **Edge Functions: read & write** |

  данные остаются в Великобритании» остаётся верным буквально: в EU уходят
  только отчёты об ошибках Sentry (ADR 0041). Схема в проект пока не
  применена — первый `supabase-deploy` с `target: migrations` её и
  раскатает.
- ~~`PG_MAJOR` не сверен~~ — **закрыто 4 октября 2026**: облачный проект
  отвечает `PostgreSQL 17.11`, то есть значение `"17"` верное. Поднимать его
  придётся, когда Supabase обновит мажорную версию проекта: `pg_dump`
  отказывается дампить сервер новее себя.
- **`Required reviewers`** на окружении `production` требует на приватном
  репозитории тариф GitHub Pro или выше. Если недоступно, роль ручного шлюза
  выполняет галочка подтверждения, которую проверяет job `guard`.
